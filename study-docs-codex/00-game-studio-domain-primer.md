# 00 游戏工作室领域知识导论

这篇文档不讲 CCGS 的具体配置，而是先解释它所模拟的真实游戏开发世界。读完后，你应该能够理解：为什么一个看起来简单的功能会涉及许多角色，为什么开发前要写设计和架构文档，以及为什么“代码写完”通常不等于“功能完成”。

文档较长，不要求一次记住。第一次阅读可以只看第 1–3、11–13 节；
遇到具体术语时，再回到第 4–10 节查阅。最重要的不是记住英文缩写，
而是知道一个概念在降低什么风险、由谁负责、会交给谁使用。

本文采用“英文术语（常用中文翻译）”格式。中文游戏行业并没有完全统一
的翻译，例如 `Game Designer` 既可能叫“游戏设计师”，也常被称为“游戏
策划”；`Producer` 可能译为“制作人”或“项目制作负责人”。遇到多个译法
时，本文会同时列出，并解释这个名字强调的职责。

## 1. 先用一句话理解游戏开发

游戏开发是在有限时间和预算内，由多个专业领域共同制作一种可交互体验。

这句话包含四个关键事实：

1. 游戏不是单纯的软件，它还包含规则、美术、声音、叙事和玩家体验。
2. 游戏不是静态作品，玩家会以设计者没预料到的方式操作它。
3. 时间、人员、平台性能和资金永远有限，不可能实现所有想法。
4. 不同专业会互相影响，一个领域的决定经常给其他领域增加工作。

因此，游戏工作室最重要的能力不是“每个人都很厉害”，而是让不同专业围绕同一个玩家体验协同工作，并尽早发现错误方向。

## 2. 为什么一个小功能也会涉及很多人

假设游戏要加入 Dash（位移冲刺）：玩家按下按钮，角色快速向前移动一段距离。

注意两个英文词在中文里都常被译成“冲刺”：`Dash` 是角色的快速位移
能力，`Sprint` 是团队的一段短开发周期。本文用 Dash 和 Sprint 区分它们。

直觉上它似乎只是几行代码，但很快会出现这些问题：

- 冲刺的目的是什么，是躲避、赶路还是攻击？
- 冲刺是否消耗体力，有没有冷却时间？
- 玩家能否穿过敌人、陷阱或狭窄缝隙？
- 冲刺时角色无敌吗？无敌多久？
- 键盘、手柄和触屏分别如何操作？
- 动画如何表现速度，镜头是否需要轻微拉伸？
- 应播放什么音效，敌人是否能听到？
- 网络游戏中由客户端还是服务器判断位置？
- 低帧率时冲刺距离是否仍然一致？
- 新玩家怎样学会它？残障玩家能否舒适触发？
- 它会不会让某些关卡、敌人或 Boss 失去挑战？
- 修改以后需要重新测试哪些旧功能？

这些问题分别属于设计、程序、动画、特效、音频、关卡、网络、UX、可访问性、QA 和制作管理。小团队里可能是同一个人承担多个角色，但问题本身不会因为团队小就消失。

CCGS 创建大量 Agent，不是说独立开发者必须雇 49 个人，而是把这些不同的思考角度显式化，防止一个通用助手只从“把代码写出来”的角度处理问题。

## 3. 理解组织结构的三个维度

初学者容易把所有角色混成一张很长的名单。更简单的理解方法是看三个维度。

### 维度一：专业领域——在解决哪类问题

```text
设计：游戏规则和玩家体验
程序：系统结构和功能实现
美术：视觉语言和资产生产
音频：声音反馈、音乐和氛围
叙事：角色、世界、情节和文字
QA：验证、缺陷和质量风险
制作：范围、排期、依赖和交付
运营：发布、数据、社区和持续更新
```

### 维度二：决策层级——在什么尺度上做决定

```text
Director（总监）：决定方向和原则
Lead（负责人/主责）：把方向转成领域方案
Specialist（专家）：完成具体专业工作
```

这三个名称本身就带有层级语义：

- `Director` 来自 `direct`（引导方向），重点是定方向、做取舍；
- `Lead` 来自 `lead`（带领），重点是带领一个专业领域完成目标；
- `Specialist` 来自 `specialize`（专门化），重点是在窄领域内提供深度。

例如：

- Creative Director 决定“战斗应鼓励耐心，而不是连续猛攻”；
- Game Designer 把它变成体力、敌人攻击窗口和奖励规则；
- Systems Designer 计算体力恢复、伤害和硬直公式；
- Gameplay Programmer 按规则实现代码。

层级表示决策范围，不表示一个人比另一个人“更重要”。Specialist 往往拥有最深的具体专业知识，只是不应该独自改变整个游戏方向。

### 维度三：时间阶段——现在最需要降低什么风险

```text
早期：这个想法值得做吗？
设计期：规则足够明确、一致吗？
架构期：技术上能可靠实现吗？
预制作：完整体验和生产管线跑得通吗？
生产期：能否按计划持续交付内容？
打磨期：性能、平衡和体验达到标准吗？
发布期：玩家能否安全获得和使用产品？
```

同一个角色在不同阶段的重要性不同。概念期 Game Designer 很活跃；发布期 Release Manager、QA Lead 和 DevOps Engineer 更关键。

把三个维度合在一起，可以得到一张最小心智图：

```text
玩家体验（为什么做）
    ↓ Creative / Design
游戏规则（做成什么）
    ↓ GDD / Acceptance Criteria
技术结构（怎样实现）
    ↓ Architecture / TR / ADR
生产计划（由谁在何时做）
    ↓ Epic / Story / Sprint / Milestone
实现结果（实际做出了什么）
    ↓ Code / Assets / Build
质量证据（如何证明完成）
    ↓ Tests / Review / Playtest / Gate
```

CCGS 的大部分术语都能放进这张图，而不是互不相关的几十个概念。

## 4. 主要角色到底做什么

### 4.1 三个顶层方向角色（Directors，总监层）

#### Creative Director（创意总监）：守住“这是什么游戏”

负责核心幻想、游戏支柱、情绪、风格和创意冲突。

他关心的不是“冲刺速度填 12 还是 14”，而是“冲刺是否让玩家感到敏捷、是否破坏强调谨慎战斗的核心支柱”。

典型问题：

- 这个功能是否强化游戏独特性？
- 当战斗、美术和叙事目标冲突时，哪个更符合核心体验？
- 如果必须砍功能，什么必须保护？

#### Technical Director（技术总监）：守住“这个游戏能否健康地做出来”

负责技术方向、总体架构、引擎风险、性能预算和跨系统技术冲突。

典型问题：

- 系统边界是否清楚？
- 某种技术方案能否支持目标平台和内容规模？
- 哪些 API 或引擎版本风险必须先验证？
- 当前方案会不会在半年后无法维护？

#### Producer（制作人/项目制作负责人）：守住“团队能否按范围交付”

负责时间、人员、依赖、优先级、风险和沟通。Producer 通常不决定伤害公式，也不决定代码架构，而是让这些决定在正确时间由正确的人完成。

典型问题：

- 本 Sprint 的工作量现实吗？
- 哪个任务阻塞了另外三个部门？
- 里程碑快延期时，应缩范围还是改日期？
- 一项设计变更会增加多少下游工作？

三个角色分别守住：创意正确、技术可行、生产现实。这里的 `Producer`
来自 `produce`（生产、产出），强调“促成产品被生产出来”，并不等同于
只负责投资或署名的影视制片人。

### 4.2 部门负责人

| 角色 | 用通俗语言解释 |
|---|---|
| Game Designer（游戏设计师/游戏策划） | 把“好玩的想法”变成明确、可测试的游戏规则 |
| Lead Programmer（主程序/程序负责人） | 把技术方向变成模块、接口、代码规范和工作分配 |
| Art Director（美术总监） | 规定形状、颜色、材质、构图和视觉一致性 |
| Audio Director（音频总监） | 规定音乐、环境、反馈声音的整体风格和层次 |
| Narrative Director（叙事总监） | 保证人物、世界、剧情和语气一致 |
| QA Lead（质量保证负责人） | 决定测试策略、风险重点和发布质量门槛 |
| Release Manager（发布经理） | 组织候选版本、平台提交、发布检查和补丁流程 |
| Localization Lead（本地化负责人） | 确保文本能被提取、翻译、显示和文化适配 |

Lead 的核心工作是“把模糊目标变成该部门可以执行和验收的方案”。

### 4.3 常见专业角色

#### 程序类

- Gameplay Programmer（玩法程序员）：玩家、战斗、交互、能力等玩法代码；
- Engine Programmer（引擎程序员）：底层框架、资源、内存、渲染和平台集成；
- AI Programmer（人工智能程序员）：敌人感知、决策、寻路和调试工具；
- Network Programmer（网络程序员）：同步、预测、服务器权威和网络安全；
- UI Programmer（用户界面程序员）：菜单、HUD、输入导航和界面事件；
- Tools Programmer（工具程序员）：编辑器、导入、构建和内容生产工具；
- Performance Analyst（性能分析师）：测量 CPU、GPU、内存和加载瓶颈；
- Security Engineer（安全工程师）：作弊、存档篡改、网络攻击和数据暴露。

#### 内容类

- Systems Designer（系统设计师/系统策划）：公式、经济、成长和系统之间的数值关系；
- Level Designer（关卡设计师/关卡策划）：空间、路线、遭遇、节奏和教学；
- Economy Designer（经济系统设计师）：货币的产生与消耗、奖励、价格和长期平衡；
- UX Designer（用户体验设计师）：用户流程、信息层次、交互和可用性；
- Technical Artist（技术美术，TA）：连接美术与程序，解决 Shader、特效、性能和资产管线；
- Sound Designer（声音设计师）：具体制作和定义音效事件；
- Writer（编剧/文案）：对白、文本和叙事内容；
- World Builder（世界观设计师）：世界规则、历史、文化和地点；
- Prototyper（原型开发者）：用最低成本验证高风险想法。

#### 质量和运营类

- QA Tester（质量保证测试员）：设计测试、执行测试、记录证据和缺陷；
- Accessibility Specialist（无障碍/可访问性专家）：检查视觉、听觉、运动和认知可访问性；
- Analytics Engineer（数据分析工程师）：定义事件和指标，分析真实玩家行为；
- Live-Ops Designer（在线运营设计师）：设计赛季、活动、奖励和持续内容；
- Community Manager（社区经理）：玩家沟通、公告、反馈和社区风险；
- DevOps Engineer（开发运维工程师）：构建、持续集成、部署和环境可靠性。

#### 引擎专家

Godot、Unity、Unreal 有各自的文件格式、生命周期、API 和最佳实践。引擎专家负责确认“通用程序方案”在具体引擎版本中是否成立。子专家进一步处理 Shader、UI、网络、GAS、DOTS、GDExtension 等特殊领域。

## 5. 最容易混淆的设计术语

### 5.1 Core Fantasy（核心幻想/玩家幻想）

不是剧情设定，而是玩家想象自己“正在成为谁、做什么”。

例如：

- “成为以一敌百的武术高手”；
- “经营一间温暖的小店”；
- “在未知星球上靠知识生存”。

功能应该帮助玩家更强烈地感受到这种幻想。

### 5.2 Game Pillars（游戏支柱）

3–5 条不可轻易破坏的设计原则，用于在选项冲突时做取舍。

好的支柱：

> 战斗奖励观察和时机，而不是连续按键。

差的支柱：

> 游戏应该很好玩。

前者可以指导实际决定，后者无法排除任何方案。

### 5.3 Core Loop（核心循环）

玩家反复执行、构成主要体验的动作闭环。

```text
探索 → 发现敌人 → 战斗 → 获得资源 → 强化角色 → 探索更危险区域
```

循环说明玩家为什么会继续玩。菜单、剧情和美术可以强化循环，但不能替代循环本身。

### 5.4 Mechanic、Dynamic、Aesthetic（机制、动态、审美体验）

这是 MDA 的三个层次：

- Mechanic：设计者写下的规则，例如“冲刺有 2 秒冷却”；
- Dynamic：规则运行后产生的玩家行为，例如“玩家故意保留冲刺应对 Boss 重击”；
- Aesthetic：玩家感受到的体验，例如紧张、掌控感和成功躲避后的满足。

设计者直接控制 Mechanic，却真正想得到 Aesthetic。中间的 Dynamic 往往需要原型和试玩才能发现。

### 5.5 Tuning Knob（调节旋钮/调参项）

可以不改代码就调整体验的参数，如速度、冷却、掉率、敌人数量。把它们外置为数据，设计者才能快速试验。

### 5.6 Edge Case（边界情况）

正常流程以外但必须定义的情况。例如冲刺时角色被击晕、暂停、断线、进入传送门或同时触墙。未写明的边界情况最终会由程序员猜测，容易造成设计不一致。

### 5.7 Scope、MVP 与 Scope Creep（范围、最小可行产品、范围蔓延）

- Scope：承诺要制作的内容边界；
- MVP：最小但完整、可验证价值的版本；
- Scope Creep：没有重新评估时间和资源，就不断增加工作。

MVP 不是“随便做个很差的版本”，而是保留核心价值、删除非必要复杂度。

### 5.8 Prototype 与 Vertical Slice（原型与纵向切片）

| 术语 | 要回答的问题 | 质量要求 |
|---|---|---|
| Prototype | 这个想法有趣或可行吗？ | 快速、可丢弃 |
| Vertical Slice | 团队能否用目标质量做出一个完整小切片？ | 接近生产质量 |

Prototype 验证想法，Vertical Slice 验证完整产品和生产流程。两者都小，但“小”的原因不同。

## 6. 文档和架构术语

### 6.1 GDD（Game Design Document，游戏设计文档）

GDD 描述玩家体验和游戏规则。它应让不同人对“功能应该怎样表现”形成共同理解。

CCGS 要求系统 GDD 包含概览、玩家幻想、详细规则、公式、边界情况、依赖、调节参数和验收标准。GDD 不应该规定具体类名或引擎 API，那属于技术设计。

### 6.2 Architecture（架构）

架构描述大型系统如何分割、谁拥有数据、模块怎样通信、性能和平台限制是什么。

通俗地说，GDD 说“要建什么房子”，架构说“承重结构、水电和房间怎样组织”。

### 6.3 ADR（Architecture Decision Record，架构决策记录）

一份短文档，记录一个重要技术决定：

- 当时的问题和约束；
- 最终选择；
- 考虑过但未选择的方案；
- 选择带来的好处和代价；
- 对其他系统的影响。

ADR 的价值不是证明决定永远正确，而是让未来的人知道“为什么当时这样选”，避免重复争论或无意破坏前提。

### 6.4 TR（Technical Requirement，技术需求）

把设计要求翻译成可追踪、可验证的技术要求，并给它稳定 ID。

例如：

```text
GDD：玩家在任何支持帧率下冲刺距离一致。
TR-MOV-004：冲刺位移必须基于 delta time 或等价的固定物理步实现。
```

### 6.5 Interface 与 Contract（接口与契约）

Interface 是模块对外提供的入口，Contract 是通信双方共同遵守的约定。

例如伤害系统发出事件：

```text
damage_dealt(amount, target, is_critical)
```

如果 UI、音频和成就系统都使用它，参数含义就是跨系统 Contract。随意修改会同时破坏多个消费者。

### 6.6 State Ownership（状态所有权）

每份关键数据必须有一个唯一权威写入者。例如 HealthSystem 拥有生命值，UI 只能显示，敌人攻击系统只能请求扣血。否则多个系统同时改生命值，会造成难以追踪的错误。

### 6.7 Dependency（依赖）

A 必须使用 B 的结果才能工作，就说 A 依赖 B。依赖决定设计、实现和排期顺序。

如果 HUD 依赖 HealthSystem 提供当前生命值，那么先完成漂亮血条但没有稳定数据接口，通常只会产生返工。

### 6.8 Performance Budget（性能预算）

60 FPS 时每帧约有 16.67 毫秒。渲染、物理、AI、动画、脚本和 UI 要共同分享这段时间。性能预算是预先给各系统分配可接受成本，避免所有模块都认为自己可以占满一帧。

### 6.9 Technical Debt（技术债务）

为了更快交付而接受的结构缺陷或未来成本。技术债不一定是错误；关键是知道欠了什么、风险多大、何时偿还。完全不记录的临时方案才最危险。

## 7. 制作管理术语

### 7.1 Backlog、Epic、Story、Task（积压清单、史诗、故事、任务）

可以把它们理解成从大到小的工作拆分：

```text
Backlog：所有候选工作
  └─ Epic：一个较大的业务/系统目标
       └─ Story：一次可以完成并验收的用户价值
            └─ Task：为完成 Story 所需的具体动作
```

例子：

```text
Epic：玩家移动系统
  Story：玩家可以冲刺躲避攻击
    Task：加入输入映射
    Task：实现冲刺状态
    Task：编写距离一致性测试
```

CCGS 强调 Story 应足够小，通常可在 1–3 天内完成，并具有明确验收标准。

### 7.2 Acceptance Criteria（验收标准）

描述“什么事实成立时，这项工作算完成”。

不好的标准：

> 冲刺手感很好。

较好的标准：

> 地面状态按下冲刺键后，角色在 0.2 秒内沿输入方向移动 4 米；冷却期间再次按键不会触发；30、60、120 FPS 下距离误差不超过 2%。

主观体验仍需试玩，但可观察部分应尽量具体。

### 7.3 Definition of Done（完成定义，DoD）

团队对“Done”的共同标准，通常不仅是代码写完，还包括：

- 验收标准全部满足；
- 自动测试通过；
- 必要的视觉或手工证据已记录；
- Code Review 完成；
- 没有未记录的设计/架构偏差；
- 文档、配置和状态已更新。

### 7.4 Sprint 与 Milestone（迭代冲刺与里程碑）

- Sprint：通常 1–2 周的短周期，承诺一组可完成工作；
- Milestone：更大的产品检查点，如 Prototype、Alpha、Beta、Release Candidate。

Sprint 管近期执行，Milestone 管产品阶段目标。

### 7.5 Estimate、Capacity 与 Velocity（估算、产能与速率）

- Estimate：一项工作预计需要多少努力；
- Capacity：本周期团队实际可投入多少时间；
- Velocity：历史上团队每周期真正完成多少工作。

计划不能只看 Estimate，还要看依赖、风险和历史 Velocity。把所有人的理论工时加满通常不是现实计划，因为沟通、评审、修复和意外也需要时间。

### 7.6 Blocker、Risk、Issue（阻塞项、风险、已发生问题）

- Risk：尚未发生，但可能影响目标；
- Issue：已经发生的问题；
- Blocker：使依赖工作无法继续的问题。

“有风险”不等于必须停止；“被阻塞”则意味着继续做依赖步骤只会制造浪费。

## 8. QA 和测试术语

### 8.1 QA（Quality Assurance，质量保证）不只是找 Bug

Quality Assurance 是“质量保证”，包括提前让需求可测试、设计测试策略、识别高风险区域、验证证据和决定版本是否达到发布标准。Testing 是 QA 的一部分。

### 8.2 常见测试类型（Test Types）

| 类型 | 回答的问题 | Dash 示例 |
|---|---|---|
| Unit Test | 一个小逻辑单元是否正确？ | 冷却计时和冲刺距离公式 |
| Integration Test | 多个模块组合后是否正确？ | 输入→角色状态→碰撞→体力 UI |
| Smoke Test | 最关键路径是否基本可用？ | 能启动、进入关卡、移动、暂停、退出 |
| Regression Test | 新修改是否破坏旧功能？ | 加冲刺后普通移动和碰撞仍正常 |
| Performance Test | 是否满足时间、内存和加载预算？ | 100 个敌人时仍达到目标帧率 |
| Soak Test | 长时间运行是否积累问题？ | 连续运行 8 小时是否泄漏内存 |
| Playtest | 真实玩家体验是否符合设计目标？ | 玩家是否理解冲刺、是否觉得公平 |

自动测试擅长验证确定规则，Playtest 擅长发现体验和理解问题，两者不能互相替代。

### 8.3 Test Evidence（测试证据）

“我试过了”不是可复查证据。证据可以是：

- 测试文件和通过输出；
- 截图或录屏；
- 明确的操作步骤与实际结果；
- 性能采样报告；
- Playtest 观察记录。

证据让另一个人能够判断测试做了什么，而不是只相信结论。

### 8.4 Severity 与 Priority（严重程度与处理优先级）

- Severity：Bug 对产品有多严重；
- Priority：团队多快需要处理它。

一个极少发生但会损坏存档的问题 Severity 很高；一个首页错别字 Severity 很低，但在发布宣传截图前 Priority 可能很高。

## 9. 发布和运营术语

### Release Candidate（发布候选版本，RC）

认为可能成为正式发布版的候选构建。除阻塞缺陷外，不再随意加入功能。

### Changelog 与 Patch Notes（变更日志与补丁说明）

- Changelog：面向开发团队，记录技术和内容变化；
- Patch Notes：面向玩家，用可理解语言说明变化和影响。

两者信息来源相近，但读者和表达目的不同。

### Hotfix 与 Day-One Patch（热修复与首日补丁）

- Hotfix：线上严重问题的紧急、小范围修复；
- Day-One Patch：母盘或首发构建确定后，到正式上市之间准备的集中修复包。

紧急不代表可以省略记录、验证和回滚方案。

### Localization（本地化）

不只是翻译文字，还包括文本提取、复数和性别规则、字体、布局扩张、字幕、文化适配、语音和平台术语。

### Accessibility（无障碍/可访问性）

让不同视觉、听觉、运动和认知能力的玩家可以使用产品。它不是发布前加一个色盲滤镜，而应在输入、UI、音频、难度和反馈设计早期进入需求。

### Live Ops（在线运营/持续运营）

游戏发布后的持续运营，包括活动、赛季、经济调整、社区沟通、数据分析和线上事故处理。它要求内容、技术、QA、发布和社区继续协作。

## 10. 协作术语

### 10.1 Delegation（委派）

上层角色明确目标、约束和成功标准，把专业执行交给正确角色。委派不是只说“你去做”，而是传递足够上下文并说明决策权限。

### 10.2 Consultation（咨询/会签）

一个角色需要另一个领域提供意见，但仍由原责任人做本领域决定。例如 Gameplay Programmer 咨询 Technical Artist 关于冲刺残影成本。

### 10.3 Escalation（升级处理）

当当前层级无权或无法解决冲突时，把问题交给共同上级。升级不是失败，而是避免两个专业在没有全局授权时互相覆盖决定。

### 10.4 Review（评审）

由另一个视角检查工件是否满足标准。设计评审看体验和规则，代码评审看正确性和架构，QA 评审看测试覆盖。评审目标是尽早发现返工风险，不是展示权威。

### 10.5 Gate（阶段门/质量门）

在投入下一阶段的大量成本前，确认关键工件和风险已经达到最低要求。

Gate 更像登机前检查：检查通过不能保证旅程永远无事故，但能避免带着已知的燃料、导航或证件问题起飞。

### 10.6 Sign-off（签署认可/放行）

责任角色明确表示某个领域达到可接受状态。它不是“绝对没有问题”，而是“已知风险在当前阶段可以接受，并由对应责任人承担判断”。

### 10.7 Handoff（交接）

一个阶段或角色把可消费的结果交给下一方。好的交接包含文件、上下文、未决问题、风险和下一步，不应只发一句“我做完了”。

## 11. 七阶段流程的通俗解释

| 阶段 | 通俗问题 | 最大风险 |
|---|---|---|
| Concept | 我们到底想做什么，为什么值得做？ | 做了一个没人真正想要的游戏 |
| Systems Design | 规则到底是什么，各系统会不会冲突？ | 每个人按不同理解工作 |
| Technical Setup | 用什么结构和技术实现才不会失控？ | 写到一半发现架构或引擎路线不成立 |
| Pre-Production | 一个完整小样能否证明体验和生产方式可行？ | 大规模生产后才发现整条流程有问题 |
| Production | 怎样持续、可预测地完成内容？ | 依赖混乱、范围膨胀、质量不断下降 |
| Polish | 已有游戏是否稳定、平衡、清晰且达到性能目标？ | 功能齐全但体验粗糙或无法稳定运行 |
| Release | 构建、平台、商店、支持和紧急方案是否就绪？ | 做完游戏却无法安全交付玩家 |

阶段不是绝对瀑布。试玩可能迫使设计回退，技术验证可能促使缩减范围。阶段的价值是让团队知道“当前主要目标和最低退出条件是什么”。

## 12. 用 Dash 功能串起完整流程

下面把前面的术语连成一条真实链路。

### 第一步：创意和设计

Creative Director 检查冲刺是否符合“战斗奖励观察和时机”的支柱。Game Designer 定义用途、体力、冷却、无敌规则和边界情况。Systems Designer 提出数值范围和调节参数。

产物：更新冲刺 GDD 和设计注册表。

### 第二步：技术设计

Technical Director 决定冲刺状态属于移动系统；Lead Programmer 定义状态机和接口；引擎专家确认当前引擎的移动/碰撞 API；必要时写 ADR。

产物：TR、ADR、Control Manifest 更新。

### 第三步：生产拆分

Producer 检查依赖和容量，把工作放入 Movement Epic。Lead Programmer 拆出实现 Story，QA Lead 检查验收标准能否测试。

产物：Story、估算、Sprint 计划。

### 第四步：并行制作

Gameplay Programmer 实现移动状态和测试；Technical Artist 制作残影方案；Sound Designer 定义音效；UI Programmer 显示体力和冷却。只有共享接口稳定后，互不依赖的工作才适合并行。

产物：代码、配置、视觉/音频资产、测试。

### 第五步：集成和验证

Lead Programmer 做代码评审；QA Tester 运行 Unit、Integration、Regression 和性能测试；Level Designer 检查旧关卡是否可被冲刺越界；Playtest 验证玩家是否理解且觉得公平。

产物：Review 结论、测试证据、Bug 和 Playtest 报告。

### 第六步：完成和传播

若实际实现必须偏离 GDD，不能悄悄保留偏差。责任人要决定修改实现还是正式修改设计，并把变化传播到 TR、ADR、Story、教程、关卡和测试。

产物：一致的最终工件和 Done 状态。

这就是 CCGS 里大量角色与文档的原因：它们分别负责一条真实风险，而不是为了让流程显得复杂。

## 13. 初学者不需要一次使用所有角色

对于第一个小项目，可以只保留一条最小路径：

```text
你（最终决策）
  → Game Designer：把玩法说清楚
  → Lead Programmer：把实现边界说清楚
  → Gameplay Programmer + 引擎专家：实现
  → QA Tester：验证
  → Producer 思维：控制范围和下一步
```

遇到以下情况再增加角色：

- 视觉方向混乱 → Art Director / Technical Artist；
- UI 难用 → UX Designer / UI Programmer；
- 性能下降 → Performance Analyst；
- 多人同步 → Network Programmer / Security Engineer；
- 叙事量增大 → Narrative Director / Writer；
- 准备发布 → QA Lead / Release Manager / DevOps Engineer；
- 跨领域功能 → 对应 `team-*` Skill。

组织结构是工具箱，不是每个任务都必须召集全员开会。

## 14. 看见术语时先问什么

遇到陌生术语，不要先背定义，先问：

1. 它在降低哪种风险？
2. 谁负责创建或决定它？
3. 谁会消费它？
4. 它在什么阶段最有用？
5. 它怎样证明自己已经完成？

例如 ADR：降低技术决定遗失和反复争论的风险；由技术负责人创建；程序员、QA 和未来维护者消费；架构期最重要；通过明确状态、理由、后果和引用来完成。

## 15. 中英术语与命名语义速查

下面的“命名语义”不是逐字硬译，而是解释英语使用者看到这个名称时会
自然联想到什么。理解这种联想，可以帮助你在遇到新术语时自行推断用途。

### 15.1 组织与角色

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| Studio | 工作室/开发工作室 | 原指艺术家工作的房间，游戏行业中指共同创作产品的组织 |
| Discipline | 专业领域/工种 | 原意是经过训练形成的学科，强调程序、美术、设计等不同专业体系 |
| Department | 部门 | 按专业责任划分的组织单元，如程序部、美术部 |
| Director | 总监 | 来自 direct“指明方向”，负责方向、原则和高层取舍 |
| Lead | 负责人/主责 | 来自 lead“带领”，负责带领某个专业领域执行方向 |
| Specialist | 专家/专项人员 | 来自 specialize“专门化”，强调窄领域的深度能力 |
| Creative Director | 创意总监 | Creative 指创意与作品身份，负责“作品最终是什么” |
| Technical Director | 技术总监 | Technical 指实现技术，负责“怎样可靠地做出来” |
| Producer | 制作人/项目制作负责人 | 来自 produce“生产、产出”，负责让团队在约束内形成交付物 |
| Game Designer | 游戏设计师/游戏策划 | Design 是有目的地设计规则，不只是提出点子 |
| Systems Designer | 系统设计师/系统策划 | Systems 强调多个规则、数值和反馈回路组成的整体 |
| Level Designer | 关卡设计师/关卡策划 | Level 是玩家实际游玩的空间、遭遇和节奏单元 |
| Lead Programmer | 主程序/程序负责人 | Programmer 的 Lead，负责代码层方案、规范和分工 |
| Technical Artist | 技术美术（TA） | 名称把 Technical 与 Artist 并列，表示连接程序和美术的桥梁角色 |
| UX Designer | 用户体验设计师 | UX 是 User Experience，关注用户完整体验而不只界面外观 |
| QA Lead | 质量保证负责人 | QA 是 Quality Assurance，范围比“测试负责人”更广 |
| Release Manager | 发布经理 | 管理 Release 从候选构建到玩家可获得版本的过程 |
| DevOps Engineer | 开发运维工程师 | Development + Operations 的合成词，强调开发和运行交付不再割裂 |
| Live-Ops Designer | 在线运营设计师 | Live 表示产品已在线“活着”，Operations 表示持续运行与内容运营 |

### 15.2 游戏设计

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| Core Fantasy | 核心幻想/玩家幻想 | Fantasy 是玩家想象自己成为谁、能做什么；Core 表示它是体验中心 |
| Game Pillar | 游戏支柱 | 借用建筑支柱隐喻：移除后作品身份会“站不住” |
| Core Loop | 核心循环 | Loop 表示玩家会反复执行并获得反馈的动作闭环 |
| Mechanic | 机制/玩法规则 | 像机器内部机构一样，指设计者直接定义的规则和操作 |
| Dynamic | 动态/运行时行为 | 规则互相作用后在游玩过程中“动起来”产生的行为模式 |
| Aesthetic | 审美体验/感受 | MDA 中不是只指画面美术，而是玩家获得的情绪和体验品质 |
| MDA | 机制—动态—审美体验框架 | Mechanics、Dynamics、Aesthetics 三层首字母缩写 |
| Player Agency | 玩家能动性/自主作用 | Agency 指行动并造成结果的能力，强调选择是否真正影响游戏 |
| Feedback Loop | 反馈循环 | 行动产生结果，结果又影响下一次行动，形成循环 |
| Tuning Knob | 调节旋钮/调参项 | 借用设备旋钮隐喻：不改结构，只“拧动”参数就改变体验 |
| Edge Case | 边界情况 | 位于正常输入范围的边缘，虽少见但容易暴露规则漏洞 |
| Scope | 范围 | 原意是可观察或覆盖的边界，表示项目承诺包含什么、不包含什么 |
| MVP | 最小可行产品 | Minimum Viable Product，最小但仍能传递核心价值并接受验证的版本 |
| Scope Creep | 范围蔓延 | Creep 有悄悄爬行之意，强调工作范围在未正式决策时一点点扩大 |
| Prototype | 原型 | 来自“最初形态”，用于学习和验证，不代表最终生产实现 |
| Vertical Slice | 纵向切片 | 像纵向切蛋糕，一小块却穿过玩法、UI、美术、音频、技术等全部层次 |
| Horizontal Slice | 横向切片 | 只广泛覆盖某一层，如做完全部灰盒关卡，但未形成完整端到端体验 |
| Game Feel | 游戏手感 | 玩家输入、运动、反馈和节奏共同形成的即时感受，不等于单一数值 |

### 15.3 文档与技术架构

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| GDD | 游戏设计文档 | Game Design Document 的首字母，记录体验目标和游戏规则 |
| Architecture | 架构 | 借用建筑学，强调承重关系、边界和整体组织，而非某一段代码 |
| ADR | 架构决策记录 | Architecture Decision Record，Record 强调保留当时决定和理由 |
| TR | 技术需求 | Technical Requirement，把设计要求翻译为技术上可验证的要求 |
| Requirement | 需求/要求 | 系统必须满足的条件，不只是“希望有”的想法 |
| Interface | 接口 | 两个模块相接触的表面，隐藏内部细节并暴露有限能力 |
| Contract | 契约/约定 | 借用法律契约，表示生产者和消费者都必须遵守的稳定约定 |
| API | 应用程序编程接口 | Application Programming Interface，供程序通过明确入口使用能力 |
| Module | 模块 | 可相对独立理解、测试和替换的功能单元 |
| State | 状态 | 系统在某一时刻保存、并会影响后续行为的数据 |
| State Ownership | 状态所有权 | 指定谁是状态的唯一权威写入者，避免多人同时修改 |
| Dependency | 依赖 | A 必须先获得 B 的能力或结果才能工作，表示实现和排期顺序关系 |
| Data-Driven | 数据驱动 | 行为由外部数据控制，而不是把数值和规则写死在代码里 |
| Runtime | 运行时 | 程序实际运行的时期，与编辑、编译或构建时期相对 |
| Game Engine | 游戏引擎 | Engine 借用“发动机”隐喻，提供驱动游戏运行的通用核心能力 |
| Framework | 框架 | 像建筑骨架，规定组织方式并留出填充具体业务的空间 |
| Pipeline | 流水线/管线 | 输入经过连续处理阶段形成输出，如资产导入、构建和发布 |
| Performance Budget | 性能预算 | 像金钱预算一样，把有限帧时间、内存分配给不同系统 |
| Technical Debt | 技术债务 | 当前省下的工程成本会像债务一样在未来支付维护“利息” |
| Control Manifest | 控制清单/控制规则清单 | Manifest 是正式清单，把分散 ADR 汇总成可直接遵守的规则 |
| Traceability | 可追踪性 | 能从需求一路追到决定、实现和证据，也能反向找到来源 |

### 15.4 制作与项目管理

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| Backlog | 待办积压/积压清单 | 原指堆积在后面的工作，表示尚未承诺进当前周期的候选项 |
| Epic | 史诗/大型工作项 | 借用长篇史诗，表示大到必须拆成多个 Story 的目标 |
| Story | 用户故事/工作故事 | 用用户视角讲一个小段价值：“谁需要什么，为什么” |
| Task | 任务 | 为完成 Story 执行的具体技术或制作动作 |
| Sprint | 迭代冲刺/短周期 | 原意是短跑，强调短时间、明确终点和集中交付，不是长期马拉松 |
| Milestone | 里程碑 | 原指道路标记距离的石碑，表示产品旅程中的重要检查点 |
| Roadmap | 路线图 | 像地图一样显示较长期方向和阶段，不等于每项工作的精确承诺 |
| Acceptance Criteria | 验收标准 | Criteria 是一组判断条件，满足后需求方才接受该工作 |
| Definition of Done | 完成定义（DoD） | 团队共同定义什么才叫 Done，防止每个人的“做完”标准不同 |
| Estimate | 估算 | 基于当前信息预测努力或时间，不是绝对承诺 |
| Capacity | 产能/可投入量 | 团队在一个周期实际能投入的有限能力 |
| Velocity | 速率/历史交付速度 | 借用速度概念，表示团队过去每周期真正完成多少工作 |
| Priority | 优先级 | 决定先后顺序，综合价值、时间、风险和依赖 |
| Risk | 风险 | 尚未发生但具有概率和影响的未来事件 |
| Issue | 已发生问题/事项 | 已经存在并需要处理的实际问题，不再只是可能性 |
| Blocker | 阻塞项 | 阻止依赖工作继续，名称直接来自 block“挡住” |
| Critical Path | 关键路径 | 决定最早完成日期的最长依赖链，其中任何延迟都会推迟整体 |
| Stakeholder | 利益相关方 | 会影响项目或受到项目影响的人，如玩家、发行商、平台和团队 |
| Deliverable | 交付物 | 能被下一角色、阶段或客户接收和使用的明确产物 |
| Feature Complete | 功能完成 | 计划功能均已实现，但可能仍有 Bug、性能和打磨工作 |
| Content Complete | 内容完成 | 计划关卡、文本、资产等内容已齐全，之后主要修复和打磨 |

### 15.5 QA 与测试

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| QA | 质量保证 | Quality Assurance，Assurance 强调建立对质量过程的信心，不只是执行测试 |
| QC | 质量控制 | Quality Control，偏向检查成品是否达标；QA 更强调全过程预防 |
| Bug / Defect | 缺陷/错误 | Bug 是行业俗称，Defect 更正式，表示实际行为偏离预期 |
| Test Case | 测试用例 | 一个明确的前置条件、操作、输入和预期结果组合 |
| Unit Test | 单元测试 | Unit 指最小可独立验证的逻辑单元 |
| Integration Test | 集成测试 | Integration 指把多个模块连接后验证接口和协同行为 |
| End-to-End Test | 端到端测试 | 从用户入口一直走到最终结果，覆盖完整链路两端 |
| Smoke Test | 冒烟测试 | 来自硬件通电后先看是否冒烟；表示快速检查最基本功能是否可用 |
| Regression Test | 回归测试 | Regression 指退回到坏状态，验证修改没有让旧功能倒退 |
| Performance Test | 性能测试 | 测量时间、帧率、内存、吞吐和加载等非功能指标 |
| Soak Test | 浸泡/长稳测试 | Soak 原意长时间浸泡，表示持续运行以暴露累积性问题 |
| Playtest | 试玩测试 | 让人实际游玩，观察理解、感受和行为，而非只核对代码结果 |
| Test Evidence | 测试证据 | 可复查的输出、截图、录像或记录，用来支持“已经通过”的结论 |
| Coverage | 覆盖率/覆盖范围 | 表示多少需求、代码路径或风险已被测试触达 |
| Severity | 严重程度 | 缺陷对产品和玩家造成多大影响 |
| Priority | 处理优先级 | 团队应该多快处理，可能受发布时间和业务情况影响 |
| Repro / Reproduction | 复现/复现步骤 | 能稳定让问题再次出现，是定位和验证修复的基础 |
| Triage | 缺陷分诊/分类处置 | 来自医疗分诊，按严重度、优先级和归属快速决定处理方式 |

### 15.6 发布与运营

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| Build | 构建/构建版本 | 把代码、数据和资产“建造”为可运行产品，也指其输出版本 |
| Release | 发布/发行版本 | 从内部开发状态放行给玩家或平台的过程及结果 |
| Release Candidate | 发布候选版本（RC） | Candidate 表示“候选者”，若验证通过即可成为正式版本 |
| Alpha | Alpha 阶段/早期可玩版 | 借用希腊字母顺序，通常表示核心系统可用但内容和质量未完成 |
| Beta | Beta 阶段/测试版 | 通常比 Alpha 完整，重点转向缺陷、兼容性、平衡和真实用户反馈 |
| Gold Master | 金盘/最终母版 | 来自实体光盘时代的生产母盘，表示提交制造或平台的最终基线 |
| Changelog | 变更日志 | Change + log，按版本记录发生了哪些内部变化 |
| Patch Notes | 补丁说明 | 面向玩家解释一个 Patch 修了什么、改了什么 |
| Patch | 补丁 | 像给衣物打补丁一样，对现有版本做局部更新 |
| Hotfix | 热修复/紧急修复 | Hot 表示问题正在“发热”，需要快速、小范围处理 |
| Day-One Patch | 首日补丁 | 产品正式上市第一天即可获得的更新包 |
| Rollback | 回滚 | 把发布状态“滚回”到上一个已知稳定版本 |
| Localization | 本地化 | 不只翻译，而是使产品适应目标地区语言、格式和文化 |
| Internationalization | 国际化（i18n） | 预先改造产品以支持多地区；i18n 中 18 代表 i 与 n 之间 18 个字母 |
| Accessibility | 无障碍/可访问性 | 让不同能力的人能够访问、理解和操作产品 |
| Live Ops | 在线运营/持续运营 | 游戏上线后保持服务“活着”的活动、内容、数据和事故响应 |
| Telemetry | 遥测数据 | 远程采集运行和玩家行为信号，用于观察真实产品状态 |
| Analytics | 数据分析 | 把事件数据转成趋势、指标和决策信息 |

### 15.7 协作与评审

| 英文 | 常用中文 | 命名语义：为什么这样叫 |
|---|---|---|
| Delegation | 委派 | 把任务及相应权限交给合适责任人，不是只把工作甩出去 |
| Consultation | 咨询/会签 | 向另一专业寻求意见，原责任人通常仍保留最终领域决定 |
| Escalation | 升级处理 | 把超出当前权限或无法解决的冲突向更高决策层移动 |
| Collaboration | 协作 | 多方共同塑造结果，区别于各自独立完成后简单拼接 |
| Coordination | 协调 | 对齐时间、接口、依赖和顺序，使多方工作不互相阻塞 |
| Review | 评审 | 再次查看并按标准给出问题、建议或结论 |
| Gate | 阶段门/质量门 | 像一道门，在投入下一阶段成本前检查是否满足通行条件 |
| Verdict | 结论/裁定 | 结构化评审的明确结果，如 PASS、CONCERNS、FAIL |
| Sign-off | 签署认可/放行 | 责任人明确接受当前状态和已知风险，允许进入下一步 |
| Handoff | 交接 | 把工件、上下文、风险和未决问题完整交给下一责任人 |
| Alignment | 对齐/一致认知 | 确保各方对目标、范围和约束理解一致 |
| Sync | 同步/同步会议 | 交换最新状态，使信息重新一致；不等于代替深度评审 |
| Ownership | 所有权/主责 | 谁对结果、决定和后续维护负最终责任 |
| Advisory | 建议性 | 提供专业意见但不自动拥有最终决定权 |
| Approval | 批准 | 明确同意某项方案或写入行为，通常比一般建议权限更高 |
