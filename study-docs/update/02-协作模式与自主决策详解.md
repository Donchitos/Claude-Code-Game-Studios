# 协作模式与自主决策：AI 是怎么"决定"并记录的

> 给初学者的指南。读完你能回答四个问题：
>
> 1. AI 什么时候问你、什么时候自己干？
> 2. 自主决策记录到哪里、长什么样、谁写的？
> 3. 为什么这样设计，和协作哲学冲突吗？
> 4. 你（用户）应该怎么读这些记录、怎么接管？

---

## 一句话概览

CCGS 的每个技能在**每次**调用 `AskUserQuestion` 之前，都会查一下当前的 **automation 模式**：

- **协作模式（collaborative）**：默认值。每次都问，每步都要你点头。
- **引导模式（guided）**：只在**重大决策**上问，**次要决策** AI 给推荐然后继续。
- **自主模式（autonomous）**：**不问了**。但它会把本来该问你的每个决定**写进日志**，你事后审计。

**三种模式共用同一份规则**，而且永远有一张**安全网**：`automation_always_ask` 类别里的事，哪怕在自主模式下也会停下来问你。

---

## 你已经见过的场景，三种模式下会怎样

假设你在设计一个 RPG 的战斗系统，AI 要决定"伤害公式用线性还是指数"：

| 模式 | AI 怎么做 | 你会看到什么 |
|------|----------|-------------|
| **协作** | 弹出 AskUserQuestion，两个选项，各有 pros/cons | "线性更易平衡，指数更有成长感。你选哪个？" |
| **引导** | 分类 = **minor**（公式是次要点）→ 直接给推荐然后继续 | "用线性公式，因为我们的数值规模不大。继续。" |
| **自主** | 分类 = minor → 推荐线性 → **不弹窗**但记日志 | 什么都没弹窗，但文件里会多出一行 decision-log |

再假设 AI 要**删掉一个故事文件**：

| 模式 | AI 怎么做 |
|------|----------|
| 协作 | 问你 |
| 引导 | 分类 = **major**（删文件）→ 还是问你 |
| **自主** | 检查 always_ask → `file_deletions` 在默认列表里 → **还是问你** |

这就是安全网在起作用。

## 底层怎么做到的：一张图讲清楚

每个技能的"每次 AskUserQuestion 调用"都遵循同样的 4 步判断链：

```
决策点出现
    │
    ▼
① 分类：这次决策是 major 还是 minor？
    │  （技能作者在 SKILL.md 里预先给每个决策点贴好了标签）
    ▼
② 查配置：当前 automation 模式是什么？always_ask 里有没有这个决策类别？
    │  （调用 resolve_config --keys automation, automation_always_ask）
    ▼
③ 套规则表：见下方 Universal Rules
    │
    ▼
④ 执行：问 / 给推荐继续 / 直接选 + 记日志
```

**规则表**（技能每次都按这个表走，所以行为是一致的）：

| 当前模式 | 决策类型 | 行为 |
|----------|----------|------|
| collaborative | *（全部）* | **AskUserQuestion 总问** |
| guided | major | **AskUserQuestion 问**（选项限制到 2 个 + 推荐） |
| guided | minor | **给推荐然后继续**（不弹窗） |
| autonomous | always_ask 类别 | **AskUserQuestion 问**（安全网） |
| autonomous | 其他 | **直接选推荐 + log_decision 记日志** |

**技能里怎么写**？以 [dev-story/SKILL.md](file:///workspace/.claude/skills/dev-story/SKILL.md) 为例，启动就一行：

```bash
bash resolve_config --keys automation,workflow,qa.level,...
```

然后文件里引用 [automation-modes.md](file:///workspace/.claude/docs/automation-modes.md) 作为共享规则——**技能自己不写判断分支**，它只"声明决策点是 major 还是 minor"，模式的分支逻辑全在共享文档里。这保证了 68 个技能**不会各自演化出一套规则**。

## Major 与 Minor 怎么分

不是技能作者随便拍的，有一张标准分类表（来自 [automation-modes.md](file:///workspace/.claude/docs/automation-modes.md) §Major vs Minor）：

**Major — guided 模式下也要问**

| 决策类型 | 例子 |
|---------|------|
| 互斥的设计方向 | "实时还是回合制？" |
| 选系统名或文档路径 | "这个系统叫 combat-system 还是 battle-engine？" |
| 影响下游工作的门控决策 | 引擎选型、架构方案 |
| 范围变化 | "砍功能还是延期？" |
| 改了要大返工的决策 | 核心循环玩法 |

**Minor — guided 模式下 AI 直接推荐**

| 决策类型 | 例子 |
|---------|------|
| 下一步先写哪一节 | "先写 Edge Cases" |
| 加一个可选小节 | "加个 Visual Notes 段，合适" |
| 格式与结构 | 标题层级、表格 vs 段落 |
| 已确定方向里的细节 | "用曲线 A 因为..." |
| 阶段完成后的路由 | "跑完 design-review 了，接着跑 architecture-review" |

**一句话直觉**：如果这个决策**半年后你可能会回头说"当初不该那么定"**，它就是 major。

## `automation_always_ask`：安全网的故事

这是整个机制里**最关键的一行配置**，它让"自主模式"不会变成"AI 想干嘛干嘛"。

### 它是什么

即使在 `autonomous` 模式下，**某些类别的决策也永远会停下来问你**。这个类别清单就叫 `automation_always_ask`。

### 默认清单（没配时）

```yaml
modes:
  automation_always_ask:
    - scope_changes    # 砍功能、延期、合并 epic、删验收标准
    - file_deletions   # 删故事、删 GDD、删系统、删测试文件
    - schema_changes   # 改 project.yaml 结构、改模板
```

### 可选的更多类别

你可以通过 `/settings` 加上这些：

| 类别 | 哪些决定会触发它 |
|------|----------------|
| `architecture_decisions` | 新建或替换 ADR、改系统边界 |
| `version_bumps` | 升级引擎版本、框架版本、依赖大版本 |
| `external_calls` | 自主模式下调用外部 API（资源生成、AI 服务） |

### 实际判断方式

技能里不硬编码类别检查，而是调用共享函数：

```bash
bash .claude/hooks/yaml-helper.sh is_always_ask_category file_deletions
# 返回 0 = 这个类别在清单里 → 必须问
# 返回 1 = 不在 → 可以自主决定
```

### 一个真实的边界案例

**往 registry 里追加一条实体**（比如在 `design/registry/entities.yaml` 里加一行）算什么？

- ❌ **不是** `schema_changes`——你没改 registry 的结构，只是**加数据**
- ✅ 应该算 `minor`

`schema_changes` 只意味着"改了模板或结构本身"（比如改了 story 模板的字段）。

## 自主模式的决策日志：记录到哪里、长什么样、谁写的

### 写到哪里

```
production/session-logs/decision-log.md
```

这个文件的位置、名字、格式都由 [yaml-helper.sh](file:///workspace/.claude/hooks/yaml-helper.sh) 里的 `log_decision` 函数**硬编码**，所以永远不会变。

### 谁写的

**技能**在每一个本该弹窗 `AskUserQuestion` 的决策点上，如果模式判定为"自己决定"，就调用 `log_decision`。调用者是**AI**（Claude Code 执行技能时），格式是**脚本规定**的 Markdown，所以不会产生不一致。

### 怎么写的

调用就是这一行：

```bash
bash .claude/hooks/yaml-helper.sh log_decision \
  "<skill-name>" \
  "<决策点是什么>" \
  "<本来会给哪些选项>" \
  "<实际选了哪个>" \
  "<一句话理由>" \
  "<类别：minor / scope_changes / ...>"
```

函数内部用 ISO 8601 UTC 时间戳、创建文件和父目录（如果不存在）、**append-only 追加写入**（永远不截断）。

### 日志条目长什么样

```markdown
# Decision Log

Append-only audit trail of decisions made in autonomous mode.

## 2026-10-19T08:32:11Z — design-system

**Decision point:** 战斗系统伤害公式选型
**Options considered:** [线性公式, 指数公式, 分段公式]
**Chosen:** 线性公式
**Reason:** 我们的伤害区间是 1-100，指数在这个范围里和线性几乎没差，但调参更难。
**Category:** minor

## 2026-10-19T08:34:05Z — design-system

**Decision point:** 加不加 Edge Cases 小节
**Options considered:** [加, 不加]
**Chosen:** 加
**Reason:** standard 工作流下这一节是必需的。
**Category:** minor
```

### 记录粒度：什么记，什么不记

**应该记的**：所有**本该弹窗 AskUserQuestion** 的决策点——包括选哪个方案、选哪个公式、选哪个边界条件。连"选 framing（选项怎么组织）"也要记，因为 framing 本身就是一个决策。

**不该记的**：AI 在写文档过程中自己脑子里跑的"内部 Q&A"（比如"这里要不要提一下平衡迭代？先不用，后面再提"）。这些是草稿思维，不是用户决策点。

**简化**：一个多 tab 的问题 widget 合并成 **一条**，每个 tab 的选择都列在 "Chosen" 下，不要拆成多条。

**"May I write?" 不单独记**：自主模式下 AI 直接写文件，不会为了每次写文件单独打一条。写入合并到它实现的那个决策的日志里。

## 为什么这样设计：三条设计哲学

### 哲学一：自主模式是"加速+审计"，不是"甩锅"

协作模式是 100% 控制、最慢；自主模式是 0% 弹窗、最快。但**没有日志的自主模式是不可审计的**——你怎么知道 AI 没有偷偷做了什么？日志就是让它可以审计的那个东西。

> 你可以把自主模式类比成"你的实习生独立工作一天，下班交一份详细日报"。日报不能让它变好，但让你能**发现哪里走偏了**。

### 哲学二：同一个问题必须得到同一个答案

如果每个技能自己写"if autonomous then don't ask"，很快会出现：
- A 技能判断"公式选型是 major"
- B 技能判断"公式选型是 minor"
- C 技能干脆**忘了**写这个判断，在自主模式下仍然弹窗

共享的 [automation-modes.md](file:///workspace/.claude/docs/automation-modes.md) 就是为了解决这个问题。它是**唯一的规则源**，技能只引用它，不重写它。

### 哲学三：失败要"安全"（fail safe）

`automation_always_ask` 的默认清单选的是**三个最危险的动作**：
- 改范围（scope_changes）
- 删东西（file_deletions）
- 改结构（schema_changes）

哪怕你把其他事都交给 AI，这三件事**默认还是会停下来问你**。如果你拿不准一个边界案例该不该加进 always_ask，**加进去总比不加安全**。

## 一个被问到最多的问题：既然自主模式会记日志，那我怎么跟进？

三种后续协作方式，按时机分：

### 时机一：**会话中**发现 AI 要做一件事但你想自己来

你可以在 AI 即将执行某步之前**打断**它，说"等一下，这个我来决定"。技能会切换回 collaborative 模式处理当前决策，然后继续。

### 时机二：**会话中**发现 AI 已经做了一件你不同意的事

看 decision-log.md。每条都有 timestamp、skill、决策点、选项、理由。你可以：
- 直接回复这条的 reasoning，要求 AI 修改；
- 或说"revert the decisions on combat system, keep everything else"。

### 时机三：**会话后**审计，下次会话开始前

`/help` 和 session-start hook 会告诉你 decision-log 里有多少条决策。你可以：
- 读完日志再决定要不要继续当前会话；
- 或用 `/settings modes.automation=guided` 切回引导模式；
- 或直接让 AI 把"昨天自动决定的战斗公式"改回去。

**一句话**：日志不是一个静态文件，它是**你和 AI 对话的起点**。

## 永远问（不参与任何模式切换）的 4 个技能

有些技能**天生不能让 AI 自动跑**，不管你把 automation 设成什么。它们永远表现得像 collaborative：

| 技能 | 为什么 |
|------|--------|
| `hotfix` | 紧急修补——用户必须先批准范围和风险 |
| `gate-check` | 门禁结果必须被审阅，没人认的门禁等于没门禁 |
| `day-one-patch` | 发布关键——每个动作都要明确签字 |
| `setup-engine` | 一次性、不可逆的选择，影响整个项目 |

这些技能在 SKILL.md 里**根本不引用 automation-modes.md**。

## "问了但没人回答"怎么办（每种模式都适用）

这是 1.1.3 版本专门修过的边界条件：

> 一个被关闭、被跳过、返回空的问题——**不算答案**。

行为：
- **协作/引导模式**：什么都不写、什么都不改，用纯文本再问一遍，说明"等你回答才能继续"；
- **自主模式 + always_ask 类别**：同上，因为这是安全网里的决策；
- **自主模式 + 非 always_ask**：没人能回答就按常规自己决定 + 记日志；
- **CI / headless 场景**：停下并报告"有决策在等回答"，不替你选。

## 配置速查

全部在 `project.yaml` 或 `project.local.yaml` 里：

```yaml
modes:
  automation: collaborative   # collaborative | guided | autonomous
  automation_always_ask:      # 覆盖默认清单（只配置想加的，保留默认）
    - scope_changes           # 默认就有
    - file_deletions          # 默认就有
    - schema_changes          # 默认就有
    - architecture_decisions  # 我额外想加的
    - version_bumps           # 我额外想加的
```

用 `/settings` 改：

```
/settings modes.automation=guided
/settings modes.automation_always_ask+architecture_decisions
/settings modes.automation_always_ask-scope_changes     # 只在你很确定时减
/settings --local modes.automation=autonomous           # 仅对你本机生效
```

## 动手：一次真刀真枪的自主决策审计

把下面几步跑完，你就理解整个机制了。

### 第 1 步：切到自主模式

```
/settings modes.automation=autonomous
```

### 第 2 步：让 AI 做一个会触发日志的决策

比如跑 `/design-system inventory`（库存系统）。

### 第 3 步：看日志

```bash
cat production/session-logs/decision-log.md
```

你会看到至少两类条目：
- Category: minor（AI 自动决定的）
- Category: file_deletions（如果它删了东西，always_ask 会让你停下来，**不会出现在日志里**，因为它问了你）

### 第 4 步：切回引导模式

```
/settings modes.automation=guided
```

再跑一次 `/design-system inventory`，这次你会看到 major 决策被问、minor 决策只给推荐。

### 第 5 步：验证 always_ask

故意设一个"安全"的 always_ask 清单，然后让 AI 在自主模式下做一件不在清单里的事。你会发现：它直接做了，没问，但记了日志。

### 第 6 步：再试一次，这次让 AI 做一件**在**清单里的事

比如删掉某个测试文件——你会发现 AI 在自主模式下也停下来问你了。这就是安全网。

## 常问的 6 个问题

### Q1：自主模式是不是就是让 AI 完全接管？

不是。它是"**不弹窗，但每件事都留痕**"。你可以随时切换回协作，也可以事后审计。

### Q2：日志是 AI 自己写的，我能信吗？

日志是 shell 脚本 [yaml-helper.sh 的 log_decision](file:///workspace/.claude/hooks/yaml-helper.sh#L1153-L1178) 按固定格式 append 到文件，AI 只是把参数传给脚本。格式不会乱，时间戳不会错，但"Reason"字段是 AI 自己写的一句话——你要自己判断它是不是在说实话。

### Q3：我能不能在自主模式下改某个已记日志的决定？

可以。直接说"把 combat system 的伤害公式改成分段公式，reason：我们昨晚测了"。AI 会改文件，**但不会删除旧日志条目**——旧决策还在，你能看到"AI 先是这么想的，后来你改了"。

### Q4：always_ask 列表里能加自定义类别吗？

目前只有那 6 种预定义类别，不能加自定义。如果你觉得某个动作需要新增，提一个 issue。

### Q5：同一个决策点被多个技能碰到会重复问吗？

不会。`resolve_config` 是**唯一的**模式解析函数，所有技能调用它得到同一个答案。决策点本身也是由"当前正在执行的那个技能"负责的。

### Q6：如果我把 autonomy 设成 autonomous，AI 会不会偷偷改了 project.yaml？

不会。`project.yaml` 改动属于 `schema_changes`，而它在 always_ask 默认清单里——哪怕 autonomous，也会停下来问。

## 一页总结

```
三种模式，一条共享规则源
  ├─ collaborative（默认）→ 每个决策点都问
  ├─ guided              → major 问 / minor AI 推荐继续
  └─ autonomous          → 不问，但每步写日志

永远有一张安全网
  └─ automation_always_ask：scope_changes / file_deletions / schema_changes
     这三类在任何模式下都问

日志就是你和 AI 的审计协议
  ├─ 位置：production/session-logs/decision-log.md
  ├─ 格式：timestamp + skill + decision point + options + chosen + reason + category
  ├─ 谁写：yaml-helper.sh 的 log_decision 函数（AI 调用，脚本格式化）
  └─ 什么时候记：每一个本该弹窗 AskUserQuestion 的决策点

哲学：自主 = 加速 + 审计，不是甩锅
技能只声明 "这个点是 major 还是 minor"
模式判断统一走共享文档 automation-modes.md
这样 68 个技能永远有一致行为
```
