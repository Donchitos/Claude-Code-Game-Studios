# 21 · 游戏开发完整流程与软件工程实践

## 这篇文档解决什么问题

[第 20 篇](file:///workspace/study-docs/20-claude-docs目录指南.md) 讲了 `.claude/docs/` 里每个文件是什么。这篇回答两个更根本的问题：

1. **游戏项目开发的完整流程是怎样的？**——从"我有个想法"到"游戏发布"，中间经过哪些阶段、每阶段干什么、产出什么、怎么判断能进下一阶段。
2. **这套流程背后用了哪些软件工程实践？每个实践解决什么问题？原理是什么？**——为什么要有 GDD、ADR、门禁、注册表、数据驱动、测试证据……它们不是繁文缛节，每个都解决一个真实的"会出事"的问题。

读完这篇，即使你从没做过游戏开发、没学过软件工程，也能明白"为什么正经做项目要这么折腾"。

## 第一部分：游戏开发的完整流程

### 一句话定位

> **游戏开发流程 = 把"一个模糊的想法"变成"一个玩家能玩的成品"的可控过程。每个阶段都有明确的"产出物"和"过关标准"，不达标不进下一阶段——就像盖楼，地基不打好不能砌墙。**

### 类比：把游戏开发想象成"盖一栋楼"

很多初学者以为做游戏就是"坐下来写代码"。错。就像盖楼不是"买砖开始砌"。盖一栋楼要经过：

| 盖楼阶段 | 游戏开发阶段 | 跳过会怎样 |
|---------|------------|-----------|
| 选址、想盖什么样的楼 | Phase 1 概念 | 盖到一半发现地块不对、风格没人喜欢 |
| 画建筑设计图 | Phase 2 系统设计 | 工人不知道砌几层、水电怎么走 |
| 算结构、选材料、定施工方案 | Phase 3 技术搭建 | 用错材料、承重不够、返工 |
| 打样房、试住、定施工计划 | Phase 4 预制作 | 一次盖整栋才发现户型不好用，全拆重来 |
| 一层层往上盖 | Phase 5 生产 | （这步本来就该一层层盖） |
| 精装修、验房 | Phase 6 打磨 | 毛坯交付，没人想住 |
| 交房、入住、售后 | Phase 7 发布 | 没验收就交房，漏水漏电 |

这个项目把游戏开发拆成 **7 个阶段**，每个阶段有名字、目的、要跑的命令、要产出的文档、要过的门禁。下面逐个讲。

### Phase 1：概念（Concept）

**目的**：把"我有个模糊想法"变成"一份结构化的游戏概念文档"。

**类比**：选址 + 决定盖什么样的楼。你心里有"想盖个住宅"，但要明确：几层？什么风格？卖给谁？预算多少？

**这一步干什么**：

1. **跑 `/brainstorm`**——引导式头脑风暴。AI 用游戏设计理论（MDA 框架、自我决定理论、心流理论、Bartle 玩家类型）问你问题：什么让你兴奋、你玩过什么、有什么约束。产出 3 个概念让你选，定核心循环和支柱。
2. **跑 `/setup-engine`**——配置引擎。问你 2D/3D、平台、团队大小、语言偏好，推荐引擎，钉死版本，检测 AI 的"知识缺口"（详见 [第 15 篇](file:///workspace/study-docs/15-docs目录指南.md) 的引擎参考），填充 [technical-preferences.md](file:///workspace/.claude/docs/technical-preferences.md)。
3. **跑 `/prototype`**（可选但推荐）——花 1-3 天做个一次性原型，验证核心机制好不好玩。**先验证再写设计文档**，避免设计一个不好玩的系统。
4. **跑 `/art-bible`**——写视觉身份规范（9 节）。在系统设计前定下美术方向，避免后期返工。

**产出物**：

- `design/gdd/game-concept.md`（概念文档，含支柱、MDA 分析、范围分层）
- `design/art/art-bible.md`（美术圣经）
- `.claude/docs/technical-preferences.md`（引擎配置填好）
- `prototypes/*/README.md`（原型报告，如做了原型）

**要过的门禁**：

- **CD-PILLARS**（创意总监审支柱）：支柱能不能证伪？互相有没有张力？
- **AD-CONCEPT-VISUAL**（美术总监提视觉方向）：基于支柱给 2-3 个视觉方向
- 可选：TD-FEASIBILITY（技术可行性）、PR-SCOPE（范围现实性）

**为什么这步不能省**：没有概念文档，后面写系统设计时"凭感觉"，各系统方向不一致。没有引擎配置，AI 写代码用错版本 API。没有原型验证，可能花几个月设计一个不好玩的机制。

> 💡 **关键概念——支柱（Pillars）**：3-5 条不可协商的设计原则，所有设计决策都要服从。比如《黑暗之魂》的支柱可能是"每场战斗都是承诺""世界是连贯的角色"。支柱用来在分歧时拍板——这个机制符合支柱吗？不符合就砍。

### Phase 2：系统设计（Systems Design）

**目的**：把概念拆成一个个"系统"，每个系统写一份详细的 GDD（游戏设计文档）。

**类比**：画建筑设计图。概念是"盖住宅"，系统设计是画出"客厅、卧室、厨房、卫生间"各自详图，标清每间多大、什么布局、互相怎么连。

**这一步干什么**：

1. **跑 `/map-systems`**——把概念拆成系统列表，画依赖图（战斗依赖血量、UI 依赖战斗……），分优先级（MVP / 垂直切片 / Alpha / 完整版）。
2. **跑 `/design-system [系统名]`**——**每个系统跑一次**，按依赖顺序写 GDD。AI 用 [game-design-document.md](file:///workspace/.claude/docs/templates/game-design-document.md) 模板，分节和你协作写满 8 节（Overview / Player Fantasy / Detailed Rules / Formulas / Edge Cases / Dependencies / Tuning Knobs / Acceptance Criteria）。
3. **跑 `/design-review`**——每个 GDD 写完审一次。
4. **跑 `/review-all-gdds`**——所有 GDD 写完后，跨文档一致性 + 设计理论 holistic 审查。
5. **跑 `/consistency-check`**（可选）——扫所有 GDD 找矛盾（如两个文档对同一数值写不同值）。

**产出物**：

- `design/gdd/systems-index.md`（系统索引 + 依赖图 + 优先级）
- `design/gdd/[系统名].md`（每个系统一份 GDD，状态 Approved）
- `design/gdd/gdd-cross-review-*.md`（跨 GDD 审查报告）

**要过的门禁**：

- **TD-SYSTEM-BOUNDARY**（技术总监审系统边界）：边界干净吗？有"上帝对象"风险吗？
- **CD-SYSTEMS**（创意总监审系统分解）：MVP 系统集合能交付核心幻想吗？
- **CD-GDD-ALIGN**（每个 GDD 审支柱对齐）：每个机制都服务支柱吗？
- 可选：ND-CONSISTENCY（叙事一致）、AD-VISUAL（视觉一致）

**为什么这步不能省**：没有 GDD 直接写代码，程序员不知道"连击窗口到底 0.4 秒还是 0.5 秒""暴击公式怎么算"，只能猜，猜错就返工。GDD 把"做什么"在写代码前讲清楚。

> 💡 **关键概念——GDD 的 8 节为什么是这 8 节**：每节解决一个问题。Overview 给快速浏览者；Player Fantasy 定情感目标（所有细节服从它）；Detailed Rules 给程序员无歧义实现；Formulas 给数值可追溯；Edge Cases 防遗漏；Dependencies 防集成 bug；Tuning Knobs 让平衡可调；Acceptance Criteria 让"做完了"可验证。少一节就有对应风险。

### Phase 3：技术搭建（Technical Setup）

**目的**：把 GDD 里的"做什么"翻译成"怎么做"——写架构决策（ADR）、定接口、填无障碍需求。

**类比**：算结构、选材料、定施工方案。设计图说"3 层楼"，技术搭建要决定"用钢结构还是混凝土""承重墙多厚""水电走顶还是走地"。

**这一步干什么**：

1. **跑 `/create-architecture`**——写主架构文档，覆盖所有系统。
2. **跑 `/architecture-decision`**——**每个关键技术决策写一份 ADR**（架构决策记录）。用 [architecture-decision-record.md](file:///workspace/.claude/docs/templates/architecture-decision-record.md) 模板，记 Status / Context / Decision / Alternatives / Consequences / Engine Compatibility / GDD Requirements Addressed。至少 3 份 Foundation 层 ADR。
3. **跑 `/architecture-review`**——审所有 ADR：完整性、依赖顺序、引擎兼容、GDD 覆盖。同时填充 [tr-registry.yaml](file:///workspace/docs/architecture/tr-registry.yaml)（技术需求 ID 注册表）和 [architecture.yaml](file:///workspace/docs/registry/architecture.yaml)（架构约束注册表）。
4. **跑 `/create-control-manifest`**——从已接受的 ADR 生成一份"程序员规则清单"（扁平化的 do/don't）。
5. **写无障碍需求文档**——定无障碍等级（Basic/Standard/Comprehensive/Exemplary）和功能矩阵。

**产出物**：

- `docs/architecture/architecture.md`（主架构文档）
- `docs/architecture/adr-*.md`（至少 3 份 ADR，状态 Accepted）
- `docs/architecture/architecture-review-*.md`（架构审查报告）
- `docs/architecture/control-manifest.md`（程序员规则清单）
- `design/accessibility-requirements.md`（无障碍需求）
- `docs/architecture/tr-registry.yaml`、`docs/registry/architecture.yaml`（两个注册表，自动维护）

**要过的门禁**：

- **TD-ARCHITECTURE**（技术总监签架构）：每个技术需求都有决策吗？高风险引擎领域解决了吗？
- **TD-ADR**（每个 ADR 审）：问题陈述清楚吗？备选方案真考虑了吗？后果诚实吗？
- **LP-FEASIBILITY**（主程审实现可行性）：这些决策能实现吗？有缺接口吗？
- **AD-ART-BIBLE**（美术总监签美术圣经）
- 可选：TD-ENGINE-RISK（引擎版本风险）

**为什么这步不能省**：没有 ADR，程序员各写各的，两个系统都以为自己管"玩家血量"→ 数据竞争。没有架构注册表，冲突要等到代码集成时才暴露。没有无障碍需求，后期加无障碍要重做 UI。

> 💡 **关键概念——ADR（架构决策记录）**：每个技术决策一份文档，核心是 4 个问题：**Context**（为什么必须现在决定）、**Decision**（决定了什么）、**Alternatives**（放弃了什么、为什么）、**Consequences**（接受什么代价）。ADR 不是"写完就完"，它有生命周期：Proposed → Accepted → Superseded。引用 Proposed ADR 的故事会被自动封禁——必须 Accepted 才能实现。

### Phase 4：预制作（Pre-Production）

**目的**：在全面开工前，先"试住样房"——做 UX 规范、垂直切片、拆故事、规划冲刺。验证"这套设计真的能做出来也好玩"。

**类比**：盖样房 + 试住 + 定施工计划。一次盖整栋楼才发现户型不好用就晚了。先盖一套样房，住进去体验，定好每层施工顺序。

**这一步干什么**：

1. **跑 `/asset-spec`**（可选）——列视觉实体清单（角色、敌人、UI 屏幕、HUD 元素）。
2. **跑 `/ux-design`**——为关键屏幕（主菜单、核心 HUD、暂停菜单，至少 3 个）写 UX 规范。读 [technical-preferences.md](file:///workspace/.claude/docs/technical-preferences.md) 的输入方式。
3. **跑 `/ux-review`**——审 UX 规范对齐 GDD 和无障碍等级。
4. **跑 `/prototype`**（如 Phase 1 没做）——验证核心机制好玩。
5. **跑 `/create-epics`**——把 GDD + ADR 翻译成 epic（每个架构模块一个 epic）。按层跑：先 foundation 层，再 core 层。
6. **跑 `/create-stories`**——把每个 epic 拆成可实现的故事文件。
7. **跑 `/test-setup`**（可选但推荐）——搭测试框架 + CI 管线。
8. **跑 `/sprint-plan`**——规划第一个冲刺。
9. **跑 `/vertical-slice`**（可选但推荐）——做一个生产质量的端到端切片（3-5 分钟 polished 体验），验证完整游戏循环。**做完必须试玩并记录**才能进下一阶段。

**产出物**：

- `design/ux/*.md`（至少 3 个 UX 规范）
- `production/epics/*/EPIC.md`（epic 定义）
- `production/epics/**/*.md`（故事文件，至少 2 个）
- `production/sprints/sprint-*.md`（第一个冲刺计划）
- `prototypes/*/REPORT.md`（垂直切片报告，如做了）

**要过的门禁**：

- **PR-EPIC**（制作人审 epic 结构）：epic 边界合理吗？依赖顺序对吗？
- **QL-STORY-READY**（QA 主管审每个故事的可测性）：验收标准够具体吗？
- **PR-SPRINT**（制作人审冲刺可行性）：故事量现实吗？
- **4 个 PHASE-GATE**（`/gate-check` 并行召唤 4 总监）：创意/技术/制作/美术四位总监并行评审，取最严判决
- 可选：CD-PLAYTEST（试玩验证）

**为什么这步不能省**：没有垂直切片，可能生产到一半发现"核心循环其实不好玩"或"某系统根本做不出来"，已经投入大量成本。没有可测的故事，`/dev-story` 时发现验收标准太模糊，做完了不知道对不对。

> 💡 **关键概念——垂直切片（Vertical Slice）**：不是"做完一个系统再做下一个"（横向），而是"从 UI 到玩法到存档到音频，端到端跑通一个完整的小切片"（纵向）。它验证的是"整套管线能不能产出可玩的东西"，不是"某个系统完不完整"。

### Phase 5：生产（Production）

**目的**：一个个故事实现，循环冲刺直到功能完整。这是最长的阶段。

**类比**：一层层往上盖楼。每个冲刺盖一层，盖完验收，再盖下一层。

**这一步干什么**（每个冲刺循环）：

1. **跑 `/sprint-plan`**——规划这个冲刺，挑已就绪的故事。
2. **跑 `/story-readiness`**（可选）——挑故事前验证它实现就绪。
3. **跑 `/dev-story [故事路径]`**——读故事、路由到正确的程序员智能体、实现。这是核心干活命令。
4. **跑 `/code-review`**——实现后做架构代码评审。
5. **跑 `/story-done`**——8 阶段完成审查：验验收标准、查 GDD/ADR 偏差、关故事、推荐下一个故事。
6. **跑 `/qa-plan`**（每个 epic 或冲刺）——生成 QA 测试计划。
7. **跑 `/bug-report` / `/bug-triage`**——记录和排优 bug。
8. **跑 `/retrospective`**——冲刺后回顾，记经验。
9. **跑 `/scope-check`**——查范围蔓延（故事越加越多）。
10. **跑 `/team-*`**（可选）——复杂功能跨多智能体协作（如 `/team-combat` 协调战斗全管线）。

**产出物**：

- `src/` 下的实际代码
- 故事文件状态更新（In Progress → Done）
- `tests/` 下的测试
- `production/qa/` 下的测试证据
- `production/sprints/sprint-*.md`（每个冲刺）

**要过的门禁**：

- **LP-CODE-REVIEW**（主程审每个故事实现）：符合架构边界吗？违反编码标准或禁止模式吗？
- **QL-STORY-READY**（故事进冲刺前）
- **PR-SPRINT**（每个冲刺前）
- **QL-TEST-COVERAGE**（每个冲刺结束）：所有 Logic 故事有单测吗？
- 可选：PR-MILESTONE、AD-VISUAL

**为什么这步不能省**：这是"真正写代码"的阶段。前面所有准备都是为了让这步可控——故事有明确验收标准、架构有明确边界、代码有明确规范、提交有自动校验。没有这些，生产阶段就是"各写各的、bug 满天、返工不断"。

> 💡 **关键概念——故事（Story）**：从 epic 拆出来的最小可实现单元，1-3 天能做完。每个故事有：验收标准（做完怎么知道对）、引用的 TR-ID（对应哪个需求）、引用的 ADR（对应哪个架构决策）、故事类型（Logic/Integration/Visual/UI/Config，决定要什么测试证据）。

---

### Phase 6：打磨（Polish）

**目的**：功能完整后，优化性能、调平衡、试玩、修 bug、加无障碍、打磨音画。

**类比**：精装修 + 验房。毛坯房盖好了，但要住人还得铺地板、刷墙、装灯具、测水电、修瑕疵。

**这一步干什么**：

1. **跑 `/perf-profile`**——性能剖析，找 CPU/GPU/内存瓶颈。
2. **跑 `/balance-check`**——分析平衡数据和公式，找异常值和断裂的进度曲线。
3. **跑 `/asset-audit`**——审资产命名、格式、大小预算。
4. **跑 `/playtest-report`**——**至少 3 次试玩**，覆盖：新玩家体验、中后期系统、难度曲线。
5. **跑 `/team-polish`**——协调性能/音画/UX/QA 多智能体打磨。
6. **跑 `/retrospective`**——里程碑回顾。

**产出物**：

- `production/playtests/*.md`（至少 3 份试玩报告）
- 性能/平衡/资产审计报告

**要过的门禁**：

- **QL-TEST-COVERAGE**（测试覆盖最终审）
- **CD-PLAYTEST**（创意总监审试玩）：核心幻想落地了吗？
- **PR-MILESTONE**（制作人审里程碑风险）
- 可选：AD-VISUAL

**为什么这步不能省**：功能"能跑"和"好玩"是两回事。不试玩不知道难度曲线断在哪、新玩家卡在哪。不性能剖析不知道哪里掉帧。这步把"能跑的毛坯"变成"好玩的成品"。

---

### Phase 7：发布（Release）

**目的**：上线检查、补丁说明、协调发布、监控。

**类比**：交房 + 入住 + 售后。验收合格了，办交房手续，业主入住，之后有问题要修。

**这一步干什么**：

1. **跑 `/release-checklist`**——跨部门预发布检查：代码、内容、商店、法务。
2. **跑 `/launch-checklist`**——最终上线就绪验证——上线前最后一道门。
3. **跑 `/patch-notes`**——生成面向玩家的补丁说明。
4. **跑 `/changelog`**——从 git 历史生成内部 changelog。
5. **跑 `/hotfix`**（如出紧急 bug）——带审计追踪的紧急修复，绕过正常冲刺流程。
6. **跑 `/day-one-patch`**——为 gold master 后发现的已知问题准备首日补丁。

**产出物**：

- 发布检查清单（通过）
- 补丁说明 / changelog
- 发布构建

**要过的门禁**：

- **4 个 PHASE-GATE**（`/gate-check` 最终阶段门）：四总监并行最终评审
- 可选：QL-TEST-COVERAGE

**为什么这步不能省**：上线是不可逆的。没检查就发布，可能商店审核被拒、玩家遇到致命 bug、法务问题下架。发布检查把"会出事"的点提前过一遍。

---

### 阶段转换：门禁（Gate Check）

**每个阶段之间**都要跑 `/gate-check`。它做的事：

1. **检查产出物**——按 [workflow-catalog.yaml](file:///workspace/.claude/docs/workflow-catalog.yaml) 查这阶段该有的文件在不在、合不合格。
2. **并行召唤 4 总监**——创意/技术/制作/美术四位同时评审，各给判决（READY / CONCERNS / NOT READY）。
3. **取最严判决**——一个 NOT READY 就整体 FAIL。
4. **三种结果**：
   - **PASS**：全部 READY，进下一阶段
   - **CONCERNS**：有顾虑但不阻塞，用户决定是否带风险过
   - **FAIL**：有阻塞，必须解决才能进

> ⚠️ **重要**：门禁判决是 **ADVISORY（建议性）**——它指导决策但**不硬阻塞**，用户最终决定是否进下一阶段。这是"人在环中"的体现——AI 给建议，人拍板。但别滥用，CONCERNS/FAIL 往往意味着真问题。

---

### 流程的核心特征

这套流程有 5 个特征，理解了就理解了"为什么这么设计"：

1. **顺序性**：阶段有先后，Phase 2 的 GDD 是 Phase 3 ADR 的输入，Phase 3 的 ADR 是 Phase 4 故事的依据。跳阶段会断链。
2. **可验证性**：每步有产出物（文件），可检查"做没做、合不合格"。不是"感觉差不多"。
3. **可追溯性**：TR-ID 串起"GDD 需求 → ADR 决策 → 故事实现"。改一个能找到所有受影响的。
4. **人在环中**：每个关键决策点 AI 给选项，用户拍板。AI 不替你做创意决定。
5. **可恢复性**：状态写文件，会话崩溃/压缩后能从 [active.md](file:///workspace/.claude/docs/context-management.md) 恢复。

---

## 第二部分：软件工程实践——解决什么问题，原理是什么

上面流程里塞满了"规矩"：写 GDD、写 ADR、过门禁、用注册表、数据驱动、写测试、代码评审……每个都不是随便定的，都解决一个真实的"会出事"的问题。下面逐个讲。

### 实践 1：文档驱动开发（先写文档再写代码）

**做什么**：Phase 2 写 GDD（做什么），Phase 3 写 ADR（怎么做），Phase 4 拆故事（具体任务），Phase 5 才写代码。

**解决的问题**：

- **"程序员猜需求"**：没有 GDD，程序员不知道"连击窗口 0.4 还是 0.5 秒"，猜错返工。
- **"需求漂移"**：口头需求传着传着就变了，没人记得最初说啥。
- **"无法验证完成"**：没有验收标准，做完了不知道对不对。

**背后的原理**：

- **需求工程**：软件工程的核心发现之一是"修需求错误的成本随阶段指数上升"——需求阶段改一行字，代码阶段可能改一周。所以尽早把需求写清楚、写下来。
- **显式知识**：人脑记忆不可靠，文档让知识"外化"——成为团队共享的、持久的、可引用的资产。
- **可追溯性**：文档提供"决策→实现"的链条，出 bug 时能回溯到原始需求看是需求错了还是实现错了。

**类比**：装修前先出施工图。口头说"把墙拆了"和图纸标"拆这堵非承重墙"是两回事。图纸上写错了，改图纸便宜；墙拆错了，砌回去贵。

---

### 实践 2：阶段门禁（Phase Gate）

**做什么**：每阶段结束跑 `/gate-check`，四总监并行评审，不达标不进下一阶段。

**解决的问题**：

- **"带病前进"**：地基没打好就砌墙，墙砌到三楼发现地基裂了，全拆。
- **"隐藏问题累积"**：小问题不处理，越积越多，到最后集中爆发。
- **"主观判断能不能进下一阶段"**：没有客观标准，靠"感觉差不多"。

**背后的原理**：

- **阶段门评审（Stage-Gate）**：Robert Cooper 提出的产品开发方法论。核心是每个阶段结束有明确的"门"，过门才能进下一阶段，强制早期暴露问题。
- **并行评审**：多角度同时看（创意/技术/制作/美术），避免单视角盲区。
- **最严判决原则**：一个 NOT READY 就 FAIL——保守好过返工。
- **建议性而非强制性**：门禁给建议，人最终决定。这是"辅助决策"而非"替代决策"。

**类比**：楼层验收。盖完一层找监理签字才盖下一层。监理说"承重不达标"你不听硬盖，塌了你自己负责——但至少你被告知了风险。

---

### 实践 3：架构决策记录（ADR）

**做什么**：每个关键技术决策写一份 ADR，记 Context / Decision / Alternatives / Consequences。

**解决的问题**：

- **"为什么当初这么选的"**：半年后没人记得"为什么用 Jolt 不用 GodotPhysics"，想改又怕踩当初避开的坑。
- **"重复决策"**：不知道前人已经否决过某方案，又讨论一遍。
- **"决策无依据"**：拍脑袋决定，没有权衡分析。

**背后的原理**：

- **决策记录（Decision Log）**：Michael Nygard 提出的 ADR 模式。核心洞察是"架构决策的上下文和理由，和决策本身一样重要"。
- **备选方案显式化**：写下"放弃了什么、为什么"——这比"选了什么"更有价值，因为它记录了决策空间。
- **生命周期管理**：ADR 有状态（Proposed → Accepted → Superseded），不删除只标记取代，保留历史。引用 Proposed 的故事被自动封禁——强制"决策要被接受才能实现"。

**类比**：公司的会议纪要。讨论了三个方案，选了 A，否了 B 和 C。半年后想改，翻纪要看到"B 当时因为性能问题被否"，就不会重复踩坑。

---

### 实践 4：单一事实源（Single Source of Truth）+ 注册表

**做什么**：跨文档共享的事实集中在一个地方（[tr-registry.yaml](file:///workspace/docs/architecture/tr-registry.yaml)、[architecture.yaml](file:///workspace/docs/registry/architecture.yaml)），其他文档只引用不重写。

**解决的问题**：

- **"数据不一致"**：GDD 说血量 100，故事文件复制了这句，后来 GDD 改成 120，故事还是 100 → bug。
- **"两个系统都管同一状态"**：战斗系统和健康系统都改玩家血量 → 数据竞争，血量闪烁。
- **"改一处忘改别处"**：改了 API 决策，没同步到所有用它的地方。

**背后的原理**：

- **DRY 原则（Don't Repeat Yourself）**：每个事实只有一个权威来源，其他地方引用它。复制粘贴是 bug 之源。
- **状态归属（State Ownership）**：每块共享状态只有一个 owner，只有 owner 能写，其他只读。这是并发控制的基本原理——避免写写冲突。
- **接口契约（Interface Contract）**：系统间怎么通信要显式约定（信号、直接调用、事件总线、RPC），否则集成时才发现一个用信号一个用直接调用。
- **永久 ID**：TR-ID 永不重新编号、永不删除。需求作废标 `deprecated`，被替换标 `superseded-by`。这样所有引用不会断链。

**类比**：户籍系统。一个人的户籍只有一个地方登记，其他地方查这里。如果派出所和公安局都登记户籍，两边不一致就乱了。

---

### 实践 5：数据驱动设计（Data-Driven Design）

**做什么**：玩法数值（伤害、血量、速度）不放代码里，放外部配置文件（JSON/YAML）。[coding-standards.md](file:///workspace/.claude/docs/coding-standards.md) 明确"Gameplay values must be data-driven, never hardcoded"。

**解决的问题**：

- **"改数值要重编译"**：调个伤害值要改代码、重新构建、重启，慢。
- **"数值散落代码各处"**：想平衡时找不到所有相关的值在哪。
- **"非程序员改不了数值"**：策划想调平衡，但不会改代码。

**背后的原理**：

- **关注点分离（Separation of Concerns）**：代码是"逻辑"，数据是"参数"。逻辑稳定，参数常变。分开后改参数不动逻辑。
- **配置优于代码**：变化的、需频繁调整的、非程序员要碰的——放配置。稳定的、复杂的、出 bug 危险的——放代码。
- **可观测性**：所有平衡值集中在数据文件，一眼看全，便于平衡审计（`/balance-check`）。

**类比**：菜谱和食材分开。菜谱（代码）说"放盐适量"，盐放多少（数据）写在食材表里。想调咸淡改食材表，不用重写菜谱。

---

### 实践 6：验证驱动开发（Verification-Driven Development）

**做什么**：[coding-standards.md](file:///workspace/.claude/docs/coding-standards.md) 规定"标记完成前必须有证据"。按故事类型分证据：Logic 故事必须自动单测（阻塞）、Integration 故事集成测试或试玩记录（阻塞）、Visual/Feel 截图+签字（建议）、UI 手动走查（建议）、Config 冒烟测试（建议）。

**解决的问题**：

- **"做完了不知道对不对"**：没有验收标准，"我觉得做完了"和"真的做对了"是两回事。
- **"回归 bug"**：改 A 破坏 B，没人发现就上线。
- **"全靠手动测"**：每次改都手动玩一遍，慢且容易漏。

**背后的原理**：

- **测试金字塔**：底层是大量快速的单元测试（Logic 故事），中间是集成测试（Integration 故事），顶层是少量手动测试（Visual/Feel）。自动化的覆盖广，手动的覆盖"手感"这种机器测不了的。
- **可测试性设计**：公开方法必须可单测，用依赖注入而非单例——这是"为测试而设计"的架构原则。
- **确定性测试**：测试每次结果一样，不依赖随机种子、时间、执行顺序、外部 API。否则"偶尔挂"的测试（flaky）比没测试还糟。
- **证据分级**：不是所有东西都该自动化。视觉保真、"手感"、平台渲染——机器测不了，靠截图+人签字。强行自动化反而维护成本高。

**类比**：作业写完对答案。数学题（Logic）对标准答案（自动批改），作文（Visual/Feel）给老师看（人签字）。不是说作文不该测，是测法不同。

---

### 实践 7：代码评审（Code Review）

**做什么**：[review-workflow.md](file:///workspace/.claude/docs/review-workflow.md) 规定代码改动由对应主管审、设计改动由 game-designer + creative-director 签、架构改动由 technical-director 签、跨域改动由 producer 签。Phase 5 每个故事实现后 `/code-review`。

**解决的问题**：

- **"一人写的代码没人检查"**：bug、坏模式、不规范溜进主干。
- **"知识不共享"**：只有写代码的人懂这块，他走了就没人懂。
- **"架构被悄悄破坏"**：改着改着偏离了 ADR 定的边界。

**背后的原理**：

- **四眼原则（Four-Eyes Principle）**：高风险工作至少两人过目。一人容易盲区。
- **门禁 LP-CODE-REVIEW**：主程审"符合架构边界吗、违反编码标准或禁止模式吗、API 可测可文档吗、对 GDD 规则有正确性问题吗"。
- **分层评审**：代码→主管、设计→设计总监、架构→技术总监、跨域→制作人。不同维度找不同问题。

**类比**：论文同行评审。你写了论文，导师和同行审一遍才发表。不是不信任你，是多一双眼睛少一个 bug。

---

### 实践 8：约定式提交（Conventional Commits）

**做什么**：[coding-standards.md](file:///workspace/.claude/docs/coding-standards.md) 规定提交信息用 `feat:` / `fix:` / `chore:` / `docs:` / `test:` / `refactor:` 格式，正文引用故事 ID。

**解决的问题**：

- **"提交信息看不懂"**：`update`、`fix bug`、`改了点东西`——半年后没人知道这提交干啥。
- **"无法自动生成 changelog"**：要手动写发布说明。
- **"无法追踪故事"**：哪个提交对应哪个故事？查不到。

**背后的原理**：

- **机器可解析历史**：约定式提交让 git 历史可被工具解析——`/changelog` 能从 `feat:` 提取新功能、从 `fix:` 提取修复，自动生成 changelog。
- **可追溯性**：提交引用故事 ID（如 `Story: EPIC-001-S02`），从提交能反查到故事、再反查到 ADR 和 GDD 需求。
- **语义化版本**：`feat:` 对应 minor 版本、`fix:` 对应 patch、`BREAKING CHANGE` 对应 major——可自动决定版本号。

**类比**：快递单上的品类标签。标"易碎品"和什么都不标，搬运工处理方式不同。

---

### 实践 9：增量迭代开发（Incremental & Iterative）

**做什么**：用冲刺（sprint）把大工作拆成 1-3 天的小块，每个冲刺结束回顾、调方向。垂直切片先验证再全面生产。

**解决的问题**：

- **"瀑布式开发的风险"**：一口气做完才发现方向错了，沉没成本巨大。
- **"任务过大"**：一个任务做两周，中间没法验证进度。
- **"范围蔓延"**：做着做着加功能，永远做不完。

**背后的原理**：

- **敏捷开发（Agile）**：迭代优先于计划。短周期交付、频繁反馈、适应变化。
- **最小可行产品（MVP）**：用最少功能验证核心假设。游戏里就是"核心循环好不好玩"——先验证再扩展。
- **范围分层**：MVP / 垂直切片 / Alpha / 完整版——每层是"如果时间不够就停在这"的优雅降级，不是半成品。
- **冲刺（Sprint）**：固定时长（通常 1-4 周）的迭代单元。结束时必须有可交付的增量。
- **回顾（Retrospective）**：每个冲刺结束反思"什么做得好、什么要改"，持续改进。

**类比**：写小说。先写大纲（概念），再写每章详纲（系统设计），再写第一章试投（垂直切片），读者反馈好再继续写（生产），最后润色（打磨）。不是一口气写完十万字再给人看。

---

### 实践 10：关注点分离 + 系统边界（Separation of Concerns）

**做什么**：Phase 2 的 `/map-systems` 把游戏拆成系统，每个系统有明确边界和单一职责。Phase 3 的 ADR 定义系统间接口契约。`/architecture-review` 审"边界干净吗、有上帝对象吗、依赖倒置吗"。

**解决的问题**：

- **"上帝对象"**：一个系统什么都管，改一处影响全局，无法维护。
- **"紧耦合"**：系统间互相直接依赖，改 A 必须改 B，没法独立开发。
- **"依赖倒置"**：底层 Foundation 系统依赖上层 Feature 系统，架构反转。

**背后的原理**：

- **单一职责原则（SRP）**：每个模块只有一个变化的理由。职责多的模块，任何相关变化都要改它，脆弱。
- **分层架构**：Foundation（基础层）→ Core（核心层）→ Feature（特性层）→ Presentation（表现层）→ Polish（打磨层）。依赖只能往下，不能往上。
- **接口契约**：系统间通过显式契约通信（信号/直接调用/事件总线/RPC/共享资源），契约定义 producer、consumers、signature。换实现不改调用方。
- **状态归属**：每块共享状态只有一个 owner 系统能写，避免写写竞争。

**类比**：公司的部门划分。财务部管钱、人事部管人、技术部管代码。如果一个人又管钱又管人又写代码，他请假了全公司停摆。

---

### 实践 11：性能预算（Performance Budgets）

**做什么**：[architecture.yaml](file:///workspace/docs/registry/architecture.yaml) 登记每个系统的帧时间预算，总和不超过总帧预算（60FPS = 16.6ms）。`/architecture-review` 审总和。

**解决的问题**：

- **"掉帧"**：各系统各花各的，加起来超 16.6ms，游戏卡。
- **"优化时互相甩锅"**：不知道谁超了预算。
- **"后期才发现性能问题"**：架构定型了，优化要大改。

**背后的原理**：

- **预算制**：稀缺资源（帧时间）按预算分配，总和有上限。这是资源管理的通用方法。
- **早期分配**：架构阶段就分预算，而不是写完再"看谁慢优化谁"。早期分配让每个系统从开始就考虑性能。
- **可问责**：每个系统有自己的预算，超了知道找谁。

**类比**：装修预算。总价 100 万，每个房间分多少。厨房 20 万、卫生间 15 万……加起来不能超 100 万。不是装完了算账发现超了 30 万。

### 实践 12：上下文管理（Context Management）

**做什么**：[context-management.md](file:///workspace/.claude/docs/context-management.md) 规定"文件即记忆"——重要决策写文件不靠对话、增量分节写入、主动压缩、用子智能体分担、崩溃靠 active.md 恢复。

**解决的问题**：

- **"长会话失忆"**：对话太长触发压缩，早期决策被总结掉，AI 重复问或推翻已定的事。
- **"会话崩溃丢进度"**：会话死了，没存盘的讨论全丢。
- **"上下文被无关内容占满"**：研究性读取塞满上下文，真正要干的活没空间。

**背后的原理**：

- **外部记忆（External Memory）**：人脑工作记忆有限，用笔记外化。AI 同理——上下文窗口有限，用文件外化。
- **增量持久化**：每完成一节立即写盘，而非整篇写完再存。降低崩溃损失。
- **上下文经济**：上下文是稀缺资源，用子智能体（独立上下文）干消耗大的研究活，只把摘要返回主会话。
- **检查点恢复**：active.md 是"检查点"，崩溃后从检查点恢复而非从头来。

**类比**：写论文。不是在脑子里想完整篇再落笔，而是写完一节存一节。电脑崩了重启，打开文件接着写，不用重想。

### 实践 13：人在环中（Human-in-the-Loop）

**做什么**：[COLLABORATIVE-DESIGN-PRINCIPLE.md](file:///workspace/docs/COLLABORATIVE-DESIGN-PRINCIPLE.md) 规定 AI 是"协作顾问"不是"自动驾驶生成器"。每次交互走 Question → Options → Decision → Draft → Approval 五步。写文件前必须问"可以写到这个路径吗？"。

**解决的问题**：

- **"AI 自作主张"**：你说"做个游戏"，AI 自己设计自己写，做出来不是你想要的，浪费一整轮重写。
- **"创意决策被 AI 偷走"**：AI 替你决定了"游戏是什么风格""核心机制是什么"——这些是创意决策，应该是你定。
- **"AI 猜错意图"**：没有澄清就动手，猜错了全白做。

**背后的原理**：

- **辅助决策 vs 替代决策**：AI 擅长给选项、分析权衡、起草；人不擅长穷举选项但擅长从选项里挑。各做擅长的。
- **约束式提问**：好问题是"带选项的"（2-4 个带权衡的选项），不是"开放式的"（"应该长什么样？"）。开放式问题让人不知从何答起。
- **"可以写吗"协议（May-I-write）**：写文件前显式求批准，强制"AI 提议、人批准"的节奏。
- **Explain → Capture**：先在正文里写完整分析（pros/cons、理论、参考游戏），再用工具捕获简洁选择。详细推理放正文，工具只放短标签。

**类比**：律师和当事人。律师（AI）研究法律、给建议、起草文件，但"打不打官司、接不和解"是当事人（你）决定。律师不能替你签字。

### 实践 14：自动化守卫（Automated Guards / Hooks）

**做什么**：12 个钩子（[hooks-reference.md](file:///workspace/.claude/docs/hooks-reference.md)）在提交/推送/写文件/会话事件自动触发校验——提交前查代码质量和设计文档格式、推送前跑测试门禁、写资产后查命名和大小、压缩前倒出状态。

**解决的问题**：

- **"靠自觉不可靠"**：让人记得"提交前检查"不现实，必然漏。
- **"规则形同虚设"**：写了编码标准但没人执行，等于没有。
- **"上下文压缩丢状态"**：压缩是系统行为，不主动保存就丢。

**背后的原理**：

- **左移（Shift-Left）**：问题越早发现越便宜。提交时发现比上线后发现便宜 100 倍。钩子把检查"左移"到提交/推送时。
- **不可绕过的检查**：钩子在工具层触发，AI 不能"选择不检查"。比"提醒 AI 遵守"可靠。
- **优雅降级**：缺了 jq/Python 钩子不报错只是跳过——不破坏工作流，但失去保护。
- **退出码语义**：PreToolUse 钩子 exit 2 阻断操作、exit 0 放行。这是机器可读的"通过/不通过"。

**类比**：安检门。不是靠乘客自觉"我没带违禁品"，是过安检门自动响。响了才人工复查。

### 实践 15：路径规则（Path-Specific Rules）

**做什么**：[rules-reference.md](file:///workspace/.claude/docs/rules-reference.md) 的 11 条规则按路径生效——在 `src/gameplay/` 写代码自动套"玩法规则"（数据驱动、用 delta time、不引用 UI），在 `src/ai/` 套"AI 规则"，在 `design/gdd/` 套"设计文档规则"。

**解决的问题**：

- **"一刀切规则不合适"**：玩法代码和 AI 代码规矩不一样，UI 代码和着色器规矩不一样。统一规则要么太松（玩法没保护）要么太严（原型背生产包袱）。
- **"规则不知道何时适用"**：规则写了但 AI 不知道该用哪条。
- **"原型被生产规则拖累"**：原型代码本该快速验证，却被迫写文档注释、写测试。

**背后的原理**：

- **上下文感知规则**：规则和它适用的代码物理上关联——在哪个目录就套哪条。无需 AI 判断"这是不是该用某规则"。
- **差异化标准**：`prototype-code.md` 明确"标准放宽、要 README、记假设"——原型就是该快。`engine-code.md` 要求"热路径零分配、线程安全、API 稳定"——引擎就是该严。
- **最小惊讶**：在某个目录写代码，AI 自动按那个目录的规矩来，不用人提醒。

**类比**：车间分区。机加工区戴护目镜、喷漆区戴防毒面具、办公区随便。不是全厂都戴防毒面具——按区域定规矩。

## 常见误区

**误区 1："这套流程太重，小项目/单人用不上。"**
⚠️ 半对。流程的**强度可调**——`review-mode` 有 full/lean/solo 三档，solo 全跳过门禁。`required: false` 的步骤可跳。单人用 lean 模式，game jam 用 solo 模式。但**核心实践**（GDD、ADR、数据驱动、测试）即使单人也值得——它们防的是"一个人更容易犯的错"（没人复审、没人质疑假设）。

**误区 2："先写代码再补文档也一样。"**
❌ 不一样。文档驱动开发的核心是"用文档**驱动**决策"——写 GDD 的过程逼你想清楚边界情况、公式、依赖。事后补文档只是"记录已做的"，没有"逼你想清楚"的价值。`/reverse-document` 是给遗留代码的补救，不是推荐流程。

**误区 3："门禁是 AI 在管我，我为什么要被管。"**
❌ 误解。门禁判决是 **ADVISORY（建议性）**，最终是**你决定**进不进下一阶段。门禁是"四位总监给你提建议"，不是"AI 管你"。这恰恰是"人在环中"——AI 辅助，你决策。

**误区 4："数据驱动就是所有数值都放配置文件。"**
⚠️ 过了。数据驱动针对**常变的、需平衡的、非程序员要碰的**玩法数值（伤害、血量、速度）。不是所有数值都放配置——比如"血量不能为负"这种逻辑约束就该在代码里。判断标准：这个值会不会调？谁来调？

**误区 5："测试越多越好。"**
❌ 不是。测试有维护成本。该自动化的是 Logic（公式、AI、状态机）——确定性强、回归价值高。不该强行自动化的是 Visual/Feel（手感、视觉保真）——机器测不了，强行自动化维护成本高于价值。`coding-standards.md` 的"What NOT to Automate"明确列了这些。

**误区 6："ADR 写完就完了。"**
❌ ADR 有生命周期。引擎升级了要复审（HIGH 知识风险的 ADR 标 Superseded 写新的）。决策被推翻了要标 Superseded 不能删。引用 Proposed ADR 的故事被自动封禁——必须 Accepted 才能实现。ADR 是"活的文档"。

**误区 7："范围蔓延加加班就能赶上。"**
❌ 危险。`/scope-check` 的存在就是因为范围蔓延是项目失败的头号原因。正确做法是范围分层（MVP/垂直切片/Alpha/完整版），时间不够就停在优雅的降级点，而非"什么都做但都做不好"。

**误区 8："AI 这么强，让它自己设计自己写就行。"**
❌ 这是 COLLABORATIVE-DESIGN-PRINCIPLE 明令禁止的"Autonomous Generator（自主生成器）"模式。AI 眼里的"最优"未必符合你的愿景。创意决策归你，AI 给选项和分析。这是整套架构的设计哲学。

## 小测验

**Q1**：你跳过 Phase 2（系统设计）直接写代码，最可能出什么问题？

<details>
<summary>答案</summary>

程序员不知道机制细节（如"连击窗口 0.4 还是 0.5 秒"），只能猜，猜错返工。系统边界没定，两个系统都以为自己管同一状态 → 数据竞争。没有 GDD 的 8 节，Edge Cases 和 Acceptance Criteria 缺失，做完了不知道对不对、漏了边界情况。

</details>

**Q2**：为什么 ADR 的"Alternatives Considered（备选方案）"章节比"Decision（决定）"本身更有价值？

<details>
<summary>答案</summary>

Decision 只记"选了什么"，Alternatives 记"放弃了什么、为什么"。半年后想改决策时，Alternatives 告诉你"前人已经否决过某方案、因为什么"——避免重复踩坑和重复讨论。没有 Alternatives 的 ADR 是"拍脑袋决定"的记录，不是"权衡决策"的记录。

</details>

**Q3**：你的游戏掉帧。`architecture.yaml` 怎么帮你找原因？

<details>
<summary>答案</summary>

`performance_budgets` 段登记了每个系统的帧时间预算（如战斗 2.0ms、AI 1.5ms……）和总帧预算（60FPS=16.6ms）。你逐系统量实际耗时，对比预算，超了的那个就是瓶颈。没有预算分配，掉帧时只能"全量优化"——不知道谁超了，互相甩锅。

</details>

**Q4**：为什么 GDD 的"Edge Cases（边界情况）"章节不能省？

<details>
<summary>答案</summary>

Edge Cases 防"漏掉的情况"。如"血量为 0 时同时被治疗会怎样""两个无敌效果同时触发谁优先"。不写 Edge Cases，程序员实现时遇到这些情况只能猜，猜错就是 bug。Acceptance Criteria 验证"正常情况对"，Edge Cases 验证"异常情况也不崩"。

</details>

**Q5**：你做了个原型发现核心机制不好玩。这是失败吗？

<details>
<summary>答案</summary>

不是，这是**成功**。原型的目的就是"花 1-3 天验证机制好不好玩"。发现不好玩，省下了"写完整 GDD + ADR + 实现"的几个月。这是增量迭代的核心——**早失败、便宜地失败**。创意总监会在原型后做 PROCEED / PIVOT / KILL 决定。

</details>

**Q6**：为什么说"门禁判决是建议性的"反而比"硬阻塞"更好？

<details>
<summary>答案</summary>

硬阻塞会让人为了过门禁而"凑条件"，掩盖真问题。建议性让用户知道风险但保留决策权——可能"我知道有 CONCERNS 但时间紧我接受风险过"。这是"人在环中"的体现：AI 给专业建议，人结合 AI 不知道的上下文（商业压力、个人偏好）做最终判断。当然，滥用（每次都带 FAIL 过）就失去了门禁的意义。

</details>

**Q7**：你的会话压缩后，AI 忘了之前定的"连击窗口 0.4 秒"，开始重新问。你怎么让它恢复？

<details>
<summary>答案</summary>

让它读 `production/session-state/active.md`——这是 [context-management.md](file:///workspace/.claude/docs/context-management.md) 规定的会话状态文件，记录关键决策。如果决策已经写进 GDD 文件，读 GDD 文件也能恢复。"文件即记忆"——对话会压缩，文件不会。

</details>

**Q8**：为什么 `prototypes/` 目录的规则比 `src/` 宽松？

<details>
<summary>答案</summary>

原型是"快速验证机制好不好玩"，要的是速度。强行写文档注释、写测试、遵守生产编码标准会拖慢验证。`prototype-code.md` 规则明确"标准放宽"——但要求"要 README、记假设"，保证原型可被理解且不混进生产。`src/` 是生产代码，规则严。这是**路径规则**的差异化标准——不同目录不同规矩。

</details>

## 一句话带走

> **游戏开发流程 = 7 阶段（概念→系统设计→技术搭建→预制作→生产→打磨→发布），每阶段有产出物和门禁，不达标不进下一阶段。背后的软件工程实践——文档驱动、阶段门、ADR、单一事实源、数据驱动、验证驱动、代码评审、约定式提交、增量迭代、关注点分离、性能预算、上下文管理、人在环中、自动化守卫、路径规则——每个都解决一个"会出事"的真实问题，原理都是"把会出事的地方用流程/工具固化下来，不靠自觉"。**
