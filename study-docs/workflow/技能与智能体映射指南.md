# 技能与智能体映射指南 —— 开发一个游戏要用哪些技能、哪些智能体

> **写给初学者**：这篇回答一个问题——"我想做一个游戏，从设计到发布，我该用哪些技能（skill）？每个技能背后会派哪些智能体（agent）？为什么是它们？"
>
> 依据 [docs/WORKFLOW-GUIDE.md](file:///workspace/docs/WORKFLOW-GUIDE.md) 与全部 73 个 SKILL.md 的实际派生关系逐一核实整理。

---

## 0. 先搞懂调用链：用户 → 技能 → 智能体

整个系统的运转方式只有一条链：

```
你（用户）
  │  敲 /brainstorm、/dev-story 这样的命令
  ▼
技能（Skill）—— .claude/skills/[名字]/SKILL.md
  │  正文被注入主会话，变成"作业指导书"
  │  正文里写着：第几步派谁、给它什么材料
  ▼
智能体（Agent）—— .claude/agents/[名字].md
  │  主会话用 Agent 工具（旧名 Task）派生
  │  在独立上下文里干活，干完返回文本
  ▼
产出文档/代码（数据），流程继续
```

三个关键认知：

1. **智能体不会自己跳出来**。永远是技能正文"点名"派谁，主会话照做。
2. **一个技能往往派多个智能体**，按任务性质路由——写公式派 systems-designer，写故事派 narrative-director。
3. **49 个智能体你不需要全记住**。一个阶段真正用到的就 3-8 个，下文按阶段列全。

## 2. 四张核心映射表（建议精读）

### 2.1 `/design-system` 的系统类型路由表（Phase 2 核心）

写 GDD 时按"系统是什么类型"决定派谁。**主智能体**出内容，**辅助智能体**提供专业视角：

| 系统类型 | 主智能体 | 辅助智能体 | 为什么 |
|----------|----------|------------|--------|
| 基础设施（事件总线/存档/场景管理） | systems-designer | gameplay-programmer（可行性）、engine-programmer（引擎集成） | 基础设施偏系统思维，不是玩法创意 |
| 战斗/伤害/生命 | game-designer | systems-designer（公式）、ai-programmer（敌人 AI）、art-director（打击感视觉方向） | 玩法是主，公式和表现是辅 |
| 经济/战利品/制造 | economy-designer | systems-designer（数值曲线）、game-designer（循环） | 经济系统数值敏感，交给经济专家 |
| 进度/XP/技能 | game-designer | systems-designer（曲线）、economy-designer（回收） | 进度曲线是数值问题 |
| 对话/任务/世界观 | game-designer | narrative-director（剧情）、writer（文本）、art-director（角色视觉） | 结构归设计，内容归编剧 |
| UI 系统（HUD/菜单） | game-designer | ux-designer（流程）、ui-programmer（可行性）、art-director（视觉）、technical-artist（渲染约束） | UI 牵扯方最多 |
| 音频系统 | game-designer | audio-director（方向）、sound-designer（规格） | |
| AI/寻路/行为 | game-designer | ai-programmer（实现）、systems-designer（评分） | |
| 关卡/世界系统 | game-designer | level-designer（空间）、world-builder（世界观） | |
| 镜头/输入/操控 | game-designer | ux-designer（手感）、gameplay-programmer（可行性） | |
| 动画/角色移动 | game-designer | art-director（动画风格）、technical-artist（骨骼约束）、gameplay-programmer（手感） | |
| 视觉特效/粒子/着色器 | game-designer | art-director（视觉方向）、technical-artist（性能预算）、systems-designer（触发集成） | |
| 角色系统（属性/职业） | game-designer | art-director（视觉原型）、narrative-director（角色弧光）、systems-designer（属性公式） | |

**规律**：game-designer 是大多数玩法系统的"主笔"，专家按领域当"辅助"。两条规则兜底：
- 两行都匹配 → 派两行主智能体的**并集**
- 写公式/边缘情况/验收标准这三节时，**强制**再派 systems-designer / narrative-director / qa-lead 复核

### 2.2 `/dev-story` 的程序员路由表（Phase 5 核心）

实现故事卡时按"故事的层 + 类型"决定派谁：

| 故事上下文 | 派谁 | 为什么 |
|------------|------|--------|
| Foundation 层（任何类型） | engine-programmer | 底层代码是引擎程序员的领地 |
| 任何层 · Type: UI | ui-programmer | UI 代码有专门框架 |
| 任何层 · Type: Visual/Feel | gameplay-programmer | 表现层代码贴玩法 |
| Core/Feature · 玩法机制 | gameplay-programmer | |
| Core/Feature · AI 行为/寻路 | ai-programmer | |
| Core/Feature · 网络/复制 | network-programmer | |
| Config/Data · 无代码 | 不派智能体 | 改配置文件主会话直接干 |

**副驾驶规则**：代码类故事**总是**同时派一个引擎专家当"副手"（如 Godot 项目派 godot-specialist），检查代码符合引擎习惯。引擎风险为 HIGH 时（引擎版本比模型知识新），这个副手绝不能省。

| 引擎 | 可用的专家智能体 |
|------|------------------|
| Godot 4 | godot-specialist、godot-gdscript-specialist、godot-csharp-specialist、godot-shader-specialist、godot-gdextension-specialist |
| Unity | unity-specialist、unity-ui-specialist、unity-shader-specialist、unity-dots-specialist、unity-addressables-specialist |
| Unreal | unreal-specialist、ue-gas-specialist、ue-blueprint-specialist、ue-umg-specialist、ue-replication-specialist |

### 2.3 团队技能的固定班底（Phase 5-7 跨领域功能）

9 个 `/team-*` 技能各带一支固定队伍（都是主会话当指挥，并行派活）：

| 技能 | 班底 | 干什么 |
|------|------|--------|
| `/team-combat` | game-designer + gameplay/ai-programmer + technical-artist + sound-designer + 引擎专家 + qa-tester | 战斗功能端到端 |
| `/team-narrative` | narrative-director + writer + world-builder + art-director + level-designer + localization-lead | 剧情内容 |
| `/team-ui` | ux-designer + ui-programmer + art-director + accessibility-specialist | UI 改版 |
| `/team-level` | narrative-director + world-builder + level-designer + systems-designer + art-director + accessibility-specialist + qa-tester | 关卡制作 |
| `/team-audio` | audio-director + sound-designer + accessibility-specialist + technical-artist + gameplay-programmer | 音频整体 |
| `/team-polish` | performance-analyst + engine-programmer + technical-artist + sound-designer + tools-programmer + qa-tester | 打磨冲刺 |
| `/team-qa` | qa-lead + qa-tester（大项目每故事一个） | 全周期 QA |
| `/team-release` | release-manager + qa-lead + devops-engineer + security-engineer + analytics-engineer + community-manager + producer（多人游戏加 network-programmer） | 发布协调 |
| `/team-live-ops` | live-ops-designer + economy-designer + analytics-engineer + community-manager + narrative-director + writer | 运营活动 |

**规律**：一个 team = 一个领域的全班人马。跨领域大功能别自己手动协调四五个智能体——让 team 技能来编排。

### 2.4 `/gate-check` 的总监评审团

阶段门禁不是查清单完事，是派总监智能体**评审裁决**。派几个由项目规模决定：

| 模式 | 评审团 | 为什么 |
|------|--------|--------|
| minimal | 只有 producer | 范围/排期是任何项目都逃不掉的判断 |
| standard | technical-director + producer | 有架构产物了，加技术审查 |
| full | creative-director + technical-director + producer + art-director 四人并行 | 四大维度全查 |

**机制**：并行派 → 各自跑自己的 `-PHASE-GATE` 门禁 → **取最严裁决**（一人 NOT READY，整个门禁 FAIL）。solo 模式下全跳过，只剩产物存在性检查。

## 3. 按阶段详解：技能怎么用、为什么派这些人

### Phase 1 概念：想清楚做什么

**`/brainstorm`** —— 从零到概念书。四门禁按顺序跑：
1. creative-director 跑 CD-PILLARS：压测你的设计支柱自洽吗
2. art-director 跑 AD-CONCEPT-VISUAL：定视觉锚点
3. technical-director 跑 TD-FEASIBILITY：识别最大技术风险
4. producer 跑 PR-SCOPE：划定范围梯队（MVP/切片/完整版）

**为什么四个人**：概念阶段的失误最贵。创意总监管"好玩吗"，技术总监管"做得出吗"，制作人管"做得完吗"，美术总监管"长什么样"。四视角提前碰撞，比做到一半发现冲突便宜十倍。

**`/setup-engine`** —— 定引擎。派对应引擎的专家智能体，生成 `technical-preferences.md` + 版本钉死的引擎参考文档（`docs/engine-reference/`）。**这一步决定后面 dev-story 派哪个引擎专家当副手**。

**`/map-systems`** —— 把概念拆成系统清单。三门禁：
- technical-director 跑 TD-SYSTEM-BOUNDARY：系统边界切得对吗
- producer 跑 PR-SCOPE：优先级排得合理吗
- creative-director 跑 CD-SYSTEMS：覆盖核心幻想吗

**`/prototype`** —— 概念原型（1-3 天）。派 prototyper 快速验证"核心想法好玩吗"。PIVOT 就回 brainstorm，PROCEED 就继续。

### Phase 2 系统设计：每个系统一份 GDD

**`/design-system [系统名]`** —— 逐节写 GDD，每节批准立即落盘。派谁看 2.1 路由表。**为什么派专家**：数值曲线（systems-designer）、经济平衡（economy-designer）、故事结构（narrative-director）这些是深水区，主会话自己写容易想当然。

**`/design-review [GDD路径]`** —— 审查。规则：
- 有玩法机制 → 派 game-designer
- 有公式 → 派 systems-designer
- **全部并行派**（不等一个再派下一个）
- 专家意见收齐后，creative-director 当**终审**做最终裁决

**为什么专家审 + 总监终审**：专家看深度（公式对不对），总监看方向（配不配支柱）。两层缺一不可。

**`/review-all-gdds`** —— 全部 GDD 交叉审查。派两个 game-designer 子智能体分头跑（一致性 + 设计理论），防止单一视角遗漏。

**`/art-bible`** —— 美术圣经。art-director 出视觉规范，跑 AD-ART-BIBLE 门禁。

### Phase 3 技术设置：决定怎么做

**`/create-architecture`** —— 总架构文档。两道门禁接力：
- technical-director 跑 TD-ARCHITECTURE：架构合理性
- lead-programmer 跑 LP-FEASIBILITY：程序员视角"这能落地吗"

**为什么加 lead-programmer**：架构师觉得优雅的方案，实现的人可能觉得是坑。LP-FEASIBILITY 就是让"要写代码的人"过目。

**`/architecture-decision "问题"`** —— 每个重大决策一份 ADR。派两次：
1. **引擎专家**：验证决策符合引擎习惯（对照版本钉死的参考文档，防 LLM 用过时 API）
2. **technical-director** 跑 TD-ADR：战略层终审

**`/create-control-manifest`** —— 把 Accepted 的 ADR 压成程序员速查表。technical-director 跑 TD-MANIFEST 门禁。

**`/ux-design [屏幕]`** —— UX 规格。ux-designer 是"主智能体"（写在前置元数据里），读无障碍需求文档和输入法配置自动补全覆盖检查。

### Phase 4 预生产：证明能做出来

**`/vertical-slice`** —— 垂直切片（生产质量的端到端验证）。creative-director 跑 CD-PLAYTEST 门禁裁决 PROCEED/PIVOT/KILL。

**`/create-epics layer: foundation`** —— 把设计变成史诗。producer 跑 PR-EPIC 门禁：**为什么是制作人**——史诗切分本质是范围决策，范围是 producer 的领地。

**`/create-stories [史诗名]`** —— 把史诗拆成故事卡。qa-lead 跑 QL-STORY-READY：**为什么是 QA 主管**——故事卡里的验收标准必须"可独立测试"，QA 最有资格判断。

**`/sprint-plan new`** —— 排冲刺。producer 跑 PR-SPRINT 门禁。

**`/story-readiness [故事路径]`** —— 领故事前体检。qa-lead 跑 QL-STORY-READY，查设计完整/架构覆盖/ADR 状态/manifest 新鲜度。

### Phase 5 生产：故事循环（最常用）

**主循环**：`/story-readiness` → `/dev-story` → `/story-done` → 下一个

**`/dev-story [故事路径]`** —— 实现。按 2.2 路由表派程序员 + 引擎专家副手。程序员智能体遵循协作协议：读设计 → 提问 → 给方案 → 你批准 → 才写代码。

**`/story-done [故事路径]`** —— 验收。两道：
- lead-programmer 跑 LP-CODE-REVIEW：代码审查
- qa-lead 跑 QL-TEST-COVERAGE：测试覆盖够吗

**`/code-review`** —— 架构级审查。引擎专家（主专家 + 按文件类型加语言/着色器/UI 专家）**并行**派，Logic/Integration 故事再加 qa-tester 查可测性。

**跨领域功能** → 用 2.3 的 team 技能。

### Phase 6 打磨：从"能用"到"好玩"

**`/playtest-report`** —— 试玩报告。creative-director 跑 CD-PLAYTEST：只有创意总监能裁决"这游戏好玩吗"这个终极问题。

**`/team-polish "系统名"`** —— 六专家并行打磨：performance-analyst 先剖析瓶颈出优化清单，engine-programmer/tools-programmer 照单修，technical-artist + sound-designer 做表现，qa-tester 边缘测试。

**`/security-audit`** —— security-engineer 全权审计（技能明说"审计是它的工作，主会话不要自己跑"）。

**`/localize src/`** —— localization-lead 查文化敏感度 + 提取字符串。

### Phase 7 发布：上市

**`/team-release`** —— 大部队：release-manager（部署）、qa-lead（签收）、devops-engineer（构建管线）、security-engineer（安全）、analytics-engineer（遥测）、community-manager（公告）、producer（Go/No-Go 拍板）。多人游戏加 network-programmer 签网络稳定。

**`/hotfix "问题"`** —— 线上救火：lead-programmer（审修复）、qa-tester（回归测试）、producer（批部署时机）。

## 4. 设计哲学：为什么这样映射（初学者必读）

### 规则 1：按职责匹配，不按级别堆砌

不是"越重要的活派越高级的智能体"。派谁只看**这个活是谁的职责**：
- 切范围 → producer（哪怕它是 Tier 1 总监）
- 验公式 → systems-designer（哪怕它是 Tier 3 专家）
- 裁决"好玩吗" → creative-director（只有总监有裁决权）

### 规则 2：产出方和审查方分开

GDD 是 game-designer 参与写的，但 `/design-review` 还要派 systems-designer 复核公式 + creative-director 终审。**自己不审自己**——多智能体体系的制衡核心。

### 规则 3：门禁 = 派有裁决权的人

门禁 ID 前缀就是"谁来查"（CD-/TD-/PR-/AD-/LP-/QL-/ND-）。总监能 APPROVE/REJECT，因为它们在组织层级里有这个权力设定。这继承自真实工作室的组织结构。

### 规则 4：独立上下文 = 专业深度

每个智能体在自己的上下文窗口里工作，看不到主会话的杂音，只收到技能打包的"工作简报"。这就是为什么同样一个问题，派专家比主会话自己想更准——专家的全部注意力都在这一件事上。

### 规则 5：主智能体 + 辅助智能体

复杂任务从来不是一个人扛。写战斗 GDD：game-designer 主笔，systems-designer 管公式，ai-programmer 管敌人 AI 视角，art-director 管打击感。**主会话当调度员，不当万能选手**。

## 5. 初学者速查：最少需要记住什么

| 技术裁决 | technical-director | map-systems、architecture-*、gate-check |
| 范围裁决 | producer | brainstorm、create-epics、sprint-plan、gate-check |
| 美术方向 | art-director | brainstorm、art-bible、gate-check |
| 系统设计 | game-designer | design-system 主笔、design-review |

| 经济数值 | economy-designer | design-system 辅助 |
| 剧情叙事 | narrative-director | design-system 辅助 |
| 架构落地 | lead-programmer | create-architecture、story-done 审查 |
| 引擎专家 | [你的引擎]-specialist | architecture-decision、dev-story、code-review |
| 实现主力 | gameplay-programmer（+其他程序员按需） | dev-story |
| QA 把关 | qa-lead / qa-tester | create-stories、story-readiness、story-done |
| UX | ux-designer | ux-design、team-ui |
| 性能 | performance-analyst | team-polish |
| 发布 | release-manager | team-release |

其余 34 个是"按需叫"的深专家：引擎子专家（15 个）、音频/关卡/世界观/写作/安全/本地化/运营等——用到对应技能时自然会出现，不用背。

## 6. 一图流总结

```
你敲技能 ──→ 技能按"任务性质"查路由 ──→ 派对应智能体 ──→ 产出数据

Phase 1 概念:  brainstorm ──→ CD+AD+TD+PR 四总监压测概念
              setup-engine ──→ 引擎专家定基调
              map-systems ──→ TD(边界)+PR(优先级)+CD(覆盖)
Phase 2 设计:  design-system ──→ 按系统类型路由(13行表)
              design-review ──→ 专家并行审 + CD 终审
Phase 3 技术:  create-architecture ──→ TD(合理)+LP(可行)
              architecture-decision ──→ 引擎专家(验证)+TD(终审)
              create-control-manifest ──→ TD
Phase 4 预生产: create-epics ──→ PR    create-stories ──→ qa-lead
              sprint-plan ──→ PR     story-readiness ──→ qa-lead
Phase 5 生产:  dev-story ──→ 程序员路由表 + 引擎专家副手
              story-done ──→ LP(代码)+QL(测试)
              code-review ──→ 引擎专家并行 + qa-tester
              team-* ──→ 固定专家班底
Phase 6 打磨:  playtest-report ──→ CD   team-polish ──→ 6 专家
Phase 7 发布:  team-release ──→ 发布班子 + producer 拍板
阶段门:       gate-check ──→ 总监评审团(1-4人,取最严)
```

**一句话**：技能是流程脚本，智能体是职业员工；每个技能在关键步骤"点名"最对口的员工，总监负责裁决，专家负责深度，主会话只当调度员——这就是全部。
