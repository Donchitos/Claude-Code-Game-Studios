# 7 阶段开发流程逐阶指南 —— 输入、上下文、输出、每个文档干什么

依据 [docs/WORKFLOW-GUIDE.md](file:///workspace/docs/WORKFLOW-GUIDE.md)、[workflow-catalog.yaml](file:///workspace/.claude/docs/workflow-catalog.yaml)、[project.yaml](file:///workspace/project.yaml) 整理。

> **给初学者的阅读方式**：先读"0. 必读概念"一节，建立"输入→干活→输出"的基本框架感。然后按需跳读具体阶段。每个阶段里同时有**专业表达**和**初中能懂的讲解**——专业术语加粗标注，括号里是大白话。

## 0. 必读概念：这套流程到底在干什么

### 一句话总结

> 这套流程就是：**先想清楚游戏是什么、再想清楚技术上怎么做、再拆成一个个小任务、再一个个做完、再打磨、再发布**。7 个阶段像 7 道门，过了一道才能进下一道。

### 核心心智模型：输入 → 干活 → 输出

每个阶段都是同一个循环：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   输入文档   │ ──→ │  执行命令    │ ──→ │   输出文档   │
│ （前置条件） │     │ （技能/Skill）│     │ （本阶段产出）│
└─────────────┘     └─────────────┘     └─────────────┘
```

- **输入文档**：要进这个阶段，你手上**必须已经有**的东西。比如 Phase 2 要进 Phase 3，必须先有 GDD。
- **执行命令**：你在 Claude Code 里输入的 `/xxx` 斜杠命令。每个命令背后是一个"技能"（Skill），它会召唤智能体、读文件、帮你写文档/代码。
- **输出文档**：这个阶段干完后**必须有**的东西。没有这些，`/gate-check` 会挡你。

### 什么是"上下文"

每次你跑一个斜杠命令，AI 不是从零开始干活。它会**自动读取**一些文件来"了解情况"——这些文件就是"上下文"。上下文分三类：

| 类型 | 例子 | 谁读 | 什么时候读 |
|------|------|------|-----------|
| **运行时注入** | `@.claude/docs/coordination-rules.md` | AI（自动） | 每次会话启动 |
| **技能主动读** | `/design-system` 主动读你的 game-concept.md | AI（按需） | 跑命令时 |
| **项目配置** | `project.yaml` 的 rigor / engine 设定 | AI（按需） | 跑命令时 |

### Rigor（严格度）：流程的"档位开关"

这套流程有 3 档，决定**哪些步骤是必须的、标准的还是可跳过的**。

| Rigor | 类比 | 什么时候用 | 门禁 |
|-------|------|-----------|------|
| `minimal` | 骑自行车——简单快 | solo 开发者、game jam | 不跑 |
| `standard` | 开车——规范完整 | 大多数独立项目 | 只跑阶段门 |
| `full` | 开飞机——每步都审 | 工作室项目、多人团队 | 每步都跑 |

`/start` 会根据你的描述自动帮你选。之后随时可以用 `/settings modes.rigor=full` 改。

### Gate（门禁）：阶段之间的"守门员"

每两个阶段之间要跑 `/gate-check`。它做的事：

1. 检查你有没有产出物（文件在不在、合不合格）
2. 召唤总监智能体评审（创意/技术/制作/美术四位）
3. 给出判决：PASS / CONCERNS / NOT ASSESSED / FAIL

- **PASS**：过！进下一阶段
- **CONCERNS**：有风险但不拦，你**明确接受风险**才能过
- **NOT ASSESSED**：有些该有的东西 AI 没找到，补了再来
- **FAIL**：不合格，必须解决才能过

> ⚠️ 门禁判决是**建议性**的（ADVISORY），不是硬阻塞。但别滥用——CONCERNS/FAIL 往往意味着真问题。

### project.yaml：整套系统的"大脑"

`project.yaml` 是**项目配置的单一事实源**（Single Source of Truth）。所有技能启动时都会读它，知道"这个项目用什么引擎、严格度几档、总监门禁跑不跑"。`/setup-engine` 会往里面写引擎配置，`/settings` 可以随时改。

## Phase 1：概念（Concept）——"我想做什么游戏"

### 这阶段在干什么（初中版）

> 你脑子里有个模糊想法，比如"我想做个像杀戮尖塔那样的卡牌 roguelike"。Phase 1 就是把这个模糊想法**变成一份写下来的文档**，明确：游戏是什么类型、核心玩法是什么、目标玩家是谁、美术风格是什么、用什么引擎。就像写"商业计划书"——写清楚了才能往下走。

### 输入文档

| 文件 | 性质 | 说明 |
|------|------|------|
| （无） | — | 这是第一道门，理论上什么都不用准备。但如果你脑子里有想法，`/brainstorm` 可以直接用 |

### AI 自动读取的上下文

| 文件 | 性质 | AI 读它干什么 |
|------|------|-------------|
| `project.yaml` | 配置 | 知道 rigor 档位、有没有配引擎 |
| `.claude/docs/coordination-rules.md` | 运行时注入 | 知道协作规则 |
| `.claude/docs/coding-standards.md` | 运行时注入 | 知道文档标准 |
| `.claude/docs/workflow-catalog.yaml` | 技能主动读 | `/help` 读它判断当前阶段 |

### 执行的命令

| 命令 | 干什么 | 必须？ |
|------|--------|--------|
| `/brainstorm` | 引导式头脑风暴，产出概念文档 | ✅ 必须 |
| `/design-review` | 审一下概念文档 | 可选但推荐 |
| `/setup-engine` | 选引擎、钉版本、填命名规范等 | ✅ 必须 |
| `/prototype` | 花 1-3 天做个一次性原型，验证核心机制好不好玩 | 可选但推荐 |
| `/map-systems` | 把概念拆成一个个"系统"（战斗、移动、UI……） | ✅ 必须 |
| `/art-bible` | 写美术圣经（视觉身份规范） | 可选（minimal 档跳过） |
| `/gate-check systems-design` | Phase 1 → Phase 2 的门禁 | standard/full 档必须 |

### 输出文档（按命令自动创建）

| 文件 | 谁创建 | 放在哪 | 作用（专业版） | 作用（初中版） |
|------|--------|--------|---------------|---------------|
| **game-concept.md** | `/brainstorm` | `design/gdd/` | 游戏概念文档：电梯 pitch、核心幻想、MDA 分析、目标玩家、核心循环图、USP、支柱、反支柱 | "这是什么游戏、给谁玩、核心乐趣是什么"的一页纸说明。支柱（Pillars）是最重要的——3-5 条不可协商的设计原则，用来在分歧时拍板 |
| **game-brief.md** | `/brainstorm`（minimal 档） | `design/` | minimal 档的简化概念文档，替代完整的 game-concept.md | minimal 档偷懒版：一页纸说清楚游戏是什么、MVP 做什么、制作顺序 |
| **technical-preferences.md** | `/setup-engine` | `.claude/docs/` | 项目技术配置：引擎、语言、平台、命名规范、性能预算、禁止模式、允许的库、引擎专家路由 | "这个项目用哪个引擎、变量名怎么起、用什么插件"的配置表。初始全是 `[TO BE CONFIGURED]`，`/setup-engine` 填好 |
| **project.yaml** | `/setup-engine` + `/start` | 根目录 | 项目配置单一事实源：rigor 档位、引擎设置、所有 mod | AI 每次干活前读它，知道"这个项目要多正式、用什么引擎" |
| **systems-index.md** | `/map-systems` | `design/gdd/` | 系统索引：列出游戏所有需要的系统、系统之间的依赖图、优先级分层（MVP/垂直切片/Alpha/完整版）、设计顺序（Foundation > Core > Feature > Presentation > Polish） | "我们要做哪些系统、先做哪个后做哪个、谁依赖谁"的清单 |
| **art-bible.md** | `/art-bible` | `design/art/` | 美术圣经：视觉身份规范（9 节）——风格锚点、色彩、字体、材质、光照、参考图、AI 生成提示模板 | "所有美术资产长什么样、统一风格是什么"的规范手册。`/gate-check pre-production` 前要前 4 节，`/gate-check production` 前要全部 9 节 |
| **prototypes/** | `/prototype` | `prototypes/` | 一次性概念原型 + REPORT.md（PROCEED/PIVOT/KILL 判决） | "花 1-3 天验证核心机制好不好玩"的试玩版原型。PROCEED = 进下一阶段，PIVOT = 改设计，KILL = 回到头脑风暴 |

### Phase 1 门禁检查清单

| 检查项 | 要求 |
|--------|------|
| `design/gdd/game-concept.md` | 有内容、有支柱、有 Visual Identity Anchor |
| 或 `design/game-brief.md` | 有内容（minimal 档） |
| 概念原型 | REPORT.md 说 PROCEED（推荐但不阻塞） |

## Phase 2：系统设计（Systems Design）——"每个系统具体怎么玩"

### 这阶段在干什么（初中版）

> 你已经知道游戏是什么了，现在要**把每个系统拆开来想清楚**。比如"战斗系统"——连击窗口是 0.4 秒还是 0.5 秒？暴击公式是什么？血量为 0 时被治疗会怎样？每个系统都写一份详细的"游戏设计文档"（GDD），8 个必填章节。就像写"产品需求文档"——程序员拿到 GDD 才知道具体怎么实现。

### 输入文档

| 文件 | 性质 | 说明 |
|------|------|------|
| `design/gdd/game-concept.md` | 必须有 | Phase 1 输出 |
| `design/gdd/systems-index.md` | 必须有 | Phase 1 输出 |
| `design/art/art-bible.md` | 推荐有 | Phase 1 输出（minimal 档跳过） |

### AI 自动读取的上下文

| 文件 | 性质 | AI 读它干什么 |
|------|------|-------------|
| 上面列的所有输入文档 | 主动读 | `/design-system` 读 concept 和 index 来写 GDD |
| `.claude/docs/templates/game-design-document.md` | 技能主动读 | 按模板格式写 GDD |
| `.claude/docs/templates/game-pillars.md` | 技能主动读 | `/design-review` 审支柱对齐 |
| `project.yaml` | 配置 | 知道 rigor 档位、引擎 |
| `.claude/docs/coding-standards.md` | 运行时注入 | 知道 GDD 必须有 8 节 |

### 执行的命令

| 命令 | 干什么 | 必须？ |
|------|--------|--------|
| `/map-systems next` | 从 systems-index 挑下一个该写的系统 | ✅ 每个系统跑一次 |
| `/design-system [系统名]` | 引导式写一份 GDD，一节节协作 | ✅ 每个 MVP 系统跑一次 |
| `/design-review [GDD路径]` | 审单个 GDD 的 8 节完整性 | ✅ 每个 GDD 跑一次 |
| `/quick-design "[描述]"` | 小改动的轻量设计规范，不写完整 GDD | 可选（小调整用） |
| `/review-all-gdds` | 所有 MVP GDD 写完后，跨文档一致性 + 设计理论 holistic 审查 | ✅ 必须 |
| `/consistency-check` | 扫所有 GDD 找矛盾（两个文档对同一数值写不同值） | 可选 |
| `/gate-check technical-setup` | Phase 2 → Phase 3 的门禁 | standard/full 档必须 |

### 输出文档（按命令自动创建）

| 文件 | 谁创建 | 放在哪 | 作用（专业版） | 作用（初中版） |
|------|--------|--------|---------------|---------------|
| **[系统名].md** | `/design-system` | `design/gdd/` | 单个系统的游戏设计文档，8 节：Overview / Player Fantasy / Detailed Rules / Formulas / Edge Cases / Dependencies / Tuning Knobs / Acceptance Criteria + Game Feel 节 | "这个系统具体怎么玩、怎么算、边界情况怎么处理、怎么验证做对了"的详细说明书。程序员拿到就能实现，不用猜 |
| **gdd-cross-review-[日期].md** | `/review-all-gdds` | `design/gdd/` | 跨 GDD 审查报告：Phase 1（一致性：依赖双向、规则无矛盾、所有权无冲突、公式范围兼容）+ Phase 2（设计理论：竞争循环、认知负荷、统治策略、经济平衡、难度曲线、支柱对齐、幻想连贯） | "所有 GDD 放在一起看有没有矛盾"的审查报告。比如"战斗系统输出的伤害值，能不能被受伤系统正确接收" |
| **systems-index.md**（更新） | `/design-system` / `/map-systems` | `design/gdd/` | 随着 GDD 写完更新状态（Draft → Approved） | 原来 Phase 1 创建的索引，现在更新每个系统的设计状态 |
| **quick-specs/** | `/quick-design` | `design/quick-specs/` | 小改动的轻量设计规范 | "改个数值、加个小特性"不用写完整 8 节 GDD，写个短的就行 |

### Phase 2 门禁检查清单

| 检查项 | 要求 |
|--------|------|
| `design/gdd/systems-index.md` | 至少列了 MVP 系统，有依赖图 |
| 每个 MVP 系统的 GDD | 都通过了 `/design-review`（无 MAJOR REVISION NEEDED） |
| 跨 GDD 审查报告 | 判决不是 FAIL，也不是 NOT ASSESSED |

## Phase 3：技术搭建（Technical Setup）——"技术上怎么做"

### 这阶段在干什么（初中版）

> 设计文档写完了，现在要**想清楚技术上怎么实现**。比如"NPC AI 用状态机还是行为树？""多人同步用 RPC 还是属性复制？"每个技术决策写一份"架构决策记录"（ADR），记清楚"为什么选这个、放弃了什么、有什么后果"。还写一份"程序员规则清单"，告诉程序员该用什么模式、禁什么模式。就像写"施工方案"——设计图有了，施工方案也要有。

### 输入文档

| 文件 | 性质 | 说明 |
|------|------|------|
| Phase 1 所有输出 | 必须有 | game-concept / technical-preferences / systems-index |
| Phase 2 所有输出 | 必须有 | 所有 GDD（Approved 状态）、跨 GDD 审查报告 |
| `design/art/art-bible.md` | 推荐有 | 美术圣经 |

### AI 自动读取的上下文

| 文件 | 性质 | AI 读它干什么 |
|------|------|-------------|
| 上面列的所有输入文档 | 主动读 | `/create-architecture` 读所有 GDD 和 systems-index |
| `.claude/docs/templates/architecture-decision-record.md` | 技能主动读 | 按模板格式写 ADR |
| `.claude/docs/templates/accessibility-requirements.md` | 技能主动读 | `/ux-design accessibility` 按模板写 |
| `.claude/docs/technical-preferences.md` | 运行时注入 | 知道引擎、命名、禁止模式 |
| `.claude/docs/coding-standards.md` | 运行时注入 | 知道代码标准 |
| `.claude/docs/director-gates.md` | 技能主动读 | `/architecture-decision` 按门禁 ID 取 prompt |

## Phase 4：预制作（Pre-Production）——"写故事、做垂直切片、规划冲刺"

### 这阶段在干什么（初中版）

## 跨阶段概念

### 三种 Rigor 档位的完整差异

| 维度 | minimal（默认） | standard | full |
|------|----------------|----------|------|
| 流程要多完整 | 四步到代码 | 完整 7 阶段 | 完整 7 阶段 |
| GDD 深度 | game-brief.md（一页纸） | 8 节完整 GDD | 8 节完整 GDD + Game Feel |
| 总监门禁 | solo（全跳过） | lean（只跑阶段门） | full（每步都跑） |
| QA 严格度 | 冒烟测试 | 完整测试计划 | 完整测试计划 + 回归 + soak |
| 故事粒度 | 可以很粗 | 1-3 天一个 | 1-3 天一个 + READY 检查 |

### 三种 Review Mode 的差异

| Mode | 跑什么 | 什么时候用 |
|------|--------|-----------|
| `solo` | 不跑任何总监评审 | solo 项目、game jam |
| `lean` | 只在阶段转换跑 `/gate-check` | 大多数独立项目 |
| `full` | 每步技能都跑总监门禁 | 工作室项目、多人团队 |

### 两种原型的区别

| | `/prototype`（Phase 1） | `/vertical-slice`（Phase 4） |
|--|------------------------|------------------------------|
| 目的 | 验证**核心机制好不好玩** | 验证**整套管线能不能产出可玩的东西** |
| 质量 | 一次性、可以很粗糙 | 生产质量、用真实架构层 |
| 时长 | 1-3 天 | 更长 |
| 判决 | PROCEED / PIVOT / KILL | PROCEED / PIVOT / KILL |
| 关系 | 回答"好玩吗" | 回答"能做出来吗" |

## 常见误区

**误区 1："我跳过 Phase 1-4，直接写代码，大不了以后补文档。"**
❌ 危险。后期补文档**没有"逼你想清楚"的价值**——写 GDD 的过程逼你想边界情况、公式、依赖；事后补只是"记录已做的"。`/reverse-document` 是给遗留代码的补救，不是推荐流程。

**误区 2："minimal 档就是'什么都不做'。"**
❌ minimal 档是"**最简**的必须步骤"——4 步到代码：`/setup-engine` → `/brainstorm`（产出一页纸 game-brief.md，替代完整概念+GDD）→ `/create-stories`（从 brief 的 MVP 列表拆）→ `/dev-story` + `/story-done` 一个个做。不是零步骤，是最简步骤。

**误区 3："gate-check 不过就不能往下走，AI 会强制拦我。"**
❌ 门禁判决是**建议性**的（ADVISORY），不是硬阻塞。但 FAIL 判决意味着真问题，强行 CONCERNS 通过是接受了风险。正确做法是解决问题让判决变 PASS。

**误区 4："我改了 GDD，故事文件会自动更新。"**
❌ 不会。GDD 改了后必须跑 `/propagate-design-change [GDD路径]`，它会 diff GDD 变更、找受影响的 ADR 和故事、生成影响报告。

**误区 5："minimal 档永远用着，不需要升档。"**
⚠️ 当游戏出了 3+ 个交互系统、设计要给别人实现、有多人团队、有固定发布日期——就该升 `standard`。现有文件保持不变，`/help` 会告诉你新档位要求什么。

**误区 6："我不做垂直切片，直接进生产。"**
⚠️ 可以（门禁标 CONCERNS），但风险大——到 Phase 5 才发现核心循环不好玩或某系统根本做不出来，沉没成本巨大。

**误区 7："rigor 和 review_mode 是一回事。"**
❌ 不是。rigor 控制"**需要哪些文档和步骤**"（流程完整度）；review_mode 控制"**总监门禁跑不跑**"（评审严格度）。可以 minimal 档但 full 门禁，也可以 full 档但 solo 门禁。两者独立但 rigor 会**推断一个默认值**。
