# 回填（Retrofit）与哈希重跑机制 —— "设计改了之后，怎么知道哪些东西过期了？"

> **一句话总览**：设计文档不是写完就一劳永逸的——它会改。这个项目用两套机制应对"改"：**回填（retrofit）** 负责"补窟窿不拆房子"（只填缺失的章节，绝不碰已写好的内容），**内容哈希回执** 负责"给文件按指纹"（评审过的文件被改动了指纹就变，系统立刻知道该重新跑哪个评审）。两者合起来构成一个闭环：**改设计 → 指纹变了 → 依赖它的评审/证据自动过期 → 只重跑真正需要的部分 → 补好的内容回填进下游**。

依据 [review-receipts.sh](file:///workspace/.claude/scripts/review-receipts.sh)、[design-review/SKILL.md](file:///workspace/.claude/skills/design-review/SKILL.md)、[design-system/references/1-parse-arguments.md](file:///workspace/.claude/skills/design-system/references/1-parse-arguments.md)、[ux-design/references/2-gather-context.md](file:///workspace/.claude/skills/ux-design/references/2-gather-context.md)、[consistency-check/SKILL.md](file:///workspace/.claude/skills/consistency-check/SKILL.md)、[dev-story/SKILL.md](file:///workspace/.claude/skills/dev-story/SKILL.md)、[story-done/SKILL.md](file:///workspace/.claude/skills/story-done/SKILL.md)、[hooks-reference.md](file:///workspace/.claude/docs/hooks-reference.md) 整理。

## 0. 先把你听到的这句话翻译成项目里的两件事

你听到的是："系统设计会导致回填、哈希值变了要重新跑"。这句话在项目里对应**两个独立的机制**，它们经常一起被提到，因为它们解决的是同一个问题的两面——"**设计文档会变**"：

| 你听到的 | 项目里的真名 | 解决什么 |
|----------|--------------|----------|
| "系统设计会导致回填" | **Retrofit 模式**（`/design-system retrofit`、`/ux-design`、`/art-bible`、`/architecture-decision` 都有）+ QA 测试用例回填 + 注册表回填 | 设计文档后来要补内容 / 设计改了之后下游文档要跟着改 |
| "哈希值变了要重新跑" | **内容哈希回执**（[review-receipts.sh](file:///workspace/.claude/scripts/review-receipts.sh)，被 `/design-review`、`/story-done`、`/test-evidence-review` 等消费） | 怎么**发现**"文件被改过了"，从而判断旧的评审结论/测试证据还能不能用 |

**为什么要一起讲**：它们是同一个闭环的两半。回填负责"改了之后怎么补"，哈希负责"改了之后怎么被发现"。只讲一半，你就理解不了为什么 AI 有时候"复用旧结论"、有时候又"坚持重新评审"。

## 1. 初中生版：两套机制的日常类比

### 1.1 哈希回执 = 体检报告上的"抽血日期封条"

想象你去体检：

1. 医生抽了你一管血，化验后出报告。报告上贴了个**封条**，写着："本报告基于 11 月 1 日的那管血"。
2. 一周后你想复用这份报告。医生不会凭记忆说"应该还能用吧"，而是**再抽一管血对比**——身体没变（指纹一致），报告继续有效；身体变了（指纹不一致），报告作废，重新化验。

项目里的做法一模一样：

- "抽血" = 评审一个文件时，算出这个文件内容的**哈希值**（可以理解为"内容指纹"——同样 20 个字，指纹相同；改 1 个字母，指纹就完全不同）。
- "封条" = 把指纹写进一张**回执**（receipt），比如 `design/gdd/reviews/combat-system-review-log.md` 评审日志里的一行 `Reviewed-Content-Hash: design/gdd/combat-system.md abc123...`。
- "下次复用前对比" = 再跑一次指纹计算，和封条上的比对。

**初中生版核心结论**：哈希机制回答的问题是——"**这份结论还是基于眼前的内容吗？**"

### 1.2 回填 = 老房子翻新

想象一栋老房子要翻新：

- 有的房间已经装修好了（GDD 里已写完的章节）；
- 有的房间还是毛坯（写着 `[To be designed]` 占位符的章节）。

翻新队（retrofit 模式）进场后：

1. 先逐个房间检查，列出清单："✓ 客厅装修好了（不动）/ ✗ 厨房是毛坯（要补）"；
2. 给你确认："要补这 3 个毛坯房吗？**我绝不改动任何已装修的部分**"；
3. 只对毛坯施工。

**初中生版核心结论**：回填机制回答的问题是——"**文档不是一次写完的，怎么安全地补？**"

## 2. 机制一：哈希回执（review-receipts.sh）

### 2.1 为什么不用现成的工具？（脚本自己解释了原因）

[review-receipts.sh](file:///workspace/.claude/scripts/review-receipts.sh#L4-L14) 开头的注释是一段很值得读的工程论证——为什么不比较"文件的修改时间"，也不用 git 来判断？因为各有致命缺陷：

| 方案 | 缺陷 | 后果 |
|------|------|------|
| **git diff** | 依赖用户的提交习惯：没 commit 的改动 diff 看不到（取决于基线） | 漏检 |
| **文件修改时间（mtime）** | 备份恢复、云盘同步会"把旧时间戳配上新内容" | **旧内容配上新指纹时间 → 逃过评审 = 漏检（最危险的方向）** |
| **内容哈希** | 几乎没有：内容变 ⇔ 哈希变，一一对应 | 失败方向只有"误报"（把没变的当成变了，多花一次评审的 token），**永远不会漏检** |

这里的工程思想值得记住：**两种失败方向不对称——"多跑一次评审"浪费的是钱，"漏跑一次评审"放进的是 bug。宁可浪费钱，不可冒风险。**（"fail safe 而非 fail open"）

### 2.2 哈希怎么算的

脚本优先用 `git hash-object`（稳定、内容寻址、不看时间戳），没有 git 就退回 `sha1sum`/`shasum`（见 [hash_file 函数](file:///workspace/.claude/scripts/review-receipts.sh#L124-L133)）。一个细节：两种工具算出的指纹**长得不一样**（git 会在内容前加一个头），所以"用工具 A 打的封条、用工具 B 验"会读出 CHANGED——这个失败方向也是安全的（多跑一次评审），注释原话："That failure direction is safe (re-review)"。

### 2.3 四个子命令：打封条、验封条、章节级打封条、章节级验

| 命令 | 干什么 | 类比 |
|------|--------|------|
| `hash <文件...>` | 算指纹，输出 `Reviewed-Content-Hash: <路径> <指纹>` 行，由调用方粘贴进评审报告 | 抽血、贴封条 |
| `check <回执> [文件...]` | 把当前指纹和回执里**最新的**指纹对比，逐文件报 UNCHANGED / CHANGED / NEW / GONE / UNRESOLVED | 再抽血、验封条 |
| `sections-hash <文件>` | 按 `##` 章节**分别**算指纹 | 分科目化验（血常规、尿常规各一张单） |
| `sections-check <回执> <文件>` | 逐章节对比，报 SECTION-CHANGED / SECTION-UNCHANGED 等 | 看哪一科变了重验哪一科 |

**接收方是"追加日志"**：回执文件只增不改，同一个路径出现多次时**以最后一次为准**（"The LATEST stamp wins"，[第 91-92 行](file:///workspace/.claude/scripts/review-receipts.sh#L91-L92)）——就像体检档案每次化验 appended 一页，看最新的那页。

### 2.4 check 的五种输出（把这张表记住）

| 输出 | 含义 | 类比 |
|------|------|------|
| `UNCHANGED: <路径>` | 当前指纹 = 封条上最新的指纹 | 身体没变，旧报告有效 |
| `CHANGED: <路径>` | 指纹对不上 | 身体变了，旧报告作废 |
| `NEW: <路径>` | 回执里压根没有这个路径的封条 | 新项目，从没化验过 |
| `GONE: <路径>` | 封条盖过它，但文件现在不存在了（被删/被移走） | 当时化验过，现在样本丢了——必须追查 |
| `UNRESOLVED: <路径>` | 你给的是一个**通配符**（如 `design/gdd/*.md`），shell 没展开它 | 医生说"把所有化验单拿来看"，结果一张都没拿来——这和"没有需要化验的"是两回事，必须报出来 |

三个容易忽略但很关键的设计（都在脚本头注释里）：

1. **回执同时也是清单**（[第 25-29 行](file:///workspace/.claude/scripts/review-receipts.sh#L25-L29)）：`check` 不只对比调用方点名的文件，还会把回执盖过章的**每一个**文件都验一遍。因为上一次评审实际读过的文件，可能比这次调用方记得的更多——注释里说这正是 `/architecture-review` 曾经"站在旧报告上却经历了引擎升级"的事故根源，修法就是让回执自己当清单。
2. **一个刻意的例外**（[第 16-23 行](file:///workspace/.claude/scripts/review-receipts.sh#L16-L23)）：字面写出的路径如果回执从没盖过章，`check` **保持沉默**不报 NEW——因为调用方可能每次都点名一个**可选输入**（`/design-review` 就这样点名实体注册表 `design/registry/entities.yaml`，它可以是空的）。沉默是宽容，不是漏洞。
3. **调用方必须把 UNRESOLVED / GONE 当作"不许跳过"**（[第 68-70 行](file:///workspace/.claude/scripts/review-receipts.sh#L68-L70)）：这两种情况说明"你想对比的集合"和"实际对比的集合"不一致，任何"全部 UNCHANGED 就复用旧结论"的捷径在这里都被禁止。

### 2.5 谁在用这套机制？（4 个消费场景）

| 场景 | 打章（hash） | 验章（check） | 指纹变了之后发生什么 |
|------|--------------|----------------|---------------------|
| **设计评审复用**：`/design-review` | 评审完把相关文件指纹写进 `design/gdd/reviews/[文档名]-review-log.md` | 下次评审**第一件事**就是验章（"Freshness check first"） | 见 2.6 的三分支决策树 |
| **测试证据保鲜**：`/dev-story` | 跑完游戏截图后，把**故事改过的每个文件**的指纹盖进 `production/qa/evidence/[story-slug]/stamp.txt`（[dev-story 第 240 行](file:///workspace/.claude/skills/dev-story/SKILL.md#L240)，规范见 [run-and-observe.md](file:///workspace/.claude/docs/run-and-observe.md#L44)） | `/story-done` 结项时验章（[第 171 行](file:///workspace/.claude/skills/story-done/SKILL.md#L171)） | 有 CHANGED → "证据是在代码改动**之前**截的图，重新截图" |
| **证据批量审查**：`/test-evidence-review` | （消费 dev-story 留下的章） | 逐故事验章 | CHANGED/GONE 的文件列为 POTENTIALLY STALE——注意：**只作为报告行，不改判故事结论**（[第 218-224 行](file:///workspace/.claude/skills/test-evidence-review/SKILL.md#L218-L224)） |
| **会话日志去重**：`session-stop.sh` 钩子 | 记录 active.md 的指纹 | 每次响应结束时对比 | 指纹没变就不重复归档——没有这个守卫，长会话每一轮都会把整个文件重复追加一遍（[hooks-reference.md 第 18 行](file:///workspace/.claude/docs/hooks-reference.md#L18)） |

### 2.6 核心消费方：/design-review 的三分支决策树

这是理解"哈希值变了要重新跑"最完整的地方。[design-review/SKILL.md 第 50-102 行](file:///workspace/.claude/skills/design-review/SKILL.md#L50-L102) 规定：评审一个 GDD 之前**先验章**，然后按结果走三条路：

```
                  验章结果
                     │
     ┌───────────────┼─────────────────────────┐
     ▼               ▼                         ▼
 [分支1]          [分支2]                   [分支3]
全部 UNCHANGED   目标文档和技能自身      目标文档或技能自身
且旧评审覆盖      UNCHANGED，只有        CHANGED / NEW，
本次运行的档位    注册表等跨文档          或 RECEIPT: NONE
     │           文件变了                   │
     ▼               ▼                      ▼
 直接复用旧判决   旧判决大体成立，         全量重新评审
 （问用户：用旧的  但要重新核对受          （并且明令禁止
 还是重新评？）   影响的跨文档事实；       只重读"变了的
                 出现冲突则升级为          章节"这种省事做法）
                 全量重审
```

三个要点：

1. **"覆盖"判断**：旧评审要能复用，除了文件没变，其评审深度（full > lean > solo）和工作流档位（full > standard > minimal）还得**不低于**这次要求的档位。浅评审的结论不能冒充深评审——就像体检套餐里没做的项目不能说"合格"。
2. **连自己也要验**：检查清单里包含 `.claude/skills/design-review/SKILL.md` 自身的指纹——"技能文件变了，评审方式就变了"，旧结论自然不可信。
3. **禁止"章节级偷懒"**：分支 3 明确写着 **不要** 提议"只重审没变的章节之外的差异部分"（Do not offer a partial/delta re-review）——因为"没变"只说明字节和上次一样，不说明上次的评审本身是全面的；而且人的注意力会不自觉地缩到被标记的变化上。注意这与 `sections-hash` **不矛盾**：章节级指纹是为"哪一科变了"提供**事实**，但**要不要因此偷懒**由技能的规则决定——而这个技能的答案是"内容级变更不许偷懒"。

### 2.7 脚本只报事实，不做决定

[review-receipts.sh 第 36-39 行](file:///workspace/.claude/scripts/review-receipts.sh#L36-L39)：脚本只输出 `UNCHANGED / CHANGED / NEW / RECEIPT: NONE` 这些**事实**，从不输出"通过/不通过"这类**判决**。判决由调用它的技能根据规则做出（包括结合 automation 模式决定问不问用户）。

这就是 [CLAUDE.md](file:///workspace/CLAUDE.md) 的"观察者约定"（observation-only convention）：**机制层报事实，策略层做决定**。好处是同一个脚本可以被不同技能以不同策略消费——`/design-review` 拿它决定"要不要重审"，`/story-done` 拿它决定"证据要不要重采"，互不干扰。

## 3. 机制二：回填（Retrofit / Backfill）

"回填"在项目里实际有三个用途，共享同一个思想：**增量更新，绝不推倒重来**。

### 3.1 用途一：Retrofit 模式——给设计文档"补窟窿"

触发方式：`/design-system retrofit design/gdd/[文件名].md`，或者直接传一个已存在的 GDD 路径（[1-parse-arguments.md 第 44-84 行](file:///workspace/.claude/skills/design-system/references/1-parse-arguments.md#L44-L84)）。七步流程：

1. 按章节读现有 GDD；
2. 盘点 8 个章节哪些在场、哪些缺失、哪些只是 `[To be designed]` 占位符（且**按当前档位判断**哪些算"必须补的缺口"，哪些只是"可以选补"——`standard` 档位下 Player Fantasy 和 Tuning Knobs 本来就设计为跳过，不算缺口）；
3. 列清单给用户看：✓ 已写好的（不会碰）/ ✗ 缺失或不完整的（将要写）；
4. 问："要补这 N 个缺失章节吗？**我不会修改任何已有内容。**"；
5. 确认后走正常流程，但跳过建骨架（文件已存在）、跳过已完成的章节；
6. 只用 Edit 工具替换占位符或空章节体；
7. **铁律：绝不覆盖已有章节内容。**

同样的检测逻辑也内建于其他写作型技能（不给 retrofit 参数、发现目标文件已存在也自动进入）：

- [ux-design 的 retrofit 检测](file:///workspace/.claude/skills/ux-design/references/2-gather-context.md#L147-L189)：先给一张"每章节状态表"（Complete / Empty / Placeholder），然后只写 Empty 和 Placeholder 的；
- [art-bible 的 retrofit 检测](file:///workspace/.claude/skills/art-bible/SKILL.md#L57)；
- 棕地项目（老项目接入 CCGS）的整条路线就是靠 retrofit 拼起来的：`/design-system retrofit`、`/architecture-decision retrofit` 把**已有**的 GDD/ADR 按 CCGS 标准补齐（[start-paths.md 第 37 行](file:///workspace/.claude/docs/templates/start-paths.md#L37)、[adopt 迁移计划](file:///workspace/.claude/skills/adopt/references/4-migration-plan.md#L27-L32)）。

**为什么这个铁律重要**：已写好的章节是**用户批准过的产出**（每个章节写完都经过"展示→你决定→写入"循环）。静默重写它 = 推翻你已经做过的决定。Retrofit 把"补"和"改"严格分开：补可以自动干，改必须走明示流程。

### 3.2 用途二：QA 测试用例回填——把测试规格写回故事文件

`/qa-plan` 生成冲刺测试计划时，会问你是否**回填**（backfill）各故事文件的 `## QA Test Cases` 节（规则见 [skill-rules/qa-plan.md R18/R19](file:///workspace/study-docs/workflow/skill-rules/qa-plan.md)）：

- 回填后，`/dev-story` 和 `/code-review` 实现故事时能**就地**看到自己的测试规格，不必跳回冲刺计划找；
- 没有 `## QA Test Cases` 节的故事，节会被追加在 `## Test Evidence` 之前。

这是"回填"的另一面：不只是"补缺失"，还有"把上游产出物**投射**到下游文件里，方便就地消费"。

### 3.3 用途三：设计变更传播——老 GDD 回填新决策

这是和哈希机制联动最紧的一环。设计决策经常**倒着生效**：你先设计了战斗系统，后来设计经济系统时发现需要战斗掉落遵循新的定价规则——于是"较老"的战斗 GDD 需要吸收"较新"的决策。项目里有三道防线：

| 防线 | 谁负责 | 干什么 |
|------|--------|--------|
| **评审关卡** | `/gate-check` 的 Technical Setup 门禁 | 检查"No stale GDD references flagged (older GDDs updated to reflect decisions made in later GDDs)"——显式要求老 GDD 回填新决策（[gate-technical-setup.md 第 19 行](file:///workspace/.claude/skills/gate-check/references/gate-technical-setup.md#L19)） |
| **一致性检查** | `/consistency-check` | 用 `design/registry/entities.yaml` 注册表对比所有 GDD 中的实体/公式/常量。发现"源 GDD 改了、注册表没跟上"就分类为 ⚠️ **STALE REGISTRY**（[第 213 行](file:///workspace/.claude/skills/consistency-check/SKILL.md#L213)）；发现两个 GDD 对同一实体写了不同值就是 🔴 **CONFLICT**（[第 211 行](file:///workspace/.claude/skills/consistency-check/SKILL.md#L211)）。注册表里 `source:` 字段标明谁是权威所有者，冲突时**改非权威方**，而不是和稀泥（[第 200-208 行](file:///workspace/.claude/skills/consistency-check/SKILL.md#L200-L208)） |
| **跨文档复核** | `/design-review` 的哈希验章 | 上一节分支 2：目标 GDD 没变、但注册表或关联 GDD 变了 → 重新核对跨文档事实 |

修复注册表条目时还有一条好习惯（[第 286-289 行](file:///workspace/.claude/skills/consistency-check/SKILL.md#L286-L289)）：更新值、写 `revised:` 日期，并加一条 YAML 注释 `# was: [旧值] before [日期]`——**改了什么、从哪改来，永远可追溯**。

## 4. 两个机制如何咬合成闭环

把两部分拼起来看，"设计改了之后"发生的事是一个完整循环：

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 设计变更：/design-system 补章节（回填）或改公式               │
│                        │                                        │
│                        ▼                                        │
│  2. 指纹自动失效：GDD 内容变了 → 哈希变了                        │
│     （不需要任何人"记得通知"下游——指纹对比天然发现）             │
│                        │                                        │
│                        ▼                                        │
│  3. 下游自动过期：                                              │
│     · /design-review 验章 → CHANGED → 不复用旧判决，重新评审     │
│     · 已实现故事的证据 stamp → CHANGED → /story-done 要求重截图  │
│     · 注册表 source 指向它 → /consistency-check 报 STALE         │
│                        │                                        │
│                        ▼                                        │
│  4. 变更传播（回填的另一面）：                                   │
│     · 注册表更新（带 # was: 注释）                               │
│     · referenced_by 的兄弟 GDD 按需更新                          │
│     · 受影响故事重开或补测试                                     │
│                        │                                        │
│                        ▼                                        │
│  5. 重新评审通过 → 新指纹写入新回执 → 闭环回到"可复用"状态        │
└─────────────────────────────────────────────────────────────────┘
```

**背后统一的软件工程原理有三条**：

1. **单一事实源 + 派生物必过期**：GDD 和注册表是事实的"原件"，评审判决、测试证据、兄弟 GDD 都是"复印件"。原件一改，复印件自动不可信——而检测手段不是"人记得"，是哈希指纹。
2. **检测的失败方向要设计**：宁可误报（多跑一次评审，费 token）不可漏报（拿着过期结论往下走，出 bug）。脚本所有边角情况（无哈希工具、工具混用、回执缺失、glob 未展开）全都倒向误报一侧。
3. **增量优于重造**：回填让"改"不必付出"全部重来"的代价——但增量是**受控的**增量：只补占位符、绝不覆盖已批准内容、改注册表留旧值注释。

## 5. 术语表（专业说法 + 命名语义）

| 术语 | 字面含义 | 在这个项目中的确切意思 |
|------|----------|----------------------|
| **Retrofit** | retro-（向后）+ fit（装配），"给老物件加装新部件" | 给**已存在**的设计文档补齐缺失/占位章节，不碰已有内容。`/design-system retrofit`、`/architecture-decision retrofit`、`/adopt` 都用它 |
| **Backfill** | back（回）+ fill（填），"往回填" | 同一件事的另一个词：把内容**补进已存在的文件**。QA 用例写回故事文件也叫 backfill |
| **Hash（哈希）** | 把任意内容压成一个固定长度的"指纹"，内容变指纹必变 | `git hash-object` 或 SHA-1 算出的文件内容指纹，用来检测"评审之后文件有没有被改过" |
| **Receipt（回执）** | 收据、凭证 | 存放指纹的文件（评审日志 / stamp.txt）。名字取得很准：它是"某次评审**收下过**这些文件"的凭证 |
| **Stamp（盖章）** | 盖章 | `hash` 子命令输出指纹行的动作；名词用法指 stamp.txt 这类指纹文件 |
| **Freshness（新鲜度）** | 食材是否新鲜 | "评审结论是否还基于当前内容"。`/design-review` 的 Phase 1 第一步就叫 freshness check |
| **Stale（过期）** | 食物放久了 | 一切"基于旧内容产出、但内容已变"的产物：stale GDD、stale registry entry、POTENTIALLY STALE evidence |
| **Append-only log** | 只增不改的日志 | 回执文件的形态：每行盖章记录只追加不修改，同一路径以最后一次为准 |
| **LATEST stamp wins** | 最新盖章胜出 | 同一路径在回执里出现多次时，check 只对比**最后一次**的指纹 |
| **`[To be designed]`** | 占位符 | GDD 骨架里空章节的标准占位文本；retrofit 靠识别它来定位"要补的窟窿" |
| **Observation-only** | 只观察不动手 | 脚本只报事实（UNCHANGED/CHANGED...），判决由调用技能按规则做出 |
| **STALE REGISTRY vs CONFLICT** | 过期注册 vs 冲突 | `/consistency-check` 的两个严重度：注册表落后于源 GDD（改注册表即可）vs 两个 GDD 值不同（必须裁决谁对） |

## 6. 常见误区

1. **"哈希变了 = 内容错了"**。不对。哈希只告诉你"内容**变**了"，不判断变好还是变坏。改一个错别字哈希也变。它的作用是**触发复核**，不是**否定内容**。
2. **"全部 UNCHANGED 就能无脑复用旧判决"**。还要满足两个条件：旧评审的档位**不低于**本次要求（浅评审不能冒充深评审），且没有 UNRESOLVED / GONE 行（对比集合不完整时禁止走捷径）。
3. **"有 sections-hash，评审就能只看变的章节"**。`/design-review` 明令禁止内容变更后的"差异式重审"——章节指纹提供事实，策略上仍然全量重审；"没变"不等于"上次审得全面"。
4. **"Retrofit 会帮我顺便改进已写的章节"**。不会，也**不允许**。铁律是"绝不覆盖已有内容"；要改已有内容，走正常的修改 + 重新评审流程。
5. **"回执不存在 = 出错了"**。不是。`RECEIPT: NONE` 是合法状态（比如第一次评审前），只是意味着"没有可比对的基准"，各技能按自己的规则降级处理（有的全按 NEW，有的退回日期检查）。
6. **"retrofit 只能用 retrofit 参数触发"**。不一定。多个写作技能检测到目标文件**已存在**就自动进入回填模式；`retrofit` 参数是显式触发方式。
7. **"STALE REGISTRY 很严重，说明设计错了"**。恰恰相反——它说明**注册表落后了**，源 GDD 可能完全正确。处理方式只是把注册表条目更新到和源 GDD 一致；真正严重的是 🔴 CONFLICT（两个 GDD 打架，必须裁决）。

## 7. 小测验（答案都在上文）

**Q1**：为什么项目用内容哈希而不是文件修改时间来判断"评审后文件改没改"？

> 答案：mtime 会被备份恢复、云同步"骗"到——旧时间戳配上新内容就逃过检测，这是**漏检**（危险方向）。哈希只看内容本身：内容变 ⇔ 哈希变。它的失败方向最多是误报（多跑一次评审），安全得多。

**Q2**：`/design-review` 验章后，"目标 GDD 没变、但实体注册表变了"走哪个分支？为什么注册表也要参与验章？

> 答案：分支 2——旧判决大体成立，但要重新核对该 GDD 的数值与已变更注册表是否冲突，出现冲突升级为全量重审。注册表参与验章是因为评审要用它核对跨文档事实："没变的 GDD 对照**变了**的注册表，可能得出不同的结论"。

**Q3**：retrofit 模式为什么"绝不覆盖已有章节"？在 `standard` 档位下，缺失 Player Fantasy 章节会被当成缺口吗？

> 答案：因为已有章节是用户逐节批准过的产出，静默重写等于推翻已做的决定——回填和修改必须严格分开。`standard` 档位下 Player Fantasy 和 Tuning Knobs **设计为跳过**，缺失不算缺口，只会列为"可补选项"。
