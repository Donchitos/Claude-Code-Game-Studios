# bug-triage — 开放 bug 重新分诊（AGENTS.md 移植版）

> 来源：[SKILL.md](file:///workspace/.claude/skills/bug-triage/SKILL.md) ｜ 阶段：Phase 5+ ｜ 移植目标：其它项目的 AGENTS.md / CLAUDE.md / skill 定义

## 1. 技能定位
- **命令**：`/bug-triage [sprint | full | trend]`
- **一句话职责**：把开放 bug 积压处理成**已排优先级、已分派冲刺**的行动清单——区分 severity（影响多坏）与 priority（多急着修）、检测系统性趋势、确保关键 bug 不在冲刺之间丢失。
- **触发前置**：`production/qa/bugs/`（或备用位置）有 bug 记录；**运行时机**：冲刺开始时、`/team-qa` 完成且新 bug 已提交后、开放数越过 10+ 时。无 bug 文件 → 没有可分诊的，停止（裁决 COMPLETE）。

## 2. 数据依赖
| 方向 | 内容 | 说明 |
|------|------|------|
| 读取 | 配置键：`automation, workflow`（resolve `modes.automation`，`project.local.yaml` → `project.yaml` → 默认 `collaborative`） | 每次 `AskUserQuestion` 与每次文件写遵循 `.claude/docs/automation-modes.md`（collaborative 恒问 · guided 仅重大项 · autonomous 记录并继续；`automation_always_ask` 类别恒问）；`workflow: minimal` 无冲刺 → 改报"P1 bug 即下一步修复" |
| 读取 | bug 文件按**优先序**发现：① `production/qa/bugs/*.md`（**首选格式**）② `production/qa/bugs.md`（单一合并 bug 日志，回退）③ 任何 `production/qa/qa-plan-*.md` 的 "Bugs Found" 表（最后手段）；`production/sprints/` 最近修改的文件（冲号/名、范围内故事、容量约束）；`.claude/docs/coding-standards.md`（severity/priority 定义，存在时；否则用技能内置标准定义） | `trend` 模式**禁止读 bug 正文**——趋势指标用表头字段即可算（见 R4） |
| 产出 | `production/qa/bug-triage-[date].md`（分诊报告；批准后才写） | Triage Summary、P1/P2/P3P4 表、Systemic Issues、Trend Analysis、Recommended Actions |
| 派生智能体 | 无，主会话直接执行 | — |

## 3. 核心规则
R1. 模式（第 1 步）：`sprint` → 对照当前冲刺分诊，可修的派进冲刺积压、其余延期；`full` → 不论冲刺范围全量分诊；`trend` → **只做趋势分析（不做分派），只读报告**；无参数 → 有当前冲刺则 sprint 模式，否则 full 模式。（1）
R2. bug 文件发现（2a）：按数据依赖的优先序 glob。一处都没找到 → 输出 "No bug files found in `production/qa/bugs/`. If bugs are tracked in a different location, adjust the glob pattern. If no bugs exist yet, there is nothing to triage." 并停止——**没有 bug 就不继续**；裁决 **COMPLETE** — no bug files in `production/qa/bugs/`; nothing to triage。（2a）
R3. `trend` 模式**禁止读 bug 正文**：趋势指标（volume、severity mix、by-system、by-date）用表头字段即可算。bug-report 的字段是**加粗**的（`**Severity**:`、`- **System**:`）——所以匹配 `**field**` 形态，**不是裸行首 `Field:`**。（2a）

R3 对应的表头扫描（保留原文 pattern）：

```
Grep pattern="\*\*(Severity|Priority|Status|System|Category|Reported)\*\*" glob="production/qa/bugs/*.md" output_mode="content"
```

R4. bug 正文只在 `sprint`/`full` 模式做 priority-vs-severity **重估**时才读；`trend` 是只读报告，跳过重估。（唯一需要故事状态的偏差检查——"对 Complete 故事提的 bug"——无论哪种模式都是一次定向的故事状态 grep，不是读 bug 正文。）（2a）
R5. 冲刺上下文（2b）：读 `production/sprints/` **最近修改**的文件，取当前冲号/名、范围内故事（分派目标）、容量约束（有则记）。无冲刺文件 → 注记 "No sprint plan found — assigning to backlog only."。`workflow: minimal` 档**按设计无冲刺**——改说这一点，并把 **P1 bug 点名为下一批修复**，排在 brief build order 的下一张故事之前。（2b）
R6. 严重度参照（2c）：`.claude/docs/coding-standards.md` 存在则读其 severity/priority 定义；不存在则用第 3 步的标准定义（即 R7 的表）。（2c）
R7. 逐 bug 分类（3）——提取或推断两把尺子，**severity 是客观的，priority 是团队决策**：

| Severity | 定义 |
|----------|------|
| **S1 — Critical** | 游戏崩溃、数据丢失或特性完全失败，无法继续 |
| **S2 — High** | 主要特性坏了但游戏还可玩；明显错误行为 |
| **S3 — Medium** | 特性降级但有绕行方案；轻微错误行为 |
| **S4 — Low** | 视觉毛刺、外观问题、错字；无玩法影响 |

| Priority | 定义 |
|----------|------|
| **P1 — Fix this sprint** | 阻塞 QA、阻塞发布，或是上届冲刺的回归 |
| **P2 — Fix soon** | 下个主要里程碑前应解决 |
| **P3 — Backlog** | 修了更好，但无主动阻塞影响 |
| **P4 — Won't fix / Deferred** | 已接受的风险或超出当前产品范围 |

R8. 分派规则（3）：`sprint` 模式对每个 P1/P2 bug——识别修复所属的 story 或 epic、查当前冲刺剩余容量；有容量 → 派进冲刺（`Sprint: [current]`）；**容量已满 → 旗标 `Priority overflow — consider pulling from sprint`，禁止自动塞入**。`full` 模式：全部 P1 派当前冲刺、P2 给下届冲刺估计、P3+ 进 backlog。（3）
R9. 偏差检查（3）——旗标**系统性问题**：**同一系统同一冲刺 3+ 个 bug** → "Potential design or implementation quality issue in [system]"；**同一故事 2+ 个 S1/S2** → "Story may need to be reopened and re-reviewed before shipping"；**对标记 Complete 的故事提的 bug** → "Regression in completed story — story should be re-opened in sprint tracking"。（3）
R10. 趋势分析（4）：**volume**（开放总数、本届新增、本届关闭、净变化 ±N）；**系统热点**（开放 bug 最多的系统、S1/S2 占比最高的系统）；**年龄分析**（超过 **2 个冲刺**的 bug 数；有无 S1/S2 未分派 sprint = none）；**回归指标**（对既往完成故事提的 bug 及计数——隐含故事须重开）。（4）
R11. 写盘门禁（6）：先在会话里呈现报告；**有任何 P4 候选 → 先问 "Are these acceptable as Won't Fix?"**，其 Disposition 保持 `P4 candidate` 直到用户回答。然后问 "May I write this triage report to `production/qa/bug-triage-[date].md`?"——**只有批准后才写**。（6）
R12. 写后提示（按条件，6）：有 **S1 未分派** → "S1 bugs must be assigned before the sprint can be considered healthy. Run `/sprint-status` to see current capacity."；有**回归 bug** → "Regressions found — consider re-opening the affected stories in sprint tracking and running `/smoke-check` to re-gate."；**无 P1 bug** → "No P1 bugs — build is in good shape for QA hand-off."。之后**无论有无 P1**：裁决 **COMPLETE** — triage report written。用户拒写 → 裁决 **BLOCKED** — user declined write。（6）
R13. 协作协议（铁律）：**未经用户批准永不关闭 bug、永不标 Won't Fix**——浮出为 P4 候选并问 "Are these acceptable as Won't Fix?"；**永不自动分派进已满容量的冲刺**——旗标 overflow，让冲刺 owner 决定拉什么；**severity 是客观的，priority 是团队决策**——severity 分类以建议呈现，不是命令；**趋势数据仅作参考**——禁止仅凭趋势发现阻塞工作，浮出为观察。（Collaborative Protocol）

R10-R11 对应的报告模板（保留原文结构与表列，第 5 步）：

> **Date**: [date]

## 4. 门禁与裁决
- 本技能无审查门禁、无派生智能体。内含裁决与门禁：
- **P4 门禁**：任何 Won't Fix 候选必须经用户批准，批复前 Disposition 保持 `P4 candidate`。
- **裁决**：COMPLETE（报告已写；或无 bug 文件时空转 COMPLETE — nothing to triage）/ BLOCKED（用户拒写）。
- **升档警告**：aged S1/S2（>2 冲刺未分派）> 0 时报告内出 ⚠️ 警告，视为应显式评审的已接受风险。

## 5. 移植建议
- **可直接移植**：R1-R4（三模式、无 bug 空转 COMPLETE、trend 模式只读表头不读正文、`**field**` 加粗匹配）、R7（severity/priority 双梯子四档定义）、R8（容量满则 overflow 旗标、不自动塞入）、R9（3+ 同系统 / 2+ S1S2 同故事 / 对已完成任务提 bug 三类系统性旗标）、R10（>2 冲刺 aged 警告）、R11-R13（P4 候选必问、写前必问、四条协作铁律）。
- **需替换概念**：sprint → 迭代；game system/epic/story → 模块/特性/任务；QA hand-off → 测试交接/发布前验收；`/sprint-status`、`/smoke-check`、`/team-qa`、`/hotfix` → 状态查看/冒烟复检/批量测试/紧急修复流程；"无玩法影响" → 各自领域的"不影响用户的缺陷"定义。
- **改写示例**：
  - "缺陷分诊区分严重度（客观，按影响分级）与优先级（团队决策，按紧迫度分级）；严重度分类只作为建议呈现，优先级调整和 Won't Fix 处置必须经用户确认。"
  - "同一模块在一个迭代内累计 3 个以上缺陷，或同一任务累计 2 个以上高严重度缺陷，必须在分诊报告中标为系统性质量问题；迭代容量已满时禁止自动塞入，只标 overflow 由迭代负责人裁决。"
