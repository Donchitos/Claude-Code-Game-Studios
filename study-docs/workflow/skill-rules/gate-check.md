# gate-check — 正式阶段门禁（AGENTS.md 移植版）

> 来源：[SKILL.md](file:///workspace/.claude/skills/gate-check/SKILL.md)（含 references/ 下 12 个外置文件与 CONTRACT.md） ｜ 阶段：所有阶段切换 ｜ 移植目标：其它项目的 AGENTS.md / CLAUDE.md / skill 定义

## 1. 技能定位
- **命令**：`/gate-check [target-phase: systems-design | technical-setup | pre-production | production | polish | release] [--review full|lean|solo]`
- **一句话职责**：裁定项目是否可进入下一开发阶段——工件存在性、质量检查、总监并行评审，产出 PASS/CONCERNS/NOT ASSESSED/FAIL 正式裁决；PASS（或用户显式接受 CONCERNS 风险）时双写阶段状态。
- **触发前置**：`resolve_config --keys review_mode,workflow,qa.level,testing.strict,performance.enforce,team.size,project.stage,system_overrides` 已解析（`--review` 覆盖 `review_mode`）。与 `/project-stage-detect`（诊断"我们在哪"）不同，本技能是处方式（"能否推进"+正式裁决）。**豁免于 `automation`**：协作协议恒适用，阶段门禁是从不自动运行的人工检查点。

## 3. 核心规则（逐条编号 R1、R2……）

### 七阶段与参数解析
R1. 阶段序列（7）：Concept → Systems Design → Technical Setup → Pre-Production → Production → Polish → Release。带参调用验证指定阶段就绪度；无参时用与 `/project-stage-detect` 相同的启发式自动探测当前阶段，再**必须**用 `AskUserQuestion` 与用户确认（"Detected stage: **[current]**. Running gate for [Current] → [Next]. Is this correct?"，`[A] Yes` / `[B] No — pick a different gate`〔选 B 弹第二级全部门清单〕）——**禁止跳过此确认**。（Section 1）
R2. `review_mode` 决定总监是否 spawn：`solo` → 跳过全部总监（本技能退化为纯工件存在性检查，输出注明 "Director Panel skipped — Solo mode"）；`lean` → 面板照跑（阶段门禁就是 lean 模式的目的）。`workflow` 决定面板宽度（R19）；`team.size` 只影响各总监评审的专家深度（`individual` 核心集 / `small` 标准集 / `studio` 加引擎子专家），**绝不**减少总监数量——跳总监是 `review_mode` 的职责。（Section 1、4b）
R3. `qa.level` 独立于 tier 放宽**测试类**条目：`minimal` 下 test-evidence/unit-test 工件条目在**每个** workflow tier 都变非必需、testing.strict 检查为 no-op，无测试的项目也能过；`standard` 要求 Logic+Integration 测试通过；`full` 要求覆盖率核查+回归套件（最低值取 `qa.coverage_minimum`）。**不放宽外观**：UI story 留存截图与 Visual/Feel story 截图+lead 签到（`production/qa/evidence/`）在任何 `qa.level` 都必需。**smoke check 豁免于该放宽、是地板**：`qa.level` 放宽的是逐 story 测试证据，smoke check 是 build health——否则 Production → Polish 门在 `rigor: minimal` 下会零必需工件而无法因工件 FAIL。（Section 1、2b）

### 2b — tier 缩减与覆盖
R4. 每个门文件先给 `full` 基线，再给 `standard`/`minimal` 缩减。套用规则：跑完基线清单后套该 tier 缩减——**drop** = 此档不查；**→ recommended** = 缺席呈现为 CONCERNS、绝非 Blocker；未点名的条目保持基线状态。**缩减只会放宽，唯一能加严的是 `workflow_overrides`**。（2b）
R5. 应用 tier 缩减 + `qa.level` 放宽后清点剩余必需项：**为零时报告 NOT ASSESSED（点名两个缩减器与门）**——"此门什么都没验证"，而非靠无事可查赚一个 PASS。唯一例外：门文件标注"not applicable"的转换（Systems Design → Technical Setup at `workflow: minimal`）——那不是没东西可查而是该 tier 没有这个转换：带注释 PASS（"No design gate at minimal workflow — minimal skips the Systems Design phase; advancing brief → code."），总监面板不跑（注明 "Director Panel skipped — gate not applicable at `workflow: [tier]`"），Section 6 的 stage 写入仍先征询。（2b）
R6. `performance.enforce` 同样独立于 tier，**tier 缩减永不压制它**：性能检查在每个 workflow tier 都跑，`block` 让违例在每个 tier 都是 Blocker（勿把门文件的"everything else drops"读成把它也 drop 了）；`off` 是唯一让预算变信息性的选择。`rigor: minimal` 项目尤须注意——Polish 门的 minimal 缩减会 drop 掉 "Performance is within budget"，**照样跑这个检查**。（2b）
R7. **逐系统覆盖**（`workflow_overrides.system_overrides`，仅作用于验证 MVP GDD 的门）：按"该系统在 `system_overrides` 有行→该 tier，否则项目级 `workflow`"解析每个 GDD 的生效 tier。**先反向核对**：`<system>` 是 GDD 文件名 stem（查 `design/gdd/<key>.md` 是否存在），无匹配 stem 的键要报告（点名该键并列出现有 stems："This override is doing nothing."）——以 **CONCERNS 级发现**呈现而非 Blocker（用户以为生效而实际没生效的逃生舱正是悄悄失效的方式）。系统钉**高**于项目 tier → **阻断该门**直到该系统 GDD 达到更高档章节数（唯一使门更严的逐系统情形）；钉**低** → 只放宽该系统，钉 `minimal` 的系统**没有任何 GDD 章节要求**、永不因 GDD 缺失/不全面阻断（不存在 "acceptance-criteria-only" 地板，勿发明）。加成性覆盖：`art_bible_strict: true` 无视 tier 强制完整（9 节）art bible（Technical Setup→Pre-Production 与 Pre-Production→Production 两门）；`edge_cases: true`、`tuning_knobs: true` 在验证 GDD 完整性时强制对应章节必需、叠加在解析 tier 之上；`false` 是默认/no-op，**永不**用于放宽 tier 已要求的章节。（2b）

### 3 — 跑门禁检查
R8. 工件存在性与计数**确定性解析——禁止靠开文件判断存在**：`bash .claude/scripts/artifact-check.sh --phase [source-phase]`（传推进*来源*阶段；`workflow: minimal` 另跑 `--path minimal`——brief 与 stories 在该路径上）。脚本读 `workflow-catalog.yaml`（已编码 glob/pattern/min_count/any_of），按步骤报 `PRESENT`（glob 命中且 min_count 满足且 pattern 找到）/ `ABSENT` / `SHORT`（命中但少于 min_count，给 count= min=）/ `PATTERN_MISS`（文件在但无必需标记）/ `NO_CHECK`（该步无工件声明——**磁盘上不可检测**）。它只给观察不给裁决：required/optional 拆分由你套用 tier 后决定。（Section 3）
R9. **`NO_CHECK` 不是 `PRESENT`**：表头在任何行前先打 `NO_CHECK:` 计数正是为了不被略读。这些步骤是*被扫过*而非*被满足*——逐项带进 Section 4 问用户或标 `MANUAL CHECK NEEDED`；大部分清单不可检测却报 PASS 的门正是该计数要防的失效。**存在不等于合格**：脚本分不出真文档和模板骨架——裁决实际依赖的工件必须抽查内容；裁决不依赖的不抽查。（Section 3）
R10. **smoke report 恒为裁决所依赖的工件——抽查是义务不是可选项**（`minimal` 下常是唯一必需工件，整个门压在一个没人生成、没人核验的文件上）。对照仓库核查其声称并树内矛盾即上报：报自动化套件通过 → 引擎测试根必须真有测试文件且项目有 runner（"24 passed, 0 failed" 于无测试文件的仓库是发现不是证据）；标关键路径 PASS → 该路径代码必须存在于代码根；无日期或早于触及代码根的最新提交 → 指出（过期 smoke report 描述的是已不存在的构建）。矛盾按该工件被要求同级上报：必需处为 Blocker、recommended 处为 CONCERNS。（Section 3）
R11. 质量检查：**无测试 runner 配置是 NOT ASSESSED 不是静默跳过**（跑不了测试的门没发现失败，不等于通过）。测试失败对裁决的影响按 Phase 1 解析的 `testing.strict` 块（`resolve_config` 会把 `project.local.yaml` 叠在 `project.yaml` 上——直接读文件会丢本地覆盖）：Logic（Godot `tests/unit/`、Unity Edit Mode）由 `testing.strict.logic` 门控；Integration（Godot `tests/integration/`、Unity Play Mode）由 `.integration` 门控；Unreal 单根两类并存——按 story 的 Type 分类，未知时取两档更严者。每键只认 `true`/`false`（大小写不敏感）；缺失/空/其它值 → 读 `testing.strict` 为普通布尔（legacy 形态）；再缺失/无效 → 默认 `true`。strict(`true`) 档失败是 **Blocker**（FAIL）；advisory(`false`) 档是 **Concerns**（最低 CONCERNS 不 FAIL，列 Recommendations 不列 Blockers）。未识别值呈报用户。（Section 3）
R12. 设计文档章节用 `gdd-structure-check.sh` 确定性获取（每 GDD 打 `PRESENT:`/`ABSENT:` 对 + `PLACEHOLDER:` 行点名只含 `[To be designed]` 的在场章节；`## Detailed Design` 可满足 Detailed Rules 要求；只报存在性），再套各 GDD 生效 tier：`full` 全 8 节、`standard` 5 标准节（+ 条件性 Formulas）。缺**必需**节阻断；该 tier 下可选的缺失为 advisory。PRESENT 章节若是空标题仍可判不合格——裁决依赖的节要抽查。（Section 3）
R13. 性能检查：预算四键从 `project.yaml`（否则 technical-preferences.md）读，对照 `tests/performance/` 或最近 `/perf-profile` 输出。违例含义由 Phase 1 解析块的 `performance.enforce` 定（本地可覆盖、勿直接读文件）：`warn`（默认）→ CONCERNS 绝非 Blocker；`block` → Polish 门起为 Blocker；`off` → 信息性、不进裁决。只认三值，其它呈报并回退 `warn`。（Section 3）
R14. 本地化检查：在代码根 Grep 硬编码字符串；**代码根未解析 → 报 `NOT ASSESSED — code root unresolved` 而非零命中**。交叉引用检查：`design/gdd/` 文档 vs 代码根实现；架构文档引用的每个系统有对应代码；sprint 计划引用真实工作项。（Section 3）
R15. Systems Design → Technical Setup 的跨 GDD 评审检查：`Glob('design/gdd/gdd-cross-review-*.md')` 找 `/review-all-gdds` 报告。无匹配：`full` 下该工件 **FAIL** 并醒目呈现（"Run `/review-all-gdds` before advancing"）；`standard` 下 recommended → CONCERNS 非 blocker；`minimal` 下此门不适用。找到则读裁决行：FAIL → 须先解决才能推进；NOT ASSESSED → 什么也没证明——本门该条记 NOT ASSESSED 绝不通过；`Focus:` 行只点名一次 pass（consistency 或 design-theory 单跑）的报告同等对待——另一次 pass 从未运行。（Section 3）

### 4 — 协作评估与总监面板
R16. 无法自动验证的项目**问用户**，**绝不假设 PASS**——标 `MANUAL CHECK NEEDED`。回答即解析条目："no"/"not yet" 是已检查、未通过的条目（CONCERNS 或 FAIL，点名收口的技能如 `/design-review [doc]`）——唯一例外是 Production 门的游玩问题（"not yet" 意味着没人玩过：NOT ASSESSED）。只有未回答或 "I don't know" 保持 MANUAL CHECK NEEDED（Section 5 将其转为 NOT ASSESSED）。拒绝补数据（如不跑 `/perf-profile`）→ 该条留 NOT ASSESSED；`performance.enforce: off` 时则不进裁决。（Section 4）
R17. 总监面板双轴：**Axis 1 `review_mode` 定面板是否跑**（solo 跳过并注明、lean/full 跑）；**Axis 2 `workflow` 定面板宽度**——`minimal` 1 人（`producer`）、`standard` 2 人（`technical-director`、`producer`）、`full` 4 人（`creative-director`、`technical-director`、`producer`、`art-director`）。`producer` 恒在每个面板（范围与进度就绪是没有任何 tier 可选的判断）；`technical-director` 自 `standard` 加入（首个要求架构工件的 tier）；CD/AD 自 `full` 加入（唯一要求完整 art bible 与 UX spec 集的 tier）。**宽度不等于严格度**：窄面板不软化裁决——**实际运行者中返回的最严裁决仍然胜出**；绝不从没咨询过的视角推断 PASS。（Section 4b）
R18. **总监并行评审**：出终裁前，把解析 tier 的全部总监作为**并行子代理**经 `Agent` 同时 spawn（用 `.claude/docs/director-gates.md` 的并行门禁协议）——**所有 Agent 调用一次性发出，禁止等一个完成再开下一个**。每个总监带自己的门禁 ID：CD-PHASE-GATE / TD-PHASE-GATE / PR-PHASE-GATE / AD-PHASE-GATE（各自的 `.claude/docs/director-gates/*.md`）。传给每个总监：目标阶段名、解析的 `workflow` tier、目标门在该 tier 的必需+推荐工件（缩减后的清单——**这个门要什么**，不是后面的门）、在场工件清单、及其门禁专属上下文：CD → 游戏支柱与核心幻想（`game-concept.md`，否则 `game-brief.md`）；TD → 架构文档路径、引擎参考路径（`docs/engine-reference/<engine>/VERSION.md`）、ADR 清单；PR → sprint 与里程碑工件、`team.size`（含现行 sprint 容量）、`production/epics/` 下 `Blocked` 状态 story 数（`minimal` 传 brief 的 Build order 当计划）；AD → 美术与视觉工件、Visual Identity Anchor、art bible 路径。要求总监按节读 GDD/ADR/art bible（Grep `^#` + Read offset/limit）。（Section 4b）
R19. 上下文条目三态传递，总监无需猜：**Present**（路径或值——0 个 Blocked story 也是值）；**"none"**（目标门或更早的门在此 tier 要求/推荐而它不存在——是让总监判断的项目事实）；**"not expected before [phase]"**（目标门尚不要求；点名首个要求它的阶段）/"not required at `workflow: [tier]`"——后两者**绝不**传成 "none" 也**绝非**发现（总监评的是进入阶段的就绪度，不是后面阶段）。面板窄于 4 人时**在输出点名缺席视角及获得方式**："Panel: 2 of 4 (`workflow: standard`). Creative and Art perspectives not consulted. Raise `modes.rigor` to `full` (or set `modes.workflow: full`) for the complete panel."——点名配置块显示为 workflow 来源的那个设置（`modes.workflow` 单独设置时升 rigor 不改它）；**绝不**指向 `--review full`（它定面板是否跑，不定宽度）。收集全部响应后呈现面板摘要（每总监一行 `[READY / CONCERNS / NOT READY / NOT ASSESSED]` + 反馈）。（Section 4b）
R20. 面板套用到裁决：任一总监 **NOT READY** → 裁决最低 **FAIL**（无任何 override 把 FAIL 变成阶段变更）；任一 **CONCERNS** → 最低 **CONCERNS**；任一 **NOT ASSESSED**（且无 NOT READY/CONCERNS）→ 至多 **NOT ASSESSED**（点名该总监说缺的输入，绝不计为 READY）；全体 READY → 具备 PASS 资格（仍受 Section 3 工件与质量检查约束）。（Section 4b）

### 5 — 裁决与验证链
R21. 报告结构：`## Gate Check: [Current] → [Target]` + Date/Checked by → Required Artifacts `[X/Y present]`（逐项 `[x]`/`[ ]` + 文件大小或 MISSING）→ Quality Checks `[X/Y passing]`（含 `[?] MANUAL CHECK NEEDED`）→ Blockers（编号、各点名收口技能）→ Recommendations → Verdict（PASS=全部必需工件在场且质量检查全过；CONCERNS=有小缺口可在下阶段处理——**仅在用户显式接受风险时推进**；FAIL=关键 blocker 必须先解决；NOT ASSESSED=一项以上必需检查根本没能跑——在 Blockers 节点名是哪些及为什么）→ Accepted Risks（仅用户在 CONCERNS 上推进时：每条 concern + 用户接受 + 日期）。（Section 5）
R22. **裁决优先级——首条命中规则胜出，按 FAIL → CONCERNS → NOT ASSESSED → PASS 求值**。NOT ASSESSED 高于 PASS（没能检查自己部分范围的门没有证明就绪）、低于 CONCERNS 与 FAIL（已知 blocker 比未知更可行动）——它不是更软的 FAIL："查了发现 blocker" 与 "没能查" 需要不同的修复。同时有真 blocker 与不可评估检查的门是 FAIL；带不可评估检查的 CONCERNS 仍须把该检查以 NOT ASSESSED 及原因列在 Blockers 下（正是它阻止阶段推进）。（Section 5）
R23. 以下任一情形必须给 **NOT ASSESSED**：必需工件存在但无法评估（空、不可读、或整篇 `[TO BE CONFIGURED]`/模板占位——"在场但空"是最像在场的情形）；质量检查输入无实测数据（`/perf-profile` 模板预填 `[16.67ms]`——占位数字不是测量，没人设的预算不是被满足的预算）；tier 要求的测试检查无法执行（无 runner 或 runner 起不来——**仅限要求测试的 tier**；`qa.level: minimal` 下无测试门，缺 runner 是配置姿态不是洞）；用户未解决的 `MANUAL CHECK NEEDED` 项；解析 tier 应 spawn 的总监没返回（出错、无裁决、被打断——**窄读此条**：面板按设计缩窄〔minimal 1 人/standard 2 人/solo 0 人〕是宣布过的裁剪不是评估失败，只有你预期在面板里的总监没回来才触发）；被引用的上游裁决本身是 NOT ASSESSED（向上传播而非解析成通过）。**绝不以宽松读法消解未知——检查没能跑这件事本身就是发现**。（Section 5）
R24. **验证链（Chain-of-Verification）**：起草裁决后、定稿前必须挑战它。Step 1——生成 5 个旨在推翻裁决的挑战问题，**至少 2 个必须靠重读具体文件（Read）或重跑具体检查（Grep）回答**（标 `[TOOL ACTION]`），不得全靠反思；PASS 草稿问"哪些检查是我真读了文件验证的 vs 推断的""有没有未经用户确认就标 PASS 的 MANUAL 项〔TOOL ACTION〕重扫清单""有没有只有空头的工件〔TOOL ACTION〕重读"等；CONCERNS 草稿问"有没有被我软化的 FAIL 条件""各 concern 单独都小、合计是否构成 blocker"；FAIL 草稿问"硬 blocker 与强建议分清了吗""能给出到 PASS 的最小路径吗"。Step 2——逐问独立作答，**禁止引用草稿裁决文本**——重查具体文件或问用户。Step 3——发现漏 blocker → 升级（PASS→CONCERNS 或 CONCERNS→FAIL）；发现"没能跑"而非"跑了且通过" → PASS→NOT ASSESSED；发现夸大 blocker → 仅在引用具体证据时降级；**绝不靠重新推理把 NOT ASSESSED 降到 PASS——只有拿到输入才能清除**；一致 → 确认不变。Step 4——终稿注明 `Chain-of-Verification: [N] questions checked — verdict [unchanged | revised from X to Y]`。（Section 5a）

### 6 — stage 更新条件
R25. **stage.txt 更新条件**：裁决为 **PASS 且用户确认推进**时，把新阶段**双写**——`project.yaml` 的 `project.stage: <new-stage>` **和** legacy `production/stage.txt`（单行如 `Production`）。双写是为兼容尚未迁移的 hooks 并立即更新状态行。**CONCERNS 上用户可显式 override**：默认**不**主动提供 stage 写入；用户要求强行推进时列出每条 concern 并问 "The gate returned CONCERNS. Accept these risks — [list] — and may I update `project.stage` in `project.yaml` to '[stage]' (and the legacy `production/stage.txt`)?"——仅在显式 yes 后，把 `### Accepted Risks` 节写进门报告（每条 concern+用户+日期）并写 stage。**FAIL 永不被 override 成阶段变更，NOT ASSESSED 同样**；CONCERNS 内部同理：任何必需检查仍 NOT ASSESSED 时**不提供** override（点名该检查及使其可跑的条件），须先修复/补输入并重跑。（Section 6）
R26. 写入用 `bash .claude/scripts/set-stage.sh "<new-stage>"`（两词阶段要引号）：改 `project.yaml` 的 `stage:` 行、无 `project:` 块时在 `framework:` 后补、无文件时从最小模板创建；保留注释、其它键与行尾；同时写 legacy `production/stage.txt` 并回读两文件；**绝不**写 `modes.review_mode`（由 `modes.rigor` 供给）。验证双写：展示 `stage_yaml` 与 `stage_txt` 行——Exit 0 = 两文件皆新阶段；Exit 4 = 写后不一致（分裂的阶段指示会污染后续自动探测）→ 报告差异并停止；Exit 5 = `project.yaml` 布局脚本不改（`project:` 为单行值）→ 什么都没写、明说并经用户 yes 手工编辑；其它非零 → 报告消息并停止。**写前恒问**："Gate passed. May I update `project.stage` in `project.yaml` to 'Production' (and the legacy `production/stage.txt`)?"（CONCERNS override 的显式 yes 即此问）。（Section 6.1-6.2）
R27. Rigor-fit 检查（advisory——**绝不影响裁决**）：阶段推进确认后，新阶段为 Production（或更晚）而解析 `modes.workflow` 为 `minimal` 时加一行："You're entering [stage] on `rigor: minimal` — most projects this size run `standard`. Revisit with `/settings modes.rigor=standard`?"——**只在此处提一次**，路由到 `/settings`，绝不自己改设置。（Section 6.3）

### 7/8 — 收尾
R28. 裁决呈现且 stage 更新完成后，用 `AskUserQuestion` 按刚跑的门定制收尾选项（参数名的是**进入的**阶段）。`workflow: minimal` 跳过菜单、改按 `paths.minimal` 提供第一个未完成步骤：`/setup-engine` → `/brainstorm`（代码根已有游戏时 `/reverse-document design [code root]`——从已建之物写 brief）→ `/create-stories` → `/dev-story`。其余各门：Concept→Systems Design PASS 给 `[A] /map-systems`（systems-index.md 不存在时，否则 `/design-system [首位系统]`）；Systems Design→Technical Setup PASS 给 `[A] /create-architecture`（写任何 ADR 前的必需下一步——先蓝图后 ADR，跳过即无蓝图写 ADR）；Technical Setup→Pre-Production PASS 给 `[A] /create-control-manifest`（manifest 不存在时先跑）/`[B] /vertical-slice`（写 epic 前先验证好玩）等；Pre-Production 顺序刻意**先验证好玩再详细计划**：create-control-manifest → vertical-slice **FIRST** → playtest（≥1 次记录会话、3+ 更好）→ `/ux-design` → `/create-epics layer:foundation`+`layer:core` → `/create-stories` → `/sprint-plan new`——原型若揭示核心循环要改，此前写的 epic 会部分作废（GDC postmortem 数据第一课）；其余门给两个最合逻辑下一步 + Stop。（Section 7）
R29. Follow-up 按缺失工件映射到技能（如：无 art bible→`/art-bible`；无测试框架→`/test-setup`；测试失败→委派 `lead-programmer`/`qa-tester`；性能未知→`/perf-profile`；无安全审计或有未结 CRITICAL/HIGH→`/security-audit`）。**两个例外禁止点名技能**：`design/difficulty-curve.md` 与 `design/player-journey.md` 没有任何技能写它们——明说是从 `.claude/docs/templates/` 模板**手工撰写**（`/ux-design` 只是读 player-journey 的步骤、`/quick-design` 写别的路径，指错技能会把用户带回刚失败的检查）。（Section 8）
R30. 协作协议：先扫描（查全部工件与质量门）；未知必问（绝不假设 PASS）；呈现完整清单与状态；**用户做最终决定**——裁决只是建议，只有 stage 写入被裁决绑定；写报告先批准（"May I write this gate check report to production/gate-checks/?"）；**绝不自动修复**——缺必需工件时报 FAIL 并点名该跑的技能，**禁止**创建缺失文件或自动重跑门（造文件换 PASS 即摧毁门的意义）；**绝不阻止用户干活**——裁决只决定本技能是否写新 stage；FAIL/NOT ASSESSED 下 stage 原地不动直到重跑通过，期间用户照常处理 blocker。（Collaborative Protocol、CONTRACT.md）

## 4. 门禁与裁决
- **六门清单**（full 基线要点；tier 缩减见 R4-R7 与各门文件）：
  - **Concept → Systems Design**：必需——`design/gdd/game-concept.md` 有内容、游戏支柱（concept 内或 `game-pillars.md`）、Visual Identity Anchor 节；推荐——概念原型（`prototypes/` + REPORT.md 为 PROCEED）。质量——concept 已过 `/design-review`（非 MAJOR REVISION NEEDED）、核心循环已描述、目标受众明确、VIA 含一行视觉规则+≥2 条支撑原则。`standard`：支柱+VIA→recommended；`minimal`：目标改为 `design/game-brief.md`（有内容的 brief=PASS），GDD/支柱/VIA 全 drop。
  - **Systems Design → Technical Setup**：必需——systems index（`design/gdd/systems-index.md` 列 MVP 系统）、全部 MVP GDD 存在且各自过 `/design-review`、跨 GDD 评审报告存在。质量——MVP GDD 过个人评审（full 8 节）、`/review-all-gdds` 非 FAIL（NOT ASSESSED/单 pass 报告不满足）、跨 GDD 问题已解决或显式接受、系统依赖双向一致、MVP 优先级已定、无过期 GDD 引用。`standard`：GDD 按 5 标准节、cross-review→recommended；`minimal`：**门不适用**（brief→code 自动 PASS 带注释，见 R5）。
  - **Technical Setup → Pre-Production**：必需——引擎已选（非 `[CHOOSE]`）、`project.yaml` 已配置、art bible ≥§1–4、≥3 个 Foundation 层 ADR（场景管理/事件架构/存读档）、引擎参考文档、测试框架已初始化+CI workflow+≥1 示例测试、master 架构文档、可追溯性索引、`/architecture-review` 已跑（读各报告 `Mode:` 行取最新覆盖该条者——`full` 才算"已跑"；无 `Mode:` 行的旧报告不计）、无障碍需求文档、交互模式库。质量——ADR 覆盖核心系统、命名/性能预算已设、无障碍 tier 已定（Basic 也可、undefined 不行）、UX spec 起步、全部 ADR 有 Engine Compatibility（带版本）与 GDD Requirements Addressed 节、不引用 deprecated API、HIGH RISK 引擎域已处理、追溯矩阵零 Foundation 缺口；**ADR 循环依赖检查**用 `adr-dep-graph.sh`（有 `CYCLE:` 行即 FAIL，`BLOCKED_BY_CYCLE` 记为等待而非环上节点；无环但 `UNFILLED_DEPS` 多 → CONCERNS 逐个点名）；引擎验证（VERSION.md 后读：post-cutoff API 的 ADR 标 Knowledge Risk、版本一致）。`standard`：art bible 仅当有视觉资产 story 才必需、ADR 缩到 Foundation 关键项、UX/无障碍/模式库/追溯→recommended；`minimal`：只要求引擎已配置。
  - **Pre-Production → Production**：必需——首个 sprint 计划、art bible 完整（9 节）+AD-ART-BIBLE 签到（review_mode 跳过该门时 `SKIPPED` 签到行可替代，`[Not yet reviewed]` 头读作"签到跳过——[mode] mode"而非缺失）、MVP GDD 完整、master 架构文档、≥3 Foundation ADR、Foundation+Core 层 ADR 全 `Accepted`（story 被治理 ADR 接受前不能解锁）、control manifest、Foundation+Core 层 epics、关键屏 UX spec（主菜单/核心 HUD/暂停）+HUD 文档+过 `/ux-review`。Vertical Slice 三项（build 可玩/≥1 次记录 playtest/playtest 报告）**recommended 不阻断——缺席即 CONCERNS**。质量——核心循环好玩已验证（playtest 数据）、UX 覆盖 GDD 的 UI Requirements、sprint 引用真实 story 路径（story 须嵌 GDD 需求 ID+ADR 引用）、切片 COMPLETE（完整 [start→challenge→resolution] 循环）、架构无未解 Foundation/Core 问题、ADR 有依赖节（全 None 也要写）、核心幻想已交付（≥1 名 playtester 无提示独立说出匹配 Player Fantasy 的体验）。**切片裁决规则**：建了且任一验证项 NO → 自动 FAIL（验证四项：人无引导玩通核心循环、开局 2 分钟内知道做什么、无致命 fun-blocker、核心机制手感好——主观项问用户）；建了但没人玩过（NOT ASSESSED/"not yet"）→ 该条 NOT ASSESSED 绝不通过；没建（跳过）→ 仅 CONCERNS（surfacing 晚期设计转向风险，用户决定——跳过是合法的 solo/限时选择，端着坏的上线不是）。`minimal`：地板=填好的 `design/game-brief.md`（含 build order）+stories（无 sprint 计划），其余全 drop，代之以两个现构建检查——核心循环好玩 + 端到端能跑（一条完整 start→challenge→resolution）；任一 "no" 即 FAIL、"not yet"（好玩）即 NOT ASSESSED。**全 tier 铁律：tier 缩减放宽的是必须*存在*什么，永不放宽必须*能跑*什么**。
  - **Production → Polish**：必需——代码根有组织成子系统的活跃代码、GDD 核心机制全实现（交叉核对）、主玩法路径端到端可玩、测试文件覆盖 Logic+Integration story、本 sprint Logic story 全有单测文件、smoke check 为 PASS 或 PASS WITH WARNINGS（`quick` 跑法**不算**——跳了覆盖扫描）、QA plan（advisory→CONCERNS）、QA sign-off（APPROVED / APPROVED WITH CONDITIONS）、≥3 次独立 playtest 且覆盖新玩家体验/中期系统/难度曲线、fun hypothesis 已显式验证或修订。质量——测试通过、无未结 S1 Critical bug、按 GDD 验收标准核对核心循环、性能在预算内、playtest 发现已处理（非仅记录）、无"困惑循环"（无 >50% playtester 卡关不知为何的点）、难度曲线匹配文档、已实现屏幕全有 UX spec（无"代码里现场设计"屏）、模式库最新、无障碍合规。`standard`：QA sign-off+逐 story 覆盖→recommended；`minimal`：smoke+端到端可玩+无 S1 Critical 必需，核心机制交叉核对→recommended，其余 drop。
  - **Polish → Release**：必需——里程碑计划功能全实现、内容完整（设计文档引用的关卡/资产/对话全存在）、本地化字符串外置（代码根无硬编码玩家可见文本）、QA plan+QA sign-off、全部 Must Have story 测试证据在场（Logic/Integration 测试通过；UI 每屏留存截图；Visual/Feel 截图+lead 签到——**无 qa.level 豁免这两类**）、smoke 在 RC 构建干净通过（PASS，非 quick）、无上 sprint 回归、`/balance-check` 已跑、`/release-checklist` 已跑、商店元数据、changelog 草稿。质量——qa-lead 签到、全测试通过、全目标平台性能达标、无未结 S1/S2/S3 bug、**安全项**——最新 Scope 为 `full` 的 `production/security/security-audit-*.md`（被后续 `quick` 报告更新）无未结 CRITICAL/HIGH（后续 `network`/`save`/`input` 报告只加不清其未扫类别；任一未结 CRITICAL/HIGH 即 blocker；无 full 范围报告=检查没能跑→NOT ASSESSED 绝不通过）、本地化——每个发货译文 locale 有 `/localize qa` PASS 或 PASS WITH CONDITIONS（FAIL 只阻断该 locale；无报告或 NOT ASSESSED=未验证；源语言 `en` 不需要；只发源语言则记 N/A 并说明）、无障碍基本项（改键/文本缩放）、法务（EULA/隐私/分级）、构建干净打包。`standard`：内容完整审计+QA sign-off+本地化→recommended，功能全+smoke+无 S1 Critical 必需，S2/S3→recommended；`minimal`：只 smoke+无 S1 Critical。
- **裁决词**：`PASS` / `CONCERNS` / `NOT ASSESSED` / `FAIL`；总监面板词：`READY` / `CONCERNS` / `NOT READY` / `NOT ASSESSED`。
- **最严裁决**：总监间任一 NOT READY 即整体最低 FAIL；任一 CONCERNS 即最低 CONCERNS；任一 NOT ASSESSED 至多 NOT ASSESSED——**由实际运行者取最严**（窄面板不软化）；与工件/质量检查合并后再按 R22 的 FAIL > CONCERNS > NOT ASSESSED > PASS 定终裁。
- **stage 写入绑定**（R25-R26）：仅 PASS+确认或 CONCERNS+显式接受全部风险（记录 Accepted Risks）；FAIL/NOT ASSESSED 永不写。
