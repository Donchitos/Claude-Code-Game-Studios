# reverse-document — 从现有代码反向生成设计文档（AGENTS.md 移植版）

> 来源：[SKILL.md](file:///workspace/.claude/skills/reverse-document/SKILL.md) ｜ 阶段：Any ｜ 移植目标：其它项目的 AGENTS.md / CLAUDE.md / skill 定义

## 1. 技能定位
- **命令**：`/reverse-document <type> <path>`（type：`design`→GDD 节 / `architecture`→ADR / `concept`→原型概念文档；path 为代码根下的目录或文件——Godot `src/`、Unity `Assets/`、Unreal `Source/<Module>/`，或 `prototypes/` 原型目录）
- **一句话职责**：分析既有实现（代码/原型/系统）反向生成设计或架构文档——捕捉"代码做了什么"+向用户问出"为什么"，供先写代码后补文档、接手无文档代码库、原型机制形式化等场景。
- **触发前置**：`resolve_config --keys workflow,system_overrides,automation` 已解析；`modes.automation` 决定每个提问与文件写入的协作档位（collaborative 恒问 · guided 仅重大项——新文件仍问 · autonomous 记录后继续）。

## 2. 数据依赖
| 方向 | 内容 | 说明 |
|------|------|------|
| 读取 | 目标路径全部源码/原型；`system_overrides`（把 path 映射到系统名后取该系统行，否则项目 `workflow`）——**决定生成多少文档**：`full` 写 8 节 GDD、`minimal` 写一页 brief，tier 判错整个工件就错 | 模板选择与 tier 决定输出形态 |
| 产出 | `design` → `design/gdd/[system-name].md`（`minimal` → `design/[system-name]-brief.md`；整游戏→`design/game-brief.md`）；`architecture` → `docs/architecture/[decision-name].md`；`concept` → `prototypes/[name]/CONCEPT.md` 或 `design/concepts/[name].md` | 全部带 provenance 横幅 + 元数据（见 R10-R12） |
| 派生智能体 | 无，主会话直接执行 | 只读诊断 + 协作起草，模型档位 sonnet |

## 3. 核心规则（逐条编号 R1、R2……）

### Phase 1 — 解析参数与 tier
R1. **解析 tier——禁止假设**：把 `<path>` 映射到系统名，取 `system_overrides` 该系统行，否则项目 `workflow` 值。`workflow-modes.md` 定义各 tier 的*含义*，但说不出*本项目*设的是哪档——必须取解析块。后果在此巨大：`full` 写 8 节 GDD、`minimal` 写一页 brief，tier 错了产出的就是完全错误的工件。（Phase 1）
R2. `design` 输出随 tier 缩放：**`full`** → 完整 8 节 GDD；**`standard`** → 5 节 GDD（Overview、Detailed Design、Edge Cases、Dependencies、Acceptance Criteria；当恢复的系统定义数值规则时 + Formulas；跳过 Player Fantasy 与 Tuning Knobs）；**`minimal`** → 一页 game brief 格式（`templates/game-brief.md`）而非 GDD——整游戏（path 为代码根本身）写 `design/game-brief.md`，单个系统写 `design/[system-name]-brief.md`。`architecture` 与 `concept` 输出与 tier 无关。（Phase 5）

### Phase 2 — 分析实现
R3. 按类型读代码：**design**——识别机制/规则/公式；提取玩法数值（伤害、冷却、范围）；找状态机、能力系统、进度系统；检测代码处理的边缘情况；映射依赖（哪些系统交互）。**architecture**——识别模式（ECS、singleton、observer 等）；理解技术决策（线程、序列化等）；映射依赖与耦合；评估性能特征；找约束与权衡。**concept**——识别核心机制；提取涌现玩法模式；记录什么有效什么无效；找技术可行性洞见；记录玩家幻想/手感。（Phase 2）

### Phase 3 — 问意图（本技能的灵魂）
R4. **绝不只描述代码——必须问意图**：design 类问"资源系统是为 pacing（防滥用）还是 resource management（策略深度）？""该机制是核心支柱还是辅助功能？""数值随因子指数增长——是有意设计还是需要重平衡？"；architecture 类问"用 service locator 是为可测试性、解耦、还是从旧代码继承的？""手动内存管理是性能要求还是遗留？"；concept 类问"原型重潜行轻战斗——是有意的支柱吗？""玩家拿抓钩赶路是 feature 还是 bug？"（Phase 3）

### Phase 3b — 充分性检查
R5. **起草前必须跑，失败即停**：统计 Phase 2 实际找到的三类信号——Mechanics（有可观察规则的具名行为——不是 stub、不是空类）、Formulas（由输入计算玩法值的表达式）、Values（有使用点的调参常量）。三者全为零，或目标路径非样板代码不足约 20 行 → 停止并原样报告："`[path]` does not contain enough implementation to reverse-document. Found: [N] mechanics, [N] formulas, [N] tuning values. …… 如果设计只存在于你脑中，`/design-system [name]` 才是捕捉它的技能——它靠问而非靠推断。"（Phase 3b）
R6. **禁止按部分计数补全继续**：两个机制、零公式的路径得到的是一份两机制文档 + 显式 `FORMULAS DISCOVERED: none found in the source`——因为模板每一节都是必填的，它很乐意接受发明的内容。（Phase 3b）

### Phase 4 — 呈现发现
R7. 起草前先展示发现：MECHANICS IMPLEMENTED / FORMULAS DISCOVERED / UNCLEAR INTENT AREAS（带序号澄清问题），等用户澄清后再起草。**每个节可以为空，空节必须自陈**——在标题下写 `none found in the source`：绝不省略标题（读起来像"没找过"）、绝不按"这类系统通常有什么"填充。方括号行是*形状*不是配额——一个机制的源码只出一行，不出四行。（Phase 4）
R8. **用户不回答 UNCLEAR INTENT AREAS 时，禁止照样起草已解决版本**。这些问题存在是因为**代码说不出为什么**——它记录建了什么，从不记录想要什么，两者的差距就是设计文档的全部内容。未回答项**逐字**作为开放问题带进草稿，在文档中标记 `INTENT UNKNOWN — inferred from implementation, not confirmed`。把推断意图呈现成已定意图是本技能整体的失效模式。（Phase 4）
R9. 这比在报告里更重要：本技能的输出不是报告而是**设计文档**，`/design-review`、`/create-epics`、`/create-stories` 会把它当作**已署名的创作意图**读——GDD 里一条编造的公式不会停留在文档错误：它会变成需求、变成 story、再变成为满足它而写的代码。（Phase 4）

### Phase 5 — 起草与 provenance
R10. 草稿四要素：捕捉**已存在什么**（机制/模式/实现）；记录**为什么存在**（与用户澄清的意图）；指出**缺什么**（未处理的边缘情况、设计缺口）；标记**后续工作**（平衡调参、缺失特性）。（Phase 5）
R11. **本技能写的每份文档必须在标题正下方盖 provenance 横幅（必填）**：
    > **Reverse-documented from implementation** — generated by `/reverse-document` from `[path]` on `[date]`, at commit `[short-sha]`. This records what the code **does**; intent marked `INTENT UNKNOWN` below was inferred, not confirmed by the author. Where this document and the code disagree, do not assume the document is the requirement.
    理由：该文档落在与人手写的设计文档相同的路径、相同的格式，**每个下游消费者同等对待两者**——没有任何环节问它从哪来。差异不是装饰性的：署名 GDD 陈述**意图**，本文档陈述**观察到的行为+推断**；两者冲突时，前者该改代码、后者该改文档——读者分不清手里是哪种，除非文档自己说。（Phase 5）
R12. 横幅在修订中保留。若人类随后确认了意图并把文档采纳为署名设计，移除横幅是他**显式的动作**——不是下次编辑的副作用。（Phase 5）

### Phase 6-7 — 审批与写入
R13. 展示草稿关键节（Overview、Mechanics、Formulas、Design Intent）+ **ADDITIONS I MADE**（按用户澄清记的意图、代码之外的边缘情况补充、标记的平衡疑虑）+ **SECTIONS MARKED AS INCOMPLETE**（未完全实现的交互/子集），再问 "May I write this to [tier 正确的输出路径]？"（Phase 6）
R14. 写入档位：`collaborative` → 等批准，用户可先要修改；`guided` → 新文件仍要问（"May I write?" 只对新文件问），目标已存在则呈现 diff 后**不等显式 yes** 继续；`autonomous` → 写盘并记录决定。（Phase 6）
R15. 获准后带元数据写文件：YAML front matter `status: reverse-documented` / `source: [path/]` / `date: [today]` / `verified-by: [User name]`；标题后加 Note 块（反向工程自既有实现、捕捉当前行为与已澄清意图、部分节可能不完整）。（Phase 7）

### Phase 8 与模板选择
R16. 写入后建议后续（`/balance-check` 核公式、为架构决策建 ADR、实现缺失边缘情况等）并问 "Would you like me to tackle any of these now?"——建议不自动执行。（Phase 8）
R17. 模板选择逻辑：`<code root>/gameplay/*` → design-doc-from-implementation（玩法机制→GDD）；`<code root>/core/*`、`<code root>/ai/*`、`<code root>/networking/*` → architecture-doc-from-code（技术系统→ADR）；`prototypes/*` → concept-doc-from-prototype（实验→概念文档）；`<code root>/ui/*` → design-doc（UI/UX→设计 spec）。（Template Selection Logic）
R18. 协作协议八步：先分析 → 问意图 → 呈现发现（突出不清区域）→ 用户澄清（意图与意外分离）→ 起草（现实+意图）→ 展示草稿 → 获准写入（Verdict: **COMPLETE** — document generated；拒绝 → Verdict: **BLOCKED** — user declined write）→ 标记后续。**绝不假设意图——记录"为什么"之前必问**。（Collaborative Protocol）

## 4. 门禁与裁决
- **裁决词**：`COMPLETE`（文档已生成）/ `BLOCKED`（用户拒写）；Phase 3b 失败时**不产出文档、不进入裁决**——直接停止并报告不可反向文档化。
- **本技能无独立门禁**：产物由 `/design-review`、`/gate-check`（各门）作为普通设计文档消费——provenance 横幅是唯一区分信号。
- **关键裁决纪律**：素材不足（R5）停止先于一切；意图未澄清（R8）以 INTENT UNKNOWN 带入而非编造。

## 5. 移植建议
- **可直接移植**：R1（tier 从配置解析不假设）、R4-R5（先问意图；零信号/不足 20 行即停）、R6-R7（空节自陈、行是形状不是配额）、R8（未答意图逐字带 INTENT UNKNOWN——"代码说不出为什么"）、R9（反向文档会被下游当需求读）、R11-R12（provenance 横幅必盖且修订保留、移除是显式动作）、R14（写入档位）。
- **需替换概念**：GDD/ADR/概念文档 → 领域等价物（API 设计文档、架构决策记录、产品规格）；`design/gdd/` 等输出路径 → 项目文档目录；`/design-review`、`/create-epics`、`/create-stories` → 文档评审、需求拆解、任务生成流程；Player Fantasy/Tuning Knobs 等游戏节 → 领域特定章节。
- **改写示例**：
  - R11 → "从代码反向生成的设计文档必须在标题下盖来源横幅：来源路径、日期、commit，并声明'本文记录代码*做什么*；与代码冲突时勿假设本文是需求'。下游把它与手写规格同等对待——没有横幅，读者分不清手里的文档冲突时该改代码还是改文档。"
  - R8 → "代码只记录建了什么、从不记录想要什么。用户未澄清的意图项逐字作为开放问题带进文档并标 INTENT UNKNOWN——把推断意图写成已定意图，会让'猜测'直接变成'需求'。"
