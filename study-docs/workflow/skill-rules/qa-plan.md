# qa-plan — QA 测试计划（AGENTS.md 移植版）

> 来源：[SKILL.md](file:///workspace/.claude/skills/qa-plan/SKILL.md) ｜ 阶段：Phase 5 ｜ 移植目标：其它项目的 AGENTS.md / CLAUDE.md / skill 定义

## 1. 技能定位
- **命令**：`/qa-plan [sprint | feature: system-name | story: path]`
- **一句话职责**：为一个 sprint / feature / 单个 story 生成结构化 QA 计划——按测试类型分类每个 story，明确哪些自动化、哪些手工验证、冒烟范围、何时引入 playtester。
- **触发前置**：范围内有 story 文件与对应 GDD；在 sprint 开始**前**运行（实现完成后才写的测试计划是验尸报告，不是计划）；配置经 `resolve_config --keys automation,workflow,qa.level,system_overrides` 解析；每个 `AskUserQuestion` 遵循 `.claude/docs/automation-modes.md`（collaborative 恒问 · guided 仅重大项 · autonomous 记录后继续）。

## 2. 数据依赖
| 方向 | 内容 | 说明 |
|------|------|------|
| 读取 | `production/sprints/` 最新文件 + `production/sprint-status.yaml`（sprint 模式主 story 清单）；`production/epics/*/story-*.md` + 各系统 `EPIC.md`（feature 模式）；story 文件（story 模式）；`design/gdd/systems-index.md`；各 story 引用的 GDD（按节读）；`docs/architecture/control-manifest.md`（存在时扫禁用模式） | 范围解析 / 系统优先级 / 可测需求与公式 / 自动化测试应守卫的模式 |
| 产出 | `production/qa/qa-plan-[sprint-slug]-[date].md`；可选回填各 story 文件 `## QA Test Cases` 节；`production/session-state/active.md` 追加一行 HTML 注释 | 计划文档；测试规格回填供 `/dev-story` 与 `/code-review` 追溯 |
| 派生智能体 | 无，主会话直接执行 | — |

**配置档位**：`workflow` 按每个 GDD 系统逐个解析（`workflow_overrides.system_overrides.<system>` 优先，否则项目值），决定从 GDD 挖多少节；`qa.level`：`minimal` → 只产最小冒烟计划（去掉 automated-test-required 行与 test-file DoD）；`standard` → 每 story 类型完整计划；`full` → 另加每系统覆盖目标。两轴独立。**任何级别都不去掉 Visual/Feel 与 UI 截图行**——测试在 `minimal` 豁免，外观不豁免。

## 3. 核心规则（逐条编号 R1、R2……）

### Phase 1 — 解析范围
R1. 范围解析：`sprint` → 读 `production/sprints/` 最新文件提取全部 story 路径，`sprint-status.yaml` 存在时作为主 story 清单、sprint 计划回退取元数据；`feature: [system-name]` → glob `production/epics/*/story-*.md` 按路径或标题过滤并查该系统 `EPIC.md`；`story: [path]` → 校验存在后加载；无参数 → `AskUserQuestion` 四选项（当前 sprint / 指定 feature / 指定 story / 整个 epic）。解析后必须报告 "Building QA plan for [N] stories in [scope]."。（Phase 1）
R2. 单个 story 文件引用了但不存在 → 记 **MISSING** 并继续处理其余 story，禁止因一个缺失文件让整个计划失败。（Phase 1）
R3. **N=0 守卫（强制）**：解析出的范围内零 story 必须停止、禁止生成计划——报告 `NOT ASSESSED — no stories in scope`，点名搜索了哪个范围、哪条路径为空，并路由：`production/sprints/` 无文件 → "Run `/sprint-plan new`"（`workflow: minimal` 无 sprint 属设计如此 → 改路由 `/qa-plan feature: [epic-slug]` 或 `/qa-plan story: [path]`）；sprint 计划存在但无 story → "Run `/create-stories [epic-slug]`"；`feature:`/`story:` 匹配为空 → 命名返回为空的 glob。没有该守卫，空范围会打印 "Building QA plan for 0 stories" 并产出空表计划——**零 story 的 QA 计划看起来和完成的 QA 计划一模一样**，而本技能是通向手工 QA 的交接门。（Phase 1）

### Phase 2 — 载入输入
R4. **先定分母再收集**：glob 范围内 story 文件并数出 **N**，然后用 targeted section greps（而非逐个全读）取字段：`Grep "^## Acceptance Criteria" -A 15`、`Grep "^> \*\*(Type|Status|Estimate)\*\*"`、`Grep "^## (Context|Dependencies)" -A 8`（sprint 模式把 glob 限定到 sprint 计划的 story 路径）。标题与 story ID 从文件名取（零读取）；实现文件与引擎注记仅在测试计划确实依赖时才全读那几个 story。（Phase 2）
R5. **绝不能把缺失节当作缺失 story**：某 story 未匹配到 `## Acceptance Criteria` 时必须全读该 story 并说明——无可测标准的 story 本身就是一个 QA 发现，不是要跳过的 story。（Phase 2）
R6. 支撑上下文一次性加载（非逐 story）：`systems-index.md` 理解系统优先级与已批准 GDD；每个被引用的唯一 GDD 按该系统 workflow 档位挖掘测试素材——`full` 挖全部 8 节；`standard` 挖必需节中测试相关子集（**Acceptance Criteria 与 Edge Cases 恒定**，定义数值规则的系统另加 **Formulas**）；`minimal` 仅 **Acceptance Criteria**。禁止加载 GDD 全文——用 Grep `^#`（content 模式）建标题图，再 offset/limit 有界读。Edge Cases 节缺失（或 minimal 下不期望有）→ 逐 GDD 注记 "No Edge Cases section found — edge case coverage will be inferred from acceptance criteria only."。（Phase 2）
R7. story 未引用 GDD → 记为 gap 但不阻塞计划，该 story 仅用验收标准分类。（Phase 2）

### Phase 3 — 分类每个 story
R8. story 头部已有 `Type:` 字段 → **原样接受，禁止重新分类或对照指标验证**——Type 由 lead-programmer 在创建 story 时设定且权威。`Type:` 缺失 → 按验收标准用分类表推断，并在报告中注明类型是推断（inferred）而非声明，标记为 gap——story 应在实现开始前显式声明 Type。（Phase 3）
R9. 分类指标表：**Logic**（计算/公式/数值阈值/状态转移/AI 决策/数据校验/buff 叠加/经济交易等可测计算）；**Integration**（两系统以上交互、信号跨系统边界、存读档往返、网络同步、持久化）；**Visual/Feel**（动画行为、VFX、shader 输出、"feels responsive"、体感时序、屏幕震动、粒子、音频同步）；**UI**（菜单、HUD、按钮、屏幕、对话框、库存面板、tooltip 等玩家界面）；**Config/Data**（仅改平衡数值/数据文件/配置，无新代码逻辑）。（Phase 3）
R10. 混合 story（如同时加公式和 UI 展示）：按承载最高实现风险的验收标准定主类型，注明次类型；Logic+Integration 与 Visual+UI 混合最常见。（Phase 3）
R11. 全部分类后在会话中产出分类汇总表，再进 Phase 4——让用户看到测试将如何分配。（Phase 3）

### Phase 4 — 生成测试计划
R12. 计划文档结构：头部（Date / Generated by / Scope / **Engine**——`engine.name` 非空前缀用之，否则 `technical-preferences.md` 的 Engine 字段，否则 "Not configured" / Sprint File）；**Test Summary** 表（每 story 一行：Type、Automated Test Required、Manual Verification Required）；**Automated Tests Required**（`qa.level: minimal` 省略整节并把 Test Summary 的自动化列留空）——每 story 给出：
   - 测试文件路径 `tests/[unit|integration]/[system]/[story-slug]_test.[ext]`；
   - 测什么：GDD Formulas 的公式/规则、每个具名状态转移或决策分支、每个应/不应发生的副作用；
   - 覆盖的边缘情形：零/最小输入（如 0 伤害、空库存）、最大/边界输入（如满级、属性上限）、非法或 null 输入（如丢失目标、死亡实体）、GDD Edge Cases 显式点名的项；
   - 估计测试数（~N unit tests）；GDD 无公式引用时注记 "test cases must be derived from acceptance criteria directly"。（Phase 4）
R13. **Manual QA Checklist**：每 story 给验证方式（Screenshot + designer sign-off / Playtest session / Manual step-through / 对比参考录像）、谁必须签核（designer / lead-programmer / qa-lead / art-director）、要采集的证据（截图/视频/playtest 笔记/并排对比）、把每条验收标准翻译成具体可证伪的手工检查项。任何标准用了主观语言（"feels"、"looks"、"seems"）→ 必须补充具体基准或 playtest 协议注记。（Phase 4）
R14. **Smoke Test Scope**：QA 交接前必须验证的关键路径——启动到主菜单不崩溃、能开新游戏/新会话、本 sprint 引入或改变的主机制、有回归风险的系统、存读档循环不丢数据（若有存档系统）、目标硬件性能在预算内无新帧尖峰。注明由开发者经 `/smoke-check` 验证。（Phase 4）
R15. **Playtest Requirements** 表（story / playtest 目标——该次会话必须回答什么问题 / 最少次数 / 目标玩家类型）；签核要求：playtest 笔记必须用 `/playtest-report` 写到 `production/qa/playtests/`（点名 story）并经 [designer / qa-lead] 审查后 story 才能标 COMPLETE。无 story 需要 playtest → 写 "No playtest sessions required for this sprint."。（Phase 4）
R16. **Definition of Done**——全部为真才算 DONE：
   - 全部验收标准经自动化结果或成文手工证据（截图/视频/带签核的 playtest 笔记）验证；
   - Logic 与 Integration story 的测试文件存在于指定路径（standard/full）；
   - Visual/Feel 与 UI story 每个触碰屏幕的保留截图在 `production/qa/evidence/`（**每级都要**）；
   - Visual/Feel story 有签核证据文档 `production/qa/evidence/[story-slug]-evidence.md`（**每级都要**）；
   - 冒烟通过（QA 交接前跑 `/smoke-check sprint`，standard/full）；无回归；
   - 代码已审查（`/code-review` 或成文同行评审）；story 更新为 `Status: Complete`（经 `/story-done`）。
   `minimal` 去掉 test-file 与 smoke 行——截图和签核行每级保留，因为外观不豁免。（Phase 4）
R17. 生成内容必须用 Phase 2 提取的真实 story 标题、GDD 公式文本和验收标准，禁止占位文本——每个测试条目都应反映这些具体 story 的真实需求。（Phase 4）

### Phase 5 — 写输出
R18. 会话中展示完整计划（过长可摘要），然后**两个选项一次问**（`AskUserQuestion` multiSelect）：写入 `production/qa/qa-plan-[sprint-slug]-[date].md`；同时把测试用例规格回填进各 story 文件的 `## QA Test Cases` 节（Recommended——启用 `/dev-story` 与 `/code-review` 追溯）。（Phase 5）
R19. 选择写入 → 完整照所生成内容写文件，禁止截断。选择回填 → 每个 Logic/Integration story 找到 `## QA Test Cases` 节替换为 Phase 4 生成的测试规格；无该节则在 `## Test Evidence` 之前追加；Visual/Feel 与 UI story 写手工验证步骤。（Phase 5）
R20. 写后给 next steps：sprint 实现开始前与团队分享计划；全部 sprint story 实现完成后跑 `/smoke-check sprint` 门禁 QA 交接（不是现在）；Logic/Integration story 在标 done 前按所列路径创建测试文件——`/story-done` 会检查它们。（Phase 5）
R21. 静默追加到 `production/session-state/active.md`（不存在则创建）：`<!-- QA-PLAN: [date] | System: [identifier] | Plan written: production/qa/qa-plan-[identifier]-[date].md -->`。（Phase 5）
R22. 收尾裁决：**COMPLETE** — QA plan written（写入被拒时 **COMPLETE** — QA plan shown, not written）；唯一其它出口是 Phase 1 的 `NOT ASSESSED — no stories in scope`。（Phase 5）

### 协作协议（collaborative 模式）
R23. 未经询问绝不写计划——Phase 5 需明确批准；分类保守：Logic 与 Integration 模糊时归 **Integration**（它同时要求单元与集成测试）；禁止发明超出验收标准与 GDD 公式支持的测试用例——公式缺失就标记，不猜测；playtest 要求是 advisory：边缘 Visual/Feel story 是否需要 playtest 由用户决定，标记但不强制；无参数时用 `AskUserQuestion` 选范围，其余阶段保持非交互——展示发现，然后一次询问批准写入。

## 4. 门禁与裁决
- **裁决词**：`COMPLETE` / `NOT ASSESSED — no stories in scope`。
- 本技能是通向手工 QA 交接的上游门：零 story 的假干净计划会把 build 送上一个什么都没测的"计划"（R3 守卫）。
- **消费方**：`/smoke-check`（读计划的 Smoke Test Scope）、`/dev-story` 与 `/code-review`（读回填的 QA Test Cases）、`/story-done`（检查测试文件存在）。

## 5. 移植建议
- **可直接移植**：R3（空范围 N=0 守卫——"零条目的计划与完成的计划无法区分"）、R4-R5（先定分母 + 定向节 grep + "缺失节≠缺失条目"）、R6（按档位有界读大文档）、R8（已声明的分类字段原样接受，权威不重判）、R13（主观标准必须配可证伪基准）、R16（DoD 分级豁免测试但不豁免外观证据）、R23（模糊归严：Logic/Integration 之间选覆盖更全的）。
- **需替换概念**：GDD Formulas/Edge Cases → 规格文档的公式与边界条件节；playtester → 用户研究员 / 外部评审者；story → 任务/工单；`/smoke-check`、`/story-done` → 对应的验收与完结流程；`production/qa/` → 项目的 QA 工件目录。
- **改写示例**：
  - R3 → "测试计划的范围解析结果为零个条目时必须停止并报告 NOT ASSESSED——点名搜索过的范围与为空的路径，并给出补齐上游工单的指引。禁止生成空表计划：零条目的计划与完成的计划在读者眼里无法区分。"
  - R23 → "分类模糊的任务一律归入要求更高验证的组合类型（同时要单元与集成测试），不得归入只要求单一测试的类型。"
