# 18 · 会话状态保存 与 选项澄清机制 —— 详解

这一篇回答两个被反复问到的问题：

1. **中断后回来怎么接着干？** —— 工作状态怎么存？为什么一启动就检查 `active.md`？是以 `active.md` 为中心吗？流程是什么？
2. **设计文档时给选项、又能输入自己的意见澄清、澄清完还能回到选项，这是怎么做到的？** —— 看起来很智能，背后是什么机制？

读完这篇你能讲清楚：

- Game-Studios 框架用**四个 hook + 一个状态文件**搭出一条"状态环"，让会话能跨崩溃、跨压缩、跨重启续上；
- 看似智能的"选项 ↔ 澄清"循环，本质是 **`AskUserQuestion` 工具 + skill 正文里的循环结构 + Explain→Capture 三步法**组合出来的，没有任何"魔法"；
- **初学者怎么把这套机制迁移到自己的项目里**：要打哪些基础、按什么顺序落地、底层技术原理是什么、不同宿主环境怎么变通。

文档结构：

- 第一部分：会话状态保存机制（怎么存、怎么恢复）
- 第二部分：选项澄清循环机制（怎么转、为什么"看起来智能"）
- 第三部分：两个机制的对照与启示
- 第四部分：迁移到其他项目框架（一步一步落地方案）
- **第五部分：production/ 目录详解（每个子目录和文件做什么、和流程什么关系、设计思路）**
- 附录：源码索引 + 小测验

## 第一部分：会话状态保存机制

### 0. 一句话定位

> **"文件即记忆，不是对话。"** —— [context-management.md](file:///workspace/.claude/docs/context-management.md)

这是整个框架的根原则。对话会被压缩、会被清空、会崩溃；磁盘上的文件不会。所以所有"重要决策"必须落盘，对话只是工作台，文件才是抽屉。

`active.md` 就是这个抽屉里**最重要的那张便签**。

---

### 1. 是以 `active.md` 为中心吗？—— 是，但准确说是"以文件为中心"

很多人问"是不是以 `active.md` 为中心"，这个说法对一半。准确的说法是：

**框架以"文件即记忆"为中心，`active.md` 是这套策略里最关键的那个文件，但不是唯一文件。**

完整的"记忆文件体系"是这样的：

| 文件 | 角色 | 谁来写 | 何时写 |
|------|------|--------|--------|
| `production/session-state/active.md` | **活的工作检查点** —— 当前任务、进度清单、关键决策、改了哪些文件、未解决问题 | skill 在每个里程碑后写 | 每写完一个 GDD 章节后；每完成一个故事卡后；每次架构决策后 |
| `design/gdd/[system].md` 等 GDD 文件 | **设计决策的最终归宿** —— 每个章节批准后立即写入，不再依赖对话 | skill 在用户批准后用 Edit 写 | 增量写入：骨架 → 一节一节填 |
| `design/registry/entities.yaml` | **跨 GDD 的事实清单** —— 锁定的数值、公式、常量，防止不同 GDD 互相打架 | `/design-system` 在第 5b 阶段更新 | GDD 完成后注册 |
| `docs/architecture/adr-*.md` | **架构决策记录** —— 每个重要技术决策一份 | `/architecture-decision` 写 | 架构阶段 |
| `production/sprints/sprint-*.md` | **冲刺计划** | `/sprint-plan` 写 | 进入生产阶段后 |
| `production/session-logs/session-log.md` | **会话审计日志** —— 每次会话结束时归档 | `session-stop.sh` hook 自动写 | 会话结束 |
| `production/stage.txt` | **当前项目阶段** —— Concept / Systems Design / Technical Setup / Pre-Production / Production | `/start` 写，`/project-stage-detect` 可更新 | 入职时定一次 |

`active.md` 的特殊地位在于：**它是最常被读写、且专门为"恢复"而设计的那个文件**。其它文件是产物，`active.md` 是"我现在在干什么"的索引。

---

### 2. `active.md` 长什么样

[context-management.md](file:///workspace/.claude/docs/context-management.md#L10-40) 规定它的内容应该包含：

- **当前任务**（在做什么）
- **进度清单**（哪些做完了，哪些没做）
- **关键决策**（这次会话里拍板的事）
- **正在改的文件**（哪些文件是"工作中"）
- **未解决问题**（卡在哪、等谁拍板）

进入 Production 及以后阶段，还要加一个**结构化状态块**供状态栏脚本解析：

```markdown
<!-- STATUS -->
Epic: Combat System
Feature: Melee Combat
Task: Implement hitbox detection
<!-- /STATUS -->
```

这块会被 [statusline.sh](file:///workspace/.claude/statusline.sh#L91-118) 解析，在终端底部状态栏显示成面包屑：`Combat System > Melee Combat > Hitboxes`。打开会话第一眼就知道焦点。

### 3. 状态环：四个 hook 把 `active.md` 围成一圈

很多人误以为"`active.md` 是大模型自己想起来去读的"。**不是**。是四个 hook 脚本在特定事件自动触发，强制把 `active.md` 推到大模型眼前。

这是关键区分（[14-四大机制协作工作流.md](file:///workspace/study-docs/14-四大机制协作工作流.md) 里也强调过）：

> **skill / agent / 门禁 是大模型主动调用的；hook 是事件自动触发的，大模型不需要知道、也无法绕过。**

四个 hook 构成的"状态环"如下：

```
       ┌─────────────────────────────────────────────┐
       │                                             │
       │   ① session-start.sh                        │
       │      会话开始时跑：检测并预览 active.md     │
       │                                             │
       ▼                                             │
   [新会话开始]                                       │
       │                                             │
       │   主会话读 active.md 全文                   │
       │   读 GDD 里已完成章节                       │
       │   从下一个未完成章节继续                    │
       │                                             │
       │   ……工作中……                               │
       │                                             │
       │   ② pre-compact.sh                          │
       │      上下文将满时跑：把 active.md 全文      │
       │   和 WIP 文件清单注入压缩摘要               │
       │                                             │
       ▼                                             │
   [上下文压缩]                                       │
       │                                             │
       │   ③ post-compact.sh                         │
       │      压缩完立刻跑：提醒大模型读 active.md   │
       │                                             │
       │   主会话读 active.md 恢复                   │
       │   继续干                                    │
       │                                             │
       │   ……工作中……                               │
       │                                             │
       ▼                                             │
   [会话结束]                                         │
       │                                             │
       │   ④ session-stop.sh                         │
       │      会话结束时跑：把 active.md 归档进      │
       │   session-log.md（不删除 active.md）        │
       │                                             │
       └─────────────────────────────────────────────┘
```

下面逐个看这四个 hook 的源码做了什么。

### 4. Hook ①：`session-start.sh` —— 为什么一启动就检查 `active.md`

[session-start.sh](file:///workspace/.claude/hooks/session-start.sh) 是 Claude Code 在**会话开始时**自动执行的脚本，由 `settings.json` 注册，**不需要大模型主动调用**。

它做了三件事（看 [session-start.sh#L57-72](file:///workspace/.claude/hooks/session-start.sh#L57-72)）：

```bash
# --- Active session state recovery ---
STATE_FILE="production/session-state/active.md"
if [ -f "$STATE_FILE" ]; then
    echo ""
    echo "=== ACTIVE SESSION STATE DETECTED ==="
    echo "A previous session left state at: $STATE_FILE"
    echo "Read this file to recover context and continue where you left off."
    echo ""
    echo "Quick summary (last 20 lines):"
    tail -20 "$STATE_FILE" 2>/dev/null
    ...
    echo "=== END SESSION STATE PREVIEW ==="
fi
```

**做的事**：

1. **检测** `production/session-state/active.md` 是否存在
2. 如果存在，**直接把最后 20 行预览**输出到会话上下文里（hook 的 stdout 会注入到 Claude 看到的会话里）
3. 告诉大模型："有上次会话留下的状态，读它来恢复"

**为什么这是 hook 而不是 skill 的责任？**

因为这是**强制性的基础设施**。如果是 skill 的责任，大模型可能"忘了"读；hook 是 Claude Code 引擎在会话启动事件里硬塞给大模型的，绕不过。这相当于"门磁"——你推门就响，不需要你"想起来让它响"。

**完整启动流程**：

```
1. 用户启动 Claude Code
2. Claude Code 引擎触发 SessionStart 事件
3. session-start.sh 自动执行：
   - 输出 git 分支、最近 5 个提交、最新 sprint、最新 milestone、未修 bug 数、TODO/FIXME 数
   - 检测 active.md，存在则预览最后 20 行 + 提示大模型读全文
4. 这些 stdout 被注入到大模型的初始上下文里
5. 大模型一睁眼就看到：
   "=== ACTIVE SESSION STATE DETECTED ===
    上次会话留下的状态在 production/session-state/active.md
    读这个文件来恢复上下文，从你停下的地方继续"
6. 大模型读 active.md 全文
7. 大模型读 GDD 文件里已完成的章节（章节里都是真实内容，不是占位符）
8. 大模型说："我看到了，上次我们做完 [章节 1-4]，接下来做 [章节 5]，要继续吗？"
```

**关键设计**：hook 不恢复状态，hook 只**提醒大模型去读状态文件**。真正"恢复"的动作是大模型自己做的（读文件 + 读 GDD）。这把"硬编码逻辑"降到最低，让大模型的灵活性来处理"上次到底停在哪"这种需要理解的事。

### 5. Hook ②：`pre-compact.sh` —— 压缩前先存盘

当上下文接近上限，Claude Code 会触发**上下文压缩**（compaction）：把前面的对话总结成摘要，腾出空间。

问题：摘要可能丢关键信息。怎么办？

[pre-compact.sh](file:///workspace/.claude/hooks/pre-compact.sh) 在压缩**之前**自动跑，把以下信息注入到"即将被摘要的上下文"里（这样摘要时这些信息会被保留）：

1. **`active.md` 全文**（如果超过 100 行则取前 100 行 + 提示）
2. **当前 git 工作树里改了哪些文件**（unstaged + staged + untracked）
3. **GDD 里的 WIP 标记**（grep `TODO|WIP|PLACEHOLDER|[TO BE|[TBD]`）
4. **恢复指令**："压缩后读 `active.md` 恢复完整工作上下文，再读上面列出的正在改的文件"
5. **写一行日志**到 `production/session-logs/compaction-log.txt`

看 [pre-compact.sh#L77-80](file:///workspace/.claude/hooks/pre-compact.sh#L77-80)：

```bash
echo "## Recovery Instructions"
echo "After compaction, read $STATE_FILE to recover full working context."
echo "Then read any files listed above that are being actively worked on."
```

**设计意图**：摘要算法是大模型内部的，框架没法控制它保留什么；但框架可以**在压缩前大喊三声"记得读 active.md"**，让这个指令进到摘要的输入里，从而进到摘要的输出里。

---

### 6. Hook ③：`post-compact.sh` —— 压缩后立刻提醒恢复

[post-compact.sh](file:///workspace/.claude/hooks/post-compact.sh) 在压缩**之后**立刻跑：

```bash
ACTIVE="production/session-state/active.md"

echo "=== Context Restored After Compaction ==="

if [ -f "$ACTIVE" ]; then
  SIZE=$(wc -l < "$ACTIVE" 2>/dev/null || echo "?")
  echo "Session state file exists: $ACTIVE ($SIZE lines)"
  echo "IMPORTANT: Read this file now to restore your working context."
  echo "It contains: current task, decisions made, files in progress, open questions."
else
  echo "No session state file found at $ACTIVE"
  echo "If you were mid-task, check production/session-logs/ for the last session audit."
fi
```

**和 `pre-compact.sh` 的分工**：

- `pre-compact.sh`：把信息塞进**摘要的输入**，让摘要有内容可保留
- `post-compact.sh`：在**摘要输出之后**立刻喊一嗓子"读 active.md"

两道保险，确保大模型压缩完不会"失忆"。

---

### 7. Hook ④：`session-stop.sh` —— 结束时归档，但不删

[session-stop.sh](file:///workspace/.claude/hooks/session-stop.sh) 在会话结束时跑。看 [session-stop.sh#L14-25](file:///workspace/.claude/hooks/session-stop.sh#L14-25)：

```bash
# --- Archive active session state on shutdown (do NOT delete) ---
# active.md persists across clean exits so multi-session recovery works.
# It is only valid to delete active.md manually or when explicitly superseded.
STATE_FILE="production/session-state/active.md"
if [ -f "$STATE_FILE" ]; then
    {
        echo "## Archived Session State: $TIMESTAMP"
        cat "$STATE_FILE"
        echo "---"
        echo ""
    } >> "$SESSION_LOG_DIR/session-log.md" 2>/dev/null
fi
```

**关键设计**：

- **归档**：把 `active.md` 内容追加到 `production/session-logs/session-log.md`，留审计痕迹
- **不删除** `active.md` —— 这样下次会话启动时 `session-start.sh` 还能检测到它、还能恢复

为什么"不删除"很重要？因为用户可能只是关掉终端，明天再开。如果他第二天打开会话，发现 `active.md` 没了，那"无缝续上"就破产了。`active.md` 必须是**跨会话持久**的，只有用户手动或新 skill 显式覆盖时才能动。

`session-stop.sh` 同时还把这次会话的 git 提交、未提交改动也写进日志：

```bash
RECENT_COMMITS=$(git log --oneline --since="8 hours ago" 2>/dev/null)
MODIFIED_FILES=$(git diff --name-only 2>/dev/null)
```

这样 `session-log.md` 就成了一份完整的"工作日记"。

### 8. 谁来写 `active.md`？—— skill 的责任

hook 只负责**提醒读**和**归档**，但 `active.md` 本身是谁写的？

是 **skill**。看 [design-system SKILL.md](file:///workspace/.claude/skills/design-system/SKILL.md#L288-298)：

```
After writing, update `production/session-state/active.md`:
- Use Glob to check if the file exists.
- If it **does not exist**: use the **Write** tool to create it.
- If it **already exists**: use the **Edit** tool to update the relevant fields.

File content:
- Task: Designing [system-name] GDD
- Current section: Starting (skeleton created)
- File: design/gdd/[system-name].md
```

每个 skill 在关键里程碑后会被要求更新 `active.md`：

- 创建骨架后
- 写完每个章节后（[design-system SKILL.md#L357-359](file:///workspace/.claude/skills/design-system/SKILL.md#L357-359)）
- GDD 完成后（[design-system SKILL.md#L766-772](file:///workspace/.claude/skills/design-system/SKILL.md#L766-772)）

**这套分工很清楚**：

| 角色 | 干什么 |
|------|--------|
| **skill** | 主动写 `active.md` —— 它知道当前进度是什么 |
| **hook** | 自动读 `active.md` 并提醒大模型 —— 它不知道进度，但能在对的时间点提醒 |
| **大模型** | 按 hook 的提醒去读 `active.md`，然后决定接下来干什么 |

### 9. 让"恢复"成为可能：增量写入策略

光有 `active.md` 不够。如果 GDD 文件本身是"等全部讨论完再一次性写"，那会话崩溃时 GDD 还是空的，`active.md` 里说"写到第 4 章"也没用——文件里什么都没有。

所以 [COLLABORATIVE-DESIGN-PRINCIPLE.md](file:///workspace/docs/COLLABORATIVE-DESIGN-PRINCIPLE.md#L476-508) 规定了**增量写入**：

```
1. Agent 创建骨架（所有章节标题，空内容）
2. 对每一节：
   a. 在对话里起草
   b. 用户批准
   c. 立刻用 Edit 把这一节写入文件
   d. 更新 active.md
   ─── 这一节的对话上下文现在可以被安全压缩 ───
   ─── 决策已经在文件里 ───
3. 会话崩溃 / 压缩后：
   - 读 GDD 文件 → 已完成章节都是真实内容
   - 读 active.md → 知道下一步该写哪节
   - 从下一节继续
```

**这是让恢复真正成立的底层支撑**。`active.md` 是索引，GDD 文件是内容，两者配合才能"无缝续上"。

为什么增量写入能省上下文？看 [context-management.md](file:///workspace/.claude/docs/context-management.md#L43-56)：

> 8 节 + 每节 2-3 轮修改的设计文档会话能累积 30-50k token 的对话。增量写入能把活上下文压到 3-5k token（只装当前这一节的讨论），因为已完成的章节都在磁盘上。

### 10. 完整的"中断后回来"流程图

把上面所有机制串起来，一次完整的"中断 → 续上"是这样：

```
═══ 第一次会话（写到一半中断） ═══

T0  用户运行 /design-system combat
T1  skill 加载，读上下文（概念文档、系统索引、依赖 GDD）
T2  skill 创建骨架 design/gdd/combat.md，写 active.md: "Task: Combat GDD, Section: skeleton"
T3  skill 走 Section A (Overview): 问问题 → 给选项 → 用户选 → 起草 → 用户批 → Edit 写入文件
T4  skill 更新 active.md: "Section: A done, next B"
T5  skill 走 Section B (Player Fantasy): ... → 写入 → 更新 active.md
T6  skill 走 Section C (Detailed Design): 起草中...
T7  ← 用户关掉终端 / 电脑断电 / 网断了

═══ 此时磁盘上的状态 ═══

design/gdd/combat.md:
  ## Overview
  [真实内容 - Section A]
  ## Player Fantasy
  [真实内容 - Section B]
  ## Detailed Design
  [To be designed]   ← 还没写
  ## Formulas
  [To be designed]
  ...

production/session-state/active.md:
  Task: Designing combat GDD
  Current section: C (Detailed Design) - in progress
  File: design/gdd/combat.md
  Sections done: A, B
  Sections pending: C, D, E, F, G, H
  Key decisions:
    - Combat is real-time, not turn-based
    - Damage = base * weapon_mult * crit_mult * resistance

═══ 第二次会话（用户回来） ═══

T8   用户重新启动 Claude Code
T9   Claude Code 引擎触发 SessionStart 事件
T10  session-start.sh 自动执行：
       - 输出 git 分支、最近提交
       - 检测到 active.md 存在
       - 输出最后 20 行预览
       - 提示"读这个文件恢复上下文"
T11  这些 stdout 注入大模型初始上下文
T12  大模型一睁眼看到提示，读 active.md 全文
T13  大模型读 design/gdd/combat.md → 看到 A、B 有真实内容，C-H 是占位符
T14  大模型：上次我们做完 Overview 和 Player Fantasy，
       下一节是 Detailed Design。要继续吗？
T15  用户：继续
T16  skill 从 Section C 接着走 —— 不重新问 A、B 的决策

═══ 中途上下文满了 ═══

T17  对话累积到 70%+
T18  Claude Code 触发压缩
T19  pre-compact.sh 自动跑：
       - 把 active.md 全文塞进压缩输入
       - 把 combat.md 的 WIP 标记列出来
       - 把 git 改动列出来
       - 输出"压缩后读 active.md 恢复"
T20  压缩执行，摘要保留了 active.md 的关键信息
T21  post-compact.sh 自动跑：
       - 提醒大模型"读 active.md 恢复工作上下文"
T22  大模型读 active.md，继续干

═══ 用户结束会话 ═══

T23  用户关闭终端
T24  session-stop.sh 自动跑：
       - 把 active.md 内容追加归档到 session-log.md
       - 记录这次会话的 git 提交和未提交改动
       - 不删除 active.md
```

**没有任何一步是"魔法"**。每一步都是 hook 脚本、skill 正文、文件系统的明确动作。

---

### 11. 设计思路总结：状态环的三层防御

为什么这套机制稳？因为它有**三层防御**，任何一层失效都有后备。

| 层 | 防什么 | 失效后备 |
|----|--------|----------|
| **第一层：文件即记忆** | 对话丢失 → 文件还在 | active.md + GDD 文件都是磁盘持久 |
| **第二层：skill 主动写** | 大模型忘了更新状态 → skill 正文强制要求 | 每个 skill 在里程碑后都有"update active.md"指令 |
| **第三层：hook 自动提醒** | 大模型忘了读状态 → hook 在事件点强制注入 | session-start / pre-compact / post-compact 三道提醒 |
| **第四层：增量写入** | GDD 整体丢失 → 已批准章节不会丢 | 每节批准即写入文件，不靠会话结束统一写 |
| **第五层：归档日志** | active.md 被误删 → 还有日志 | session-stop.sh 把 active.md 追加到 session-log.md |

这五层叠起来，才有"中断后无缝续上"的体验。

## 第二部分：选项 ↔ 澄清 循环机制

### 0. 现象描述

用户在用 `/brainstorm` 或 `/design-system` 设计文档时，经常看到这样的交互：

```
Agent: 我分析了你的需求，这里有三种战斗系统方案：

  方案 A: 实时动作战斗
    ✅ 紧张感强、有打击反馈
    ❌ 平衡难度高
  
  方案 B: 回合制战术
    ✅ 思考深度高
    ❌ 节奏慢
  
  方案 C: 即时制带暂停
    ✅ 兼顾动作和策略
    ❌ 实现复杂

  [UI 弹出选项：A / B / C]

用户: 我觉得都不太对，我想要的是像 Hades 那种，但有远程法术

Agent: 明白，让我澄清一下你的意思 —— 你是想要：
  1. 像 Hades 那样的俯视角即时战斗
  2. 同时有远程法术作为主要输出手段之一
  3. 是这样吗？还是有别的细节？

用户: 对，但法术要能蓄力

Agent: 好。基于你的澄清，我重新整理三个方向：

  方案 A': Hades 风格 + 蓄力法术主输出
  方案 B': Hades 风格 + 近战主输出 + 法术辅助
  方案 C': ...

  [UI 再次弹出选项：A' / B' / C']
```

用户的问题：**这看起来很智能，是怎么做到的？**

答案：**没有任何 AI 神秘能力，是 `AskUserQuestion` 工具 + skill 正文里的循环结构 + Explain→Capture 三步法组合出来的。**

---

### 1. 三块积木

这套机制由三块"积木"拼出来：

#### 积木 1：`AskUserQuestion` 工具 —— 自带 "Other" 出口

`AskUserQuestion` 是 Claude Code 提供的一个工具，让大模型用结构化 UI（而不是纯文本）问问题。

它的关键特性是：**用户可以选预设选项，也可以点 "Other" 输入自由文本**。

看 [COLLABORATIVE-DESIGN-PRINCIPLE.md#L332-372](file:///workspace/docs/COLLABORATIVE-DESIGN-PRINCIPLE.md#L332-372) 的说明：

> Use the `AskUserQuestion` tool to present decisions as a **selectable UI** instead
> of plain markdown text. This gives the user a clean interface to pick from options
> (or type "Other" for a custom answer).

所以"用户可以不选而输入自己的意见"这件事，**不是框架做的，是工具自带的**。框架只是规定了"什么时候必须用这个工具"。

#### 积木 2：Question → Options → Decision → Draft → Approval 协作模式

[COLLABORATIVE-DESIGN-PRINCIPLE.md](file:///workspace/docs/COLLABORATIVE-DESIGN-PRINCIPLE.md#L42-138) 规定了每个 agent 交互都要走这个五步循环：

```
1. AGENT ASKS QUESTIONS          ← 澄清性问题
2. USER PROVIDES CONTEXT         ← 用户给背景（可自由文本）
3. AGENT PRESENTS OPTIONS        ← 给 2-4 个选项 + 利弊
4. USER DECIDES                  ← 用户选（选预设 / 输入自定义）
5. AGENT DRAFTS BASED ON DECISION← 基于决策起草
6. USER REVIEWS AND REFINES      ← 用户审查、要求修改
7. AGENT UPDATES DRAFT           ← 改
8. USER APPROVES NEXT STEP       ← 批准
9. [REPEAT CYCLE FOR EACH SECTION] ← 每节循环
10. FINAL APPROVAL BEFORE WRITING ← 写文件前最终批准
```

**这是框架层面的硬规定**，每个 agent、每个 skill 都要遵守。看 [CLAUDE.md](file:///workspace/CLAUDE.md#L33-43)：

> Every task follows: **Question -> Options -> Decision -> Draft -> Approval**
> - Agents MUST ask "May I write this to [filepath]?" before using Write/Edit tools
> - Agents MUST show drafts or summaries before requesting approval

#### 积木 3：Explain → Capture 三步法

[COLLABORATIVE-DESIGN-PRINCIPLE.md#L338-349](file:///workspace/docs/COLLABORATIVE-DESIGN-PRINCIPLE.md#L338-349) 规定：

> Detailed reasoning doesn't fit in the tool's short descriptions. So use a two-step pattern:
>
> 1. **Explain first** — Write your full expert analysis in conversation text: detailed pros/cons, theory references, example games, pillar alignment. This is where the reasoning lives.
> 2. **Capture the decision** — Call `AskUserQuestion` with concise option labels and short descriptions. The user picks from the UI or types a custom answer.

**为什么这样规定？** 因为 `AskUserQuestion` 的选项 label 只能 1-5 个词，description 只能 1 句话，没法装下完整分析。所以：

- **对话文本里写完整分析**（pros/cons、理论引用、参考游戏、和 pillar 的对齐）
- **工具里只放短选项**让用户点

这样用户既能看到完整推理，又能快速点选。

---

### 2. "选项 ↔ 澄清"循环是怎么转起来的

很多人误以为"用户输入澄清后，AI 自动重新生成选项"是某个特殊机制。其实**没有特殊机制**，就是 skill 正文里写了循环结构。

看 [brainstorm SKILL.md#L112-128](file:///workspace/.claude/skills/brainstorm/SKILL.md#L112-128) 的概念选择环节：

```
AskUserQuestion(
  prompt: "Which concept resonates with you? You can pick one, combine elements, or ask for fresh directions.",
  options: [
    "Concept 1 — [Title]",
    "Concept 2 — [Title]",
    "Concept 3 — [Title]",
    "Combine elements across concepts",
    "Generate fresh directions"
  ]
)
```

注意最后两个选项：

- **"Combine elements across concepts"** —— 用户觉得没有完全对的，想混搭
- **"Generate fresh directions"** —— 用户觉得都不对，要重生成

这两个**预设的"逃离选项"**就是循环的入口。

但还有第三种逃离方式：**用户直接点 "Other" 输入自定义文本**，比如"我想要 Hades 风格但有远程法术"。

无论走哪条逃离路径，**skill 正文都规定了下一步要做什么**。`AskUserQuestion` 工具本身只返回用户的选择，"接下来怎么办"完全是 skill 正文决定的。

---

### 3. 三种"循环回选项"的标准模式

框架里有三种典型的"循环回选项"模式，每种都有 skill 正文明确写出来。

#### 模式 A：预设"重生成"选项

[brainstorm SKILL.md#L112-128](file:///workspace/.claude/skills/brainstorm/SKILL.md#L112-128) 这种。选项里直接放"Generate fresh directions"，用户点了就走重生成流程，生成完再用 `AskUserQuestion` 问一次。

```
第一次 AskUserQuestion:
  选项: [Concept 1, Concept 2, Concept 3, Combine, Generate fresh]

用户点 Generate fresh →

Agent 基于第一次的反馈重新生成 3 个概念
  → 第二次 AskUserQuestion:
       选项: [Concept 1', Concept 2', Concept 3', Combine, Generate fresh]

用户点 Concept 2' → 进入下一阶段
```

#### 模式 B：预设"修改"选项 + 循环

[brainstorm SKILL.md#L190-198](file:///workspace/.claude/skills/brainstorm/SKILL.md#L190-198) 的 pillar 确认环节是经典例子：

```
AskUserQuestion:
  Prompt: "Do these pillars feel right for your game?"
  Options:
    [A] Lock these in
    [B] Rename or reframe one
    [C] Swap a pillar out
    [D] Something else

If the user selects B, C, or D, make the revision, then use AskUserQuestion again:
  Prompt: "Pillars updated. Ready to lock these in?"
  Options:
    [A] Lock these in
    [B] Revise another pillar
    [C] Something else

Repeat until the user selects [A] Lock these in.
```

注意这里：

- **选项 [D] "Something else"** 就是给"用户想输入自定义澄清"留的口子
- skill 正文明确写了"Repeat until the user selects [A]" —— **这是显式循环**
- 每次循环里：用户给意见 → Agent 改 → 再问一次

#### 模式 C：批准环节的"修改 / 重来"

[design-system SKILL.md#L326-334](file:///workspace/.claude/skills/design-system/SKILL.md#L326-334) 的章节批准环节：

```
After the draft — in the SAME response — use AskUserQuestion.
  - Prompt: "Approve the [Section Name] section?"
  - Options:
      [A] Approve — write it to file
      [B] Make changes — describe what to fix
      [C] Start over
```

- **[A] 批准** → 写入文件，进入下一节
- **[B] 修改** → 用户描述要改什么 → Agent 改 → 再用 `AskUserQuestion` 问批准
- **[C] 重来** → 这一节从头再来

skill 正文里有句话特别关键：

> The draft and the approval widget MUST appear together in one response.
> If the draft appears without the widget, the user is left at a blank prompt
> with no path forward — this is a protocol violation.

**强制要求"草稿 + 批准 widget"必须在同一个响应里**。这避免了"Agent 写完草稿就停下，用户不知道怎么办"的尴尬。

### 4. 用户的"澄清"是怎么被处理的

用户点 "Other" 输入自由文本后，工具返回这段文本给 Agent。**接下来发生什么完全由 skill 正文决定**。

框架里常见的处理模式是**"复述确认"**：

```
用户: [Other] 我想要 Hades 风格但有远程法术

Agent: 让我确认我理解对了 —— 你想要：
  1. 俯视角即时战斗（Hades 风格）
  2. 远程法术作为主要输出手段
  
  是这样吗？还是有别的细节我漏了？

[AskUserQuestion:
  Prompt: "我理解对了吗？"
  Options:
    [A] 对，就这样
    [B] 大方向对，但有细节要补充
    [C] 不对，我重新说]

用户点 [A] → Agent 基于澄清重新整理选项
       或
用户点 [B] → 用户继续补充，Agent 再确认
       或
用户点 [B] → Agent 再次复述确认
```

**这不是工具在"理解"用户**，是 skill 正文要求 Agent 这么做。看 [COLLABORATIVE-DESIGN-PRINCIPLE.md#L654-670](file:///workspace/docs/COLLABORATIVE-DESIGN-PRINCIPLE.md#L654-670) 的 Agent 内部规则：

```
BEFORE proposing solutions:
1. Identify what's ambiguous or unspecified
2. Ask clarifying questions
3. Gather context about user's vision and constraints

WHEN proposing solutions:
1. Present 2-4 options (not just one)
2. Explain trade-offs for each
3. Reference game design theory, user's pillars, or comparable games
4. Make a recommendation but defer final decision to user

BEFORE writing files:
1. Show draft or summary
2. Explicitly ask: "May I write this to [file]?"
3. Wait for "yes"
```

这段是写在每个 agent 都要遵守的规范里的。**"识别模糊 → 澄清 → 给选项"是规定的流程，不是 AI 自发的智能**。

---

### 5. 完整的"选项 ↔ 澄清"流程图

用一个具体例子把整个循环走一遍。场景：用户在用 `/design-system` 设计战斗系统的 Section C（详细设计）。

```
═══ 第 1 轮：Agent 给选项 ═══

Agent 读上下文（概念文档、依赖 GDD、pillar）
  ↓
Agent 起草 Section C 时发现有设计选择需要拍板
  ↓
Agent 在对话文本里写完整分析（Explain）：
  "战斗系统有三种风格可选：
   A. 实时动作 - pros/cons/参考游戏/pillar 对齐
   B. 回合战术 - pros/cons/参考游戏/pillar 对齐  
   C. 即时带暂停 - pros/cons/参考游戏/pillar 对齐"
  ↓
同一个响应里调用 AskUserQuestion（Capture）：
  Prompt: "Which combat style fits your vision?"
  Options: [A, B, C]

═══ 分支 1：用户直接选 A ═══

用户点 A
  ↓
工具返回 "A" 给 Agent
  ↓
skill 正文：用户已决策 → 进入起草阶段
  ↓
Agent 起草 Section C 内容
  ↓
同一个响应里调用 AskUserQuestion：
  Prompt: "Approve Section C?"
  Options: [Approve / Make changes / Start over]

═══ 分支 2：用户点 "Other" 输入澄清 ═══

用户: [Other] 我想要 Hades 那种但有远程法术
  ↓
工具返回这段自由文本给 Agent
  ↓
skill 正文：BEFORE proposing solutions → 识别模糊 → 问澄清
  ↓
Agent 复述确认：
  "我理解对了吗？你想要：
   1. 俯视角即时战斗
   2. 远程法术作为主输出
   是这样吗？"
  ↓
AskUserQuestion: [对 / 大方向对但有补充 / 不对重说]

  ↓ 假设用户点 "大方向对但有补充"
  ↓
用户: 法术要能蓄力
  ↓
Agent: 好，明白了。基于你的澄清，我重新整理方向：
       在对话文本里写新的三个方案（Explain）
       A'. Hades 风格 + 蓄力法术主输出
       B'. Hades 风格 + 近战主 + 法术辅助
       C'. Hades 风格 + 法术近战双修
  ↓
同一个响应里 AskUserQuestion（Capture）：
  Prompt: "Which refined direction?"
  Options: [A', B', C']
  ↓
[回到第 1 轮的结构 —— 循环]
```

**关键点**：

1. 工具只负责"问 + 收集用户输入"，**循环逻辑在 skill 正文里**
2. 用户输入澄清后，**Agent 会先复述确认**（因为规范要求"BEFORE proposing solutions → 识别模糊 → 澄清"）
3. 确认后，**Agent 重新 Explain + Capture** —— 这就是"返回选项选择"
4. 循环退出条件：用户点 "Approve" 或 "Lock these in"

### 6. 为什么这套机制"看起来很智能"

因为它把几个简单的东西组合出了一个"会听话"的表象：

| 看起来 | 实际上 |
|--------|--------|
| AI 听懂了我的意思 | skill 规定 Agent 要复述确认，避免误解 |
| AI 主动重新出选项 | skill 正文写了 "Repeat until..." 循环 |
| AI 知道什么时候该问 | skill 正文每个 Phase 都标了 AskUserQuestion 调用点 |
| AI 给的选项正好是我想要的 | Agent 在对话文本里做了完整分析，UI 选项只是浓缩 |
| AI 不越权写文件 | skill 规定 "MUST ask May I write" 才能用 Write 工具 |

**底层没有任何"智能"**，全是：

- 工具能力（`AskUserQuestion` 有 "Other" 出口）
- skill 正文里的循环结构（"Repeat until..."）
- 协作规范（Question→Options→Decision→Draft→Approval）
- Explain→Capture 三步法

把"会听话"这件事拆成可工程化的步骤，是这套框架最值得学的地方。

## 第三部分：两个机制的对照与启示

### 1. 共同的设计哲学

两个机制看似不相关，其实共享同一条哲学：

> **把"对的事"从"AI 自觉"变成"机制强制"。**

- 状态保存：不靠 AI"想起来"读 active.md，靠 hook 强制提醒
- 选项澄清：不靠 AI"自觉"问澄清，靠 skill 正文规定的循环结构

**这是工程化 AI 编排的核心思想**。AI 是概率系统，会忘、会跳、会自作主张。把关键约束落到 hook、skill 正文、工具调用规范里，让"对的事"成为唯一路径。

### 2. 两个机制的对照表

| 维度 | 状态保存机制 | 选项澄清机制 |
|------|--------------|--------------|
| **触发方** | hook（事件自动） | skill 正文（大模型按脚本调） |
| **核心载体** | `active.md` 文件 | `AskUserQuestion` 工具 |
| **循环结构** | 状态环（4 个 hook 围一圈） | Question→Options→Decision→Draft→Approval |
| **退出条件** | 会话结束（但 active.md 不删） | 用户点 Approve / Lock in |
| **强制层** | hook 在 settings.json 注册，绕不过 | skill 正文规定 "MUST" / "Repeat until" |
| **失败兜底** | session-log.md 归档 | "Start over" 选项 + 复述确认 |

### 3. 给编排者的启示

1. **关键状态必须落盘**。对话不是记忆，文件才是。任何"重要决策"都要在做出后立即写入文件。
2. **恢复动作靠 hook 提醒，不靠 AI 自觉**。会话启动、压缩前后是三个关键提醒点。
3. **增量写入比一次性写入稳**。每节批准即落盘，崩溃也只丢"当前在写的那一节"。
4. **选项 UI 要留"逃离口"**。预设选项 + "Other" 自由输入 + "重生成" / "修改" 选项，三管齐下覆盖用户的所有"不按套路出牌"。
5. **循环逻辑写在 skill 正文里**。工具不提供循环，循环靠 skill 正文的 "Repeat until..." 显式写出来。
6. **澄清后先复述确认**。避免 AI 误解用户意图，复述一遍让用户确认，再进入下一轮。

## 第四部分：迁移到其他项目框架 —— 一步一步落地方案

这一部分是写给**初学者**的。你想把"中断续上"和"选项澄清"这两套机制搬到自己的项目里（不一定是游戏开发，可能是 SaaS、文档站点、数据分析、嵌入式），怎么做？

下面给出一份**可照着抄的 12 步落地计划**，每步都说明做什么、为什么、关键代码长什么样、容易踩什么坑。

---

### 1. 迁移前的能力自检

不是所有 AI 编程环境都能完整跑这套机制。先做自检：

| 能力 | 用途 | Claude Code | Cursor | Cline / Continue | 纯 ChatGPT / Claude 网页版 |
|------|------|-------------|--------|-------------------|---------------------------|
| **Hook 系统**（事件触发脚本） | 状态环的 4 个 hook | ✅ 完整支持 | ⚠️ 部分支持（.rules 等） | ⚠️ 部分支持 | ❌ 不支持 |
| **`AskUserQuestion` 工具**（带 Other 出口的结构化选项） | 选项 ↔ 澄清循环 | ✅ 完整支持 | ❌ 需用纯文本模拟 | ⚠️ 需用纯文本模拟 | ❌ 需用纯文本模拟 |
| **Skill / slash 命令系统** | 承载循环逻辑 | ✅ 完整支持 | ⚠️ 有 .cursorrules 但无命令 | ⚠️ 有 rules 但无命令 | ❌ 不支持 |
| **文件读写工具** | 落盘 | ✅ | ✅ | ✅ | ❌（只能复制粘贴） |

**结论**：

- **在 Claude Code 里**：可以完整迁移，下面的 12 步全部适用。
- **在 Cursor / Cline 等**：状态保存可以迁（用 rules 文件 + 项目脚本手动触发），选项澄清只能用**纯文本模拟**（见 4.6 节"变体"）。
- **在纯网页大模型**：两套机制都只能迁"思想"——靠人工把决策落盘、靠人工复述确认。本文第四部分对这类环境帮助有限。

**这一节只针对 Claude Code 宿主展开**，并在 4.6 节给出其它环境的变体做法。

---

### 2. 需要先建立的基础

初学者最容易直接抄代码，结果抄完跑不通。**先打四个基础**：

#### 基础一：心智 —— 文件即记忆

如果你不内化"对话是短暂、文件是持久"，下面所有代码都会变形。最常见的变形是：

- 把决策写在对话里就以为存住了 → 压缩后丢失
- 让 AI 在对话末尾总结状态 → 压缩时连总结也丢了
- 让 hook 去恢复状态（执行业务逻辑）→ hook 变复杂、难维护

**正确心智**：对话只用来讨论；任何"未来还要用"的东西必须立刻写进文件；hook 只负责提醒，不负责恢复。

#### 基础二：目录骨架

按 Game-Studios 的约定建好以下空目录（路径可改，但结构要稳定）：

```
your-project/
├── CLAUDE.md                          # 项目根配置（写协作协议）
├── .claude/
│   ├── settings.json                  # hook 注册
│   ├── hooks/
│   │   ├── session-start.sh           # 待写
│   │   ├── pre-compact.sh             # 待写
│   │   ├── post-compact.sh            # 待写
│   │   └── session-stop.sh            # 待写
│   └── statusline.sh                  # 可选：状态栏
└── production/
    ├── session-state/
    │   └── .gitkeep                   # active.md 会出现在这里
    └── session-logs/
        └── .gitkeep                   # 日志归档目录
```

**为什么是 `production/` 而不是 `state/`**：因为这套约定假设了"项目有生产阶段产物"。你完全可以改成 `state/` 或 `.state/`，但**一旦定下来就不要再改**——hook 脚本和 skill 指令里都写死了路径。

#### 基础三：配置文件 CLAUDE.md

CLAUDE.md 是 Claude Code 在每个会话开始时自动加载的项目级 prompt。在这里写明协作协议，让大模型一开始就知道规矩。最小骨架：

```markdown
# Your Project

## Collaboration Protocol

**User-driven collaboration, not autonomous execution.**
Every task follows: Question -> Options -> Decision -> Draft -> Approval

- Agents MUST ask "May I write this to [filepath]?" before using Write/Edit
- Agents MUST show drafts before requesting approval
- Agents MUST update production/session-state/active.md after each milestone

## Context Management

The file is the memory, not the conversation. See .claude/docs/context-management.md.
```

**关键**：把"必须更新 active.md"写进 CLAUDE.md，让它成为大模型一启动就知道的硬规则。

#### 基础四：上下文管理小文档

在 `.claude/docs/context-management.md` 写一份简短的上下文管理规范（可以直接参考 Game-Studios 的 [context-management.md](file:///workspace/.claude/docs/context-management.md)）。这文档会被 skill 正文引用，是大模型理解"为什么要增量写入"的依据。

### 3. 底层技术原理（迁移前要懂的 4 条）

下面 12 步会用到这些原理，先理解再动手：

#### 原理 1：事件驱动 vs 主动调用

| 类型 | 谁触发 | 大模型能否绕过 | 适用场景 |
|------|--------|----------------|----------|
| **Hook** | 宿主引擎在事件点自动跑 | **不能**（除非删 settings.json） | 强制性提醒、校验、归档 |
| **Skill / Agent** | 大模型主动用工具调 | 能（忘了调就跳过） | 业务流程、决策、起草 |
| **Rules / CLAUDE.md** | 大模型读到时"自觉遵守" | 能（probability-driven） | 软约束、风格、习惯 |

**迁移要点**：把"必须发生的事"放 hook，把"流程怎么走"放 skill，把"风格偏好"放 rules。**别把强约束放 rules**——大模型会忘。

#### 原理 2：文件 = 状态机的快照

把会话想象成一个状态机：

```
[空] → [骨架已建] → [第1节已写] → [第2节已写] → ... → [完成]
```

每次"写文件"就是给状态机拍一张快照。`active.md` 是"当前在哪个状态的文字描述"，GDD（或你项目里的对应物）是"状态对应的真实数据"。

**迁移要点**：每次状态变化都要**同时**更新 active.md（索引）和业务文件（数据）。只更新一个，恢复时会缺一条腿。

#### 原理 3：工具能力 + 正文循环 = "智能"行为

大模型本身没有"循环回选项"的能力。这件事是：

- `AskUserQuestion` 工具提供"问 + 收任意输入"的能力（**基础设施**）
- skill 正文写 "Repeat until..."（**业务逻辑**）
- 两者相加，出现"用户澄清后 AI 重新出选项"的表象（**涌现**）

**迁移要点**：不要指望"换个更好的模型"就能有这能力。**循环逻辑必须显式写在 skill 正文里**，否则再强的模型也会在用户输入 Other 后直接执行，而不是回到选项循环。

#### 原理 4：增量写入 = 可恢复性

如果文件是"等全部讨论完再一次性写"，崩溃时文件就是空的。增量写入让"已批准的章节"立即落盘，崩溃也只丢"正在讨论的那一节"。

**迁移要点**：把"等到最后再写"的本能彻底改掉。每完成一个小单元就写一次。这同时还能省上下文——已写完的章节可以从对话里安全压缩掉。

### 4. 12 步落地计划

#### Step 1：选定宿主环境并确认 hook 支持

按 4.1 节自检。**只在 Claude Code（或同等级别的支持 hook 的环境）里继续往下走**。其它环境看 4.6 节变体。

**完成标志**：你能在 `.claude/settings.json` 里写一个 `"SessionStart"` hook，启动会话时看到它的 stdout 出现在大模型上下文里。

#### Step 2：建目录骨架

按 4.2 节建好目录。**注意**：`production/session-state/` 和 `production/session-logs/` 要用 `.gitkeep` 占位，否则空目录不会被 git 跟踪。

**完成标志**：`ls production/session-state/` 不报错（虽然目录是空的）。

#### Step 3：定义 active.md 模板（适配你的领域）

这是**整个迁移最关键的一步**。模板决定后续所有 hook 和 skill 怎么读写。

**通用模板**（适合任何项目）：

```markdown
# Active Session State

> 最后更新：[timestamp]
> 项目阶段：[你的项目阶段，如：调研 / 设计 / 开发 / 测试 / 上线]

## Current Task
[一句话描述当前在做什么]
- 工作单元：[你的领域的工作单元名 —— 如 feature / chapter / module / section]
- 当前步骤：[当前在工作的具体步骤]
- 文件：[正在改的文件路径]

## Progress Checklist
- [x] [已完成项 1]
- [x] [已完成项 2]
- [ ] [未完成项 1]
- [ ] [未完成项 2]

## Key Decisions This Session
- [决策 1]：[理由]
- [决策 2]：[理由]

## Files In Progress
- [path/to/file.ext] —— [在改什么]
- [path/to/another.ext] —— [在改什么]

## Open Questions
- [问题 1] —— 等 [谁] 拍板
- [问题 2] —— 卡在 [什么] 上
```

**领域适配示例**：

| 领域 | "工作单元" 填什么 | "文件" 填什么 |
|------|-------------------|---------------|
| 软件开发 | Feature / Story / Task | `src/...`、`tests/...` |
| 文档/写作 | Chapter / Section | `manuscript/ch01.md` |
| 数据分析 | Question / Hypothesis | `notebooks/02-eda.ipynb` |
| 设计 | Screen / Component | `design/specs/login.md` |
| 研究 | Section / Sub-question | `paper/related-work.md` |

**可选**：如果你的项目有"阶段"概念，在 active.md 顶部加一个状态块供状态栏脚本解析：

```markdown
<!-- STATUS -->
Project: [project name]
Phase: [phase]
Focus: [current focus]
<!-- /STATUS -->
```

**完成标志**：模板定下来，路径确定为 `production/session-state/active.md`。

#### Step 4：写 `session-start.sh`（启动时检测并预览）

**这一步是"为什么一启动就检查 active.md"的答案**。

最小可用版本：

```bash
#!/bin/bash
# 会话启动时：检测并预览 active.md

echo "=== Project Session Context ==="

# 当前分支（如果是 git 项目）
BRANCH=$(git rev-parse --abbrev-ref HEAD 2>/dev/null)
[ -n "$BRANCH" ] && echo "Branch: $BRANCH"

# 最近提交
if [ -n "$BRANCH" ]; then
    echo ""
    echo "Recent commits:"
    git log --oneline -5 2>/dev/null | while read -r line; do
        echo "  $line"
    done
fi

# --- 关键：检测 active.md ---
STATE_FILE="production/session-state/active.md"
if [ -f "$STATE_FILE" ]; then
    echo ""
    echo "=== ACTIVE SESSION STATE DETECTED ==="
    echo "A previous session left state at: $STATE_FILE"
    echo "Read this file to recover context and continue where you left off."
    echo ""
    echo "Quick summary (last 20 lines):"
    tail -20 "$STATE_FILE" 2>/dev/null
    TOTAL_LINES=$(wc -l < "$STATE_FILE" 2>/dev/null)
    if [ "$TOTAL_LINES" -gt 20 ]; then
        echo "  ... ($TOTAL_LINES total lines — read the full file to continue)"
    fi
    echo "=== END SESSION STATE PREVIEW ==="
fi

echo "==================================="
exit 0
```

**关键设计**：

1. **不恢复，只提醒** —— hook 只输出"有状态文件，去读它"，不解析、不业务逻辑
2. **预览 20 行** —— 让大模型一眼看到状态大概，决定要不要读全文
3. **明确喊"读全文"** —— 用指令性语言，避免大模型偷懒只看预览

**完成标志**：删除 active.md 时启动会话看不到提示；放一个测试 active.md 进去后启动会话能看到预览。

#### Step 5：写 `pre-compact.sh`（压缩前注入）

```bash
#!/bin/bash
# 压缩前：把 active.md 全文 + WIP 文件清单注入摘要输入

echo "=== SESSION STATE BEFORE COMPACTION ==="
echo "Timestamp: $(date)"

STATE_FILE="production/session-state/active.md"
if [ -f "$STATE_FILE" ]; then
    echo ""
    echo "## Active Session State (from $STATE_FILE)"
    STATE_LINES=$(wc -l < "$STATE_FILE" 2>/dev/null | tr -d ' ')
    if [ "$STATE_LINES" -gt 100 ] 2>/dev/null; then
        head -n 100 "$STATE_FILE"
        echo "... (truncated — $STATE_LINES total lines, showing first 100)"
    else
        cat "$STATE_FILE"
    fi
else
    echo ""
    echo "## No active session state file found"
fi

# git 改动
echo ""
echo "## Files Modified (git working tree)"
CHANGED=$(git diff --name-only 2>/dev/null)
STAGED=$(git diff --staged --name-only 2>/dev/null)
UNTRACKED=$(git ls-files --others --exclude-standard 2>/dev/null)
[ -n "$CHANGED" ] && echo "Unstaged:" && echo "$CHANGED" | sed 's/^/  - /'
[ -n "$STAGED" ] && echo "Staged:" && echo "$STAGED" | sed 's/^/  - /'
[ -n "$UNTRACKED" ] && echo "Untracked:" && echo "$UNTRACKED" | sed 's/^/  - /'
[ -z "$CHANGED$STAGED$UNTRACKED" ] && echo "  (no uncommitted changes)"

# WIP 标记扫描（按你的项目改 glob 模式）
echo ""
echo "## Work-In-Progress Files"
WIP_FOUND=false
for f in docs/*.md src/**/*.md; do
    [ -f "$f" ] || continue
    INCOMPLETE=$(grep -n -E "TODO|WIP|PLACEHOLDER|\[TO BE|\[TBD\]" "$f" 2>/dev/null)
    if [ -n "$INCOMPLETE" ]; then
        WIP_FOUND=true
        echo "  $f:"
        echo "$INCOMPLETE" | sed 's/^/    /'
    fi
done
[ "$WIP_FOUND" = false ] && echo "  (no WIP markers found)"

# 恢复指令
echo ""
echo "## Recovery Instructions"
echo "After compaction, read $STATE_FILE to recover full working context."
echo "Then read any files listed above that are being actively worked on."
echo "=== END SESSION STATE ==="

# 写日志
mkdir -p production/session-logs 2>/dev/null
echo "Context compaction occurred at $(date)." >> production/session-logs/compaction-log.txt 2>/dev/null

exit 0
```

**关键设计**：

1. **active.md 全文（截断 100 行）** —— 让摘要算法有内容可保留
2. **git 改动 + WIP 标记** —— 让摘要知道哪些文件是"工作中"
3. **明确喊"压缩后读 active.md"** —— 这句指令会进摘要输入，从而进摘要输出

**完成标志**：上下文快满时触发压缩，能在压缩前的输出里看到 active.md 全文。

#### Step 6：写 `post-compact.sh`（压缩后提醒）

```bash
#!/usr/bin/env bash
# 压缩后：立刻提醒大模型读 active.md

ACTIVE="production/session-state/active.md"

echo "=== Context Restored After Compaction ==="

if [ -f "$ACTIVE" ]; then
  SIZE=$(wc -l < "$ACTIVE" 2>/dev/null || echo "?")
  echo "Session state file exists: $ACTIVE ($SIZE lines)"
  echo "IMPORTANT: Read this file now to restore your working context."
  echo "It contains: current task, decisions made, files in progress, open questions."
else
  echo "No session state file found at $ACTIVE"
  echo "If you were mid-task, check production/session-logs/ for the last session audit."
fi

echo "========================================="
```

**和 pre-compact.sh 的分工**：pre 把信息塞进摘要输入，post 在摘要输出后喊一嗓子。两道保险。

**完成标志**：压缩完成后立刻看到提醒。

#### Step 7：写 `session-stop.sh`（结束时归档不删除）

```bash
#!/bin/bash
# 会话结束：归档 active.md 到日志，但不删除

TIMESTAMP=$(date +%Y%m%d_%H%M%S)
SESSION_LOG_DIR="production/session-logs"
mkdir -p "$SESSION_LOG_DIR" 2>/dev/null

# 归档（追加，不覆盖）
STATE_FILE="production/session-state/active.md"
if [ -f "$STATE_FILE" ]; then
    {
        echo "## Archived Session State: $TIMESTAMP"
        cat "$STATE_FILE"
        echo "---"
        echo ""
    } >> "$SESSION_LOG_DIR/session-log.md" 2>/dev/null
fi

# 记录这次会话的 git 活动
RECENT_COMMITS=$(git log --oneline --since="8 hours ago" 2>/dev/null)
MODIFIED_FILES=$(git diff --name-only 2>/dev/null)
if [ -n "$RECENT_COMMITS" ] || [ -n "$MODIFIED_FILES" ]; then
    {
        echo "## Session End: $TIMESTAMP"
        [ -n "$RECENT_COMMITS" ] && echo "### Commits" && echo "$RECENT_COMMITS"
        [ -n "$MODIFIED_FILES" ] && echo "### Uncommitted Changes" && echo "$MODIFIED_FILES"
        echo "---"
        echo ""
    } >> "$SESSION_LOG_DIR/session-log.md" 2>/dev/null
fi

exit 0
```

**关键设计**：**归档不删除**。`active.md` 必须跨会话持久。用户可能明天才回来打开会话，那时还要靠它恢复。

**完成标志**：会话结束后 `active.md` 还在，`session-log.md` 多了一段归档。

#### Step 9：在你的 skill / 工作流里写"更新 active.md"指令

hook 只负责提醒读，**写**是 skill 的责任。在你每个 skill 的 SKILL.md 里加类似这样的指令：

```markdown
## Session State Updates

After each milestone (章节完成 / 决策做出 / 文件批准), update production/session-state/active.md:

- Use Glob to check if the file exists
- If it does NOT exist: use Write to create it (use the template)
- If it already exists: use Edit to update the relevant fields

Fields to update:
- Current Task: [一句话]
- Progress Checklist: 勾掉完成项
- Key Decisions: 加新决策
- Files In Progress: 加/删正在改的文件
- Open Questions: 加/删未解问题
```

**关键**：把"更新 active.md"作为 skill 的**强制步骤**，不是"记得就做"。

**完成标志**：跑一遍你的 skill，每完成一节都能看到 active.md 被更新。

#### Step 10：写协作协议文档

在 `docs/COLLABORATION-PROTOCOL.md`（或 CLAUDE.md 里）写明选项澄清的规则。最小内容：

```markdown
# Collaboration Protocol

## Question → Options → Decision → Draft → Approval

Every decision point follows this cycle:

1. **Question** — Agent asks clarifying questions
2. **Options** — Agent presents 2-4 options with pros/cons in conversation text
3. **Decision** — User picks an option OR types custom input via "Other"
4. **Draft** — Agent drafts based on the decision
5. **Approval** — Agent calls AskUserQuestion in the SAME response with:
   - [A] Approve — write to file
   - [B] Make changes — describe what to fix
   - [C] Start over
6. **Loop** — Repeat from step 4 until user picks [A]

## Explain → Capture Pattern

When presenting options:
- **Explain first** in conversation text: full pros/cons, references, reasoning
- **Capture** with AskUserQuestion: short option labels (1-5 words) + 1-sentence descriptions

## File Write Approval

Agents MUST ask "May I write this to [filepath]?" before Write/Edit.
NEVER write a file without explicit user approval.
```

**完成标志**：CLAUDE.md 或协作协议文档里能看到上述内容。

### 6. 不同宿主环境的迁移变体

#### 变体 A：Claude Code（完整迁移）

按上面 12 步完整跑。所有机制都能用。

#### 变体 B：Cursor / Cline（部分迁移）

Cursor 没有完整的 hook 系统，但有 `.cursorrules` 和 `.rules`。变通做法：

- **状态保存**：在 `.cursorrules` 里写"每次完成里程碑后更新 `production/session-state/active.md`"。这是**软约束**，大模型可能忘，需要用户偶尔提醒。
- **压缩前后**：Cursor 没有压缩事件，但有"上下文清理"。在 `.cursorrules` 里写"清理上下文前先读 active.md 全文"。同样软约束。
- **选项澄清**：Cursor 没有 `AskUserQuestion` 工具，只能用**纯文本模拟**：

  ```
  Agent 输出：
    请从以下选项中选择，或输入"OTHER: 你的意见"进行澄清：
    [A] ...
    [B] ...
    [C] ...
    [OTHER] 我想要...
    
    如果选 OTHER，我会复述确认你的意思，然后重新出选项。
  ```

  这种纯文本模拟**没有 UI 那么清晰**，但循环逻辑一样能跑。

#### 变体 C：纯网页大模型（只能迁思想）

网页版（ChatGPT、Claude.ai）没有 hook、没有工具调用、不能读写文件。**两套机制只能迁"思想"**：

- **状态保存**：让用户自己维护一个 `state.md` 文件，每次开始粘贴给 AI，每次结束让 AI 总结后用户复制回文件。
- **选项澄清**：让 AI 输出"选项 A/B/C 或输入 OTHER"，用户手动走循环。

**这种环境不推荐**——失去自动化，价值大幅下降。

#### 变体 D：自定义 Agent 框架（LangChain / AutoGen / CrewAI 等）

这些框架一般支持工具调用和事件回调，可以**完整实现**两套机制：

- 用框架的"tool"接口实现 `update_active_md` 工具，每次里程碑后让 Agent 调
- 用框架的"event hook"或"callback"实现 session-start/pre-compact/post-compact/stop 四个事件
- 用框架的"human-in-the-loop"接口实现选项澄清循环

**关键**：别把 hook 逻辑写进 Agent 的 prompt 里。Hook 必须是**框架层面**的回调，Agent 绕不过。

### 8. 常见坑与避坑指南

#### 坑 1：把 active.md 写成全量历史

**症状**：active.md 越写越长，几百行，最后 hook 预览的 20 行都是过期信息。

**原因**：把"做了什么"全写进去，而不是只写"现在在做什么"。

**避坑**：active.md 是**当前快照**，不是日志。日志交给 `session-log.md`（由 session-stop.sh 归档）。每次更新 active.md 用 Edit **替换**对应字段，不要追加。

#### 坑 2：在 hook 里做业务逻辑

**症状**：session-start.sh 写了几百行，调用 API、解析文件、生成报告。

**原因**：误以为 hook 应该"恢复"状态。

**避坑**：hook 只做三件事 —— **检测、预览、提醒**。恢复是大模型的事。Hook 越简单越稳。

#### 坑 3：会话结束后删 active.md

**症状**：每次启动都没有状态预览，恢复机制失效。

**原因**：在 session-stop.sh 里 `rm active.md`，或用户手动删了。

**避坑**：**永远归档不删除**。只有用户手动或新 skill 显式覆盖时才能动 active.md。

#### 坑 4：skill 不强制更新 active.md

**症状**：跑完 skill，active.md 没动过。

**原因**：skill 正文里写"建议更新 active.md"而不是"必须更新"。

**避坑**：用 "MUST update" / "After [milestone], update active.md" 这种**强制指令性语言**。在大模型语境里，"should" 等于 "may not"。

#### 坑 5：选项 UI 没留 "Other" 出口

**症状**：用户有自定义意见但只能选预设，被迫选最接近的，结果 AI 误解意图。

**原因**：在 AskUserQuestion 里只放了 2-4 个预设选项，没意识到用户可以点 Other。

**避坑**：`AskUserQuestion` 工具**自带 Other 出口**，你不用手动加。但要在 skill 正文里写"用户选 Other 后走澄清流程"，否则 AI 收到 Other 输入会直接当决策执行。

#### 坑 6：循环没写退出条件

**症状**：用户一直点"修改"，AI 一直改一直问，永远不退出。

**原因**：skill 正文写了"Repeat"但没写"until"。

**避坑**：每个循环都要有明确退出条件。比如 "Repeat until user selects [A] Lock in"。如果担心用户陷入死循环，加一个"超过 N 轮后建议妥协"的兜底。

#### 坑 7：草稿和批准分开两个响应

**症状**：Agent 输出草稿后停下，用户面对空白提示符不知道怎么办。

**原因**：Agent 把"起草"和"问批准"分两次响应。

**避坑**：在 skill 正文里强制规定"草稿 + AskUserQuestion 批准 widget 必须在同一个响应里"。这是 Game-Studios 明确写的 protocol violation 防范。

#### 坑 8：增量写入粒度太粗

**症状**：写一个大文档等到全部讨论完才一次性写入，中途崩溃全丢。

**原因**：怕频繁写文件"打扰"用户。

**避坑**：每完成一个可独立的小单元（一节、一个决策、一个函数）就写一次。用户被问"May I write to file?"不会觉得打扰，反而有掌控感。

## 第五部分：production/ 目录详解

### 3. 逐项详解

#### 3.1 `stage.txt` —— 当前项目阶段

**内容**：单行文本，如 `Concept` / `Systems Design` / `Technical Setup` / `Pre-Production` / `Production` / `Polish` / `Release` / `Live`

**谁写**：[`/gate-check` skill](file:///workspace/.claude/skills/gate-check/SKILL.md#L30-31) 在门禁通过时写

```
echo -n "Production" > production/stage.txt
```

**谁读**：

- [`.claude/statusline.sh`](file:///workspace/.claude/statusline.sh#L33-38) 第一优先级读它，显示在状态栏
- 各 skill 读它判断"现在该不该跑这个 skill"（如 `/release-checklist` 不该在 Concept 阶段跑）

**为什么是单行**：

- 解析最简单（`head -1`）
- 写入最简单（`echo -n`）
- 避免格式漂移
- 没有歧义

**没有 stage.txt 怎么办**：[statusline.sh](file:///workspace/.claude/statusline.sh#L40-87) 有 fallback —— 通过检测 `design/gdd/game-concept.md` 是否存在、`docs/architecture/adr-*.md` 是否存在、`src/` 里源文件数等**自动推断**阶段。这是"显式优先 + 自动推断兜底"的双层设计。

---

#### 3.2 `review-mode.txt` —— review 深度配置

**内容**：单行，三选一：

- `lean` —— 跳过自动门禁（单人开发默认）
- `full` —— 跑所有总监级门禁（团队开发）
- `solo` —— 完全跳过

**谁写**：[`/sprint-plan` skill](file:///workspace/.claude/skills/sprint-plan/SKILL.md#L23-29) 在第一次跑时用 `AskUserQuestion` 问用户，选完写入文件

**谁读**：**所有带门禁的 skill**（`/sprint-plan`、`/gate-check`、`/qa-plan`、`/story-done`、`/milestone-review` 等）启动时第一件事就是读它，决定是否 spawn 总监级子 agent

**为什么单独抽出来**：

- review 深度是**项目级偏好**，不是单次决策
- 不抽出来的话，每次跑 skill 都要问一遍用户，体验差
- 写文件后所有 skill 共享同一设置

**设计经验**：这是个典型的"配置文件"模式 —— **一次决策、多次复用**。你的项目里如果也有"全局偏好"（如代码风格、测试严格度、目标平台），都可以用同样的单文件配置。

---

#### 3.3 `sprint-status.yaml` —— 故事状态机

**内容**：YAML 格式，每个 story 一个条目，含状态、文件路径、优先级、阻塞原因等

```yaml
updated: 2026-03-15
sprint: sprint-03
stories:
  - id: combat-damage-calc
    name: "Damage calculation"
    file: "production/epics/combat/story-combat-damage-calc.md"
    priority: must-have
    status: in-progress      # backlog | ready-for-dev | in-progress | review | done | blocked
    blocked_reason: ""
  - id: combat-hitbox
    ...
```

**谁写**：[`/sprint-plan` skill](file:///workspace/.claude/skills/sprint-plan/SKILL.md#L152-227) 创建；[`/dev-story` skill](file:///workspace/.claude/skills/dev-story/SKILL.md#L130) 在故事开始时把 status 改为 `in-progress`；[`/story-done` skill](file:///workspace/.claude/skills/story-done/SKILL.md) 在故事完成时改为 `done`

**谁读**：

- `/sprint-status` —— 30 行快速快照
- `/dev-story` —— 找当前活跃故事
- `/story-done` —— 找故事依赖
- `/help` —— 推荐下一步
- `/retrospective` —— 统计完成率

**为什么是 YAML 不是 markdown**：

- **机器可读**：skill 不用正则解析 markdown，直接 `yaml.load`
- **状态原子化**：改一个 status 字段不影响其它内容
- **避免漂移**：markdown 表格里改一行可能破坏对齐，YAML 不会
- **可 diff**：git diff YAML 看状态变化一目了然

**和 sprint-[N].md 的分工**：

| 文件 | 角色 | 谁读 |
|------|------|------|
| `sprints/sprint-03.md` | **人读**的冲刺计划（叙事、估时、依赖分析） | 用户、PM 角色读 |
| `sprint-status.yaml` | **机读**的故事状态 | 所有 skill 读 |

这是"双层源"模式：人读的叙事文档 + 机读的状态文件，两者并存。skill 优先读 yaml，fallback 到 markdown。

#### 3.4 `sprints/` —— 冲刺计划

**内容**：每个冲刺一份 markdown，含目标、故事列表、估时、风险、依赖

**谁写**：[`/sprint-plan` skill](file:///workspace/.claude/skills/sprint-plan/SKILL.md)

**和流程的关系**：进入 Pre-Production 后才有冲刺。`/gate-check` 在"Vertical Slice → Production"门禁检查"至少 1 份 sprint plan"。

**子文件 `sprint-NN-retrospective.md`**：retrospective skill 可能写在这里作为备选位置，主位置是 `retrospectives/`。

#### 3.5 `milestones/` —— 里程碑定义和评审

**内容**：

- `milestone-[name].md` —— 里程碑定义（包含哪些 sprint、目标、退出条件）
- `milestone-[name]-review.md` —— 评审报告（由 `/milestone-review` 写）

**谁读**：

- `/sprint-plan` —— 读当前里程碑决定下一个 sprint 该干什么
- `/milestone-review` —— 读里程碑定义 + 所有 sprint 报告，生成评审
- `/release-checklist` —— 读里程碑确定该版本包含哪些特性

**和流程的关系**：里程碑是"多个 sprint 的容器"。Alpha / Beta / Gold 都是里程碑。

#### 3.6 `epics/` —— 史诗和故事文件

**结构**：每个 epic 一个目录，下面有 EPIC.md 和多个 story-[slug].md

```
production/epics/
├── combat/
│   ├── EPIC.md
│   ├── story-combat-damage-calc.md
│   ├── story-combat-hitbox.md
│   └── story-combat-weapon-types.md
├── movement/
│   ├── EPIC.md
│   └── story-movement-locomotion.md
└── ui/
    └── ...
```

**谁写**：

- `/create-epics` —— 写 EPIC.md
- `/create-stories` —— 写 story-*.md

**每个 story 文件含**：

- GDD 需求 ID（不复制 GDD 内容，只引用 TR-ID —— 让引用"保鲜"）
- ADR 引用（只引 Accepted 的 ADR，Proposed 的会让故事 Status: Blocked）
- 验收标准
- 依赖列表（其它 story 必须先 done）
- 状态字段（Status: Ready / In Progress / Complete / Blocked）
- Last Updated 字段（用于检测陈旧）

**为什么按 epic 分目录**：路径驱动的规则系统。`.claude/rules/` 可以按路径生效 —— 例如 `production/epics/combat/**` 可以有专门的 combat 故事规范。这是项目"路径即上下文"哲学的体现。

**谁写**：

- `/smoke-check` —— 写 smoke-*.md
- `/team-qa` —— 写 qa-signoff-*.md
- `/playtest-report` —— 写 playtests/playtest-*.md
- 手动测试者 —— 写 evidence/*.md

**为什么单独有 evidence/**：[story-done skill](file:///workspace/.claude/skills/story-done/SKILL.md#L171-176) 检查 Visual/Feel 类故事必须有 evidence 文件且签收完整才能标记 done。evidence 文件含签收表（`[ ] Approved` / `[x] Approved`），通过 grep 检查签收状态。

**和流程的关系**：QA 阶段的产物都在这里。`/gate-check` 在 Production → Polish 门禁检查"QA sign-off 存在且 verdict 是 APPROVED"。

#### 3.8 `playtests/` —— 玩家测试报告

**和 `qa/playtests/` 的区别**：

- `qa/playtests/` —— **内部**试点测试（开发团队自己玩）
- `playtests/` —— **外部**玩家测试（招募测试者）

**谁写**：`/playtest-report` skill 写到 `qa/playtests/`，但项目里 `playtests/` 作为外部测试的归档位置（[WORKFLOW-GUIDE.md](file:///workspace/docs/WORKFLOW-GUIDE.md#L130) 提到）。

**和流程的关系**：`/gate-check` 在 Polish → Release 门禁检查"至少 3 次不同 playtest session 文档"。

#### 3.9 `releases/` —— 发布清单

**内容**：`release-checklist-[version].md`

**谁写**：[`/release-checklist` skill](file:///workspace/.claude/skills/release-checklist/SKILL.md#L173)

**和流程的关系**：Release 阶段的最终产物。包含发布前所有检查项（平台合规、本地化、性能预算、SKU 配置等）。

---

#### 3.10 `hotfixes/` —— 热修复记录

**内容**：`hotfix-[date]-[short-name].md`

**谁写**：[`/hotfix` skill](file:///workspace/.claude/skills/hotfix/SKILL.md#L63)

**为什么单独有目录**：热修复是"Live 阶段的紧急生产操作"，需要独立审计轨迹。和正常 release 流程分开，便于事后复盘。

#### 3.11 `retrospectives/` —— 回顾文档

**内容**：

- `retro-sprint-[N]-[date].md` —— 单 sprint 回顾
- `retro-[milestone]-[date].md` —— 里程碑回顾

**谁写**：[`/retrospective` skill](file:///workspace/.claude/skills/retrospective/SKILL.md#L194)

**谁读**：[`/retrospective` skill](file:///workspace/.claude/skills/retrospective/SKILL.md#L86) 下次跑时读历史回顾，检查"上次定的 action item 是否落实"

**和流程的关系**：每个 sprint 结束建议跑一次。里程碑结束必须跑。

---

#### 3.12 `risk-register/` —— 风险登记

**谁读**：`/sprint-plan`、`/milestone-review` 都读它来识别风险

**设计意图**：风险不是"出问题了才记"，而是"持续登记、定期 review"。每个风险条目含描述、概率、影响、缓解措施、责任人。

---

#### 3.13 `session-state/` —— 会话状态（gitignored）

**核心文件**：`active.md`（第一部分详讲）

**为什么 gitignore**：

- active.md 是**当前快照**，不是历史记录
- 跨开发者协作时，每个人的 active.md 不同（"我正在干什么"是私有的）
- 历史 already 在 `session-logs/`

**和其它 production/ 子目录的关键区别**：

| 维度 | sprints/、qa/、releases/... | session-state/、session-logs/ |
|------|-----------------------------|-------------------------------|
| 性质 | 团队共享产物 | 个人会话临时状态 |
| Git | 提交 | gitignore |
| 跨人共享 | 是 | 否 |
| 跨会话 | 是 | 是（但不跨人） |

---

#### 3.14 `session-logs/` —— 会话审计日志（gitignored）

**核心文件**：

- `session-log.md` —— `session-stop.sh` 每次会话结束追加的归档
- `compaction-log.txt` —— `pre-compact.sh` 每次压缩事件追加一行

**为什么 gitignore**：

- 含个人工作习惯信息（提交时间、改了哪些文件）
- 体积会持续增长
- 不影响他人继续工作

**和 active.md 的分工**：

- `active.md` —— 当前快照（"现在在干什么"）
- `session-log.md` —— 历史归档（"过去都干了什么"）

这是 18 篇第一部分讲的状态环的最后一步：`session-stop.sh` 把 active.md 内容**追加**到 session-log.md，然后**不删** active.md。

### 5. 设计思路

#### 思路一：分离"决策产物" vs "执行状态" vs "审计轨迹"

`production/` 里的东西按"时间属性"分三类：

| 类型 | 例子 | 特点 |
|------|------|------|
| **决策产物**（永久） | sprints/、milestones/、releases/、epics/ | 一旦写就基本不变，是项目历史 |
| **执行状态**（动态） | sprint-status.yaml、stage.txt、active.md | 随时在变，反映"现在" |
| **审计轨迹**（追加） | session-logs/、retrospectives/、hotfixes/ | 只追加不删，用于复盘 |

**为什么这么分**：不同类型有不同的更新模式、git 行为、读取频率。混在一起会乱。

#### 思路二：人读 + 机读 双层源

很多概念同时有 markdown（人读）和 yaml/txt（机读）两个版本：

| 概念 | 人读 | 机读 |
|------|------|------|
| 冲刺 | `sprints/sprint-03.md` | `sprint-status.yaml` |
| 阶段 | （无） | `stage.txt` |
| Review 模式 | （无） | `review-mode.txt` |

**为什么**：markdown 适合叙事但难解析；yaml/txt 易解析但人读累。两层并存，skill 优先读机读版本，fallback 到人读版本。

#### 思路三：路径驱动规则

`epics/[epic-slug]/` 的目录结构不是装饰 —— `.claude/rules/` 可以按路径生效，让"combat 史诗下的故事"自动套用 combat 规范。这是项目"路径即上下文"哲学的体现。

#### 思路四：临时 vs 持久 的 git 策略

- **持久**（git tracked）：sprints/、milestones/、epics/、qa/、releases/、retrospectives/、stage.txt、review-mode.txt、sprint-status.yaml
- **临时**（gitignored）：session-state/、session-logs/

**判断标准**：这个文件对**其他开发者**或**未来的自己**有价值吗？有 → 提交；没 → gitignore。

#### 思路五：单文件配置 + 多文件产物

- **配置类**（stage.txt、review-mode.txt）：单文件，全局唯一
- **产物类**（sprints/、qa/、releases/）：多文件，按时间或主题切片

**为什么配置是单文件**：避免"两个配置文件冲突"。`stage.txt` 只能有一个值，不存在歧义。

### 6. 工程经验

#### 经验一：用 `.gitkeep` 占位空目录

`production/session-state/` 在新项目里是空的，但目录必须存在（hook 要往里写）。用 `.gitkeep` 占位让 git 跟踪空目录。

#### 经验二：路径约定一旦定下就不要改

`production/session-state/active.md` 这个路径在 4 个 hook 脚本、10+ 个 skill、statusline.sh 里都被写死。改路径意味着改十几个文件。**第一设计时就定好，之后不再动**。

#### 经验三：状态字段用枚举值，不要自由文本

`sprint-status.yaml` 里 status 字段是固定枚举：

```
backlog | ready-for-dev | in-progress | review | done | blocked
```

不用自由文本（如 "正在做" / "做完了"）。枚举值让 skill 可以可靠地 grep、判断、跳转。

#### 经验四：日志只追加不覆盖

`session-log.md` 用 `>>` 追加，不用 `>` 覆盖。`compaction-log.txt` 同理。**审计轨迹必须只追加**，否则失去审计价值。

#### 经验五：高摩擦操作要留痕

热修复（`hotfixes/`）、发布（`releases/`）、门禁通过（`stage.txt` 更新）都是高摩擦操作 —— 出错代价大。每个都强制留一份文档，便于事后追溯。

#### 经验六：机器可读优先

`stage.txt` 单行、`sprint-status.yaml` 是 YAML、`review-mode.txt` 是单词 —— 全是机器可读格式。**人读的叙事文档（sprint-NN.md）是次要源**，skill 优先读机读版本。

#### 经验七：每个文件都问"谁写、谁读、什么时候"

设计 production/ 里任何一个新文件时，先回答三个问题：

- 谁写（哪个 skill / hook / 用户）
- 谁读（哪些 skill / hook / 用户）
- 什么时候（哪个阶段、哪个事件）

答不上来说明这个文件不该存在。这避免"为了未来可能的用途"创建空文件。

### 7. 解决了什么问题

把 `production/` 当成一个整体看，它解决了项目管理的几个核心问题：

| 问题 | 解法 | 关键文件 |
|------|------|----------|
| "我做到哪一步了？" | stage.txt 单值 + active.md 当前任务 | stage.txt、active.md |
| "我之前怎么决策的？" | milestones/、retrospectives/、releases/ 留档 | milestones/、retrospectives/ |
| "我现在该干啥？" | statusline.sh 显示阶段 + active.md 显示当前任务 + /help 推荐 | stage.txt、active.md |
| "这个故事做完了吗？" | sprint-status.yaml 机读状态 | sprint-status.yaml |
| "测试通过了吗？" | qa/ 下多份报告 + evidence/ 签收 | qa/ |
| "这版本发布了什么？" | releases/release-checklist-[version].md | releases/ |
| "上次会话发生啥了？" | session-logs/session-log.md 归档 | session-logs/ |
| "风险管了吗？" | risk-register/ 持续登记 | risk-register/ |
| "出过 hotfix 吗？" | hotfixes/ 留档 | hotfixes/ |

**一句话**：`production/` 是项目的**工作记忆 + 长期记忆 + 审计记忆**的统一存放点。文件即记忆，前四部分讲的"状态环"只是这个大原则在会话层面的应用。

### 8. 迁移到自己的项目

如果你的项目不是游戏开发，怎么设计自己的 `production/`（或叫别的名字）？

#### 第一步：列出你的"工作类型"

游戏开发的工作类型是：sprint、milestone、epic、story、qa、release、retrospective、hotfix、playtest、risk。

你的项目可能不同：

| 领域 | 工作类型 |
|------|----------|
| 软件开发 | sprint、milestone、feature、bug、release、retro、hotfix |
| 文档/写作 | draft、chapter、review、revision、final |
| 数据分析 | question、hypothesis、notebook、report、review |
| 研究 | section、draft、revision、submission、revision |

#### 第二步：每个工作类型建一个子目录

```
your-project/production/
├── sprints/         # 或 cycles/
├── features/        # 或 chapters/、questions/
├── qa/              # 或 reviews/
├── releases/        # 或 publications/
└── ...
```

#### 第三步：定 3 个根文件

- `[stage-file].txt` —— 当前阶段（如 `phase.txt`）
- `[config-file].txt` —— 项目级偏好（如 `strictness.txt`）
- `[status-file].yaml` —— 工作单元状态机

#### 第四步：定 session-state/ 和 session-logs/

照搬 Game-Studios 的设计：

- `session-state/active.md` —— 当前快照（gitignored）
- `session-logs/session-log.md` —— 历史归档（gitignored）

#### 第五步：写"谁写、谁读、什么时候"表

每个文件都填这张表（见 6 节经验七）。填不上的就删掉。

#### 第六步：迁移时遵循"最小可行"

不要一上来就建所有子目录。**按需创建**——进入对应阶段时再建。这是 [WORKFLOW-GUIDE.md](file:///workspace/docs/WORKFLOW-GUIDE.md#L135-139) 明确的建议：

> You do not need all of these on day one. Create directories as you reach the phase that needs them.

2. 上下文压缩时为什么不会丢工作进度？
   <details><summary>答案</summary>
   pre-compact.sh 在压缩前把 active.md 全文 + WIP 文件清单注入压缩输入，让摘要有内容可保留；post-compact.sh 在压缩后立刻提醒大模型读 active.md。两道保险。
   </details>

3. 用户在选项 UI 里点 "Other" 输入自定义意见后，AI 怎么知道要重新出选项？
   <details><summary>答案</summary>
   不是 AI"知道"，是 skill 正文写了循环结构。比如 brainstorm 的 pillar 确认环节写了 "Repeat until the user selects [A] Lock these in"，用户只要没点 Lock in，Agent 就会一直走"修改 → 再确认"循环。
   </details>

4. 为什么"草稿 + 批准 widget"必须在同一个响应里？
   <details><summary>答案</summary>
   design-system SKILL.md 明确规定这是 protocol violation。如果分开，用户看到草稿后会停在空白提示符前，没有路径走下一步。把两者放一起，用户能立刻点批准或要求修改。
   </details>

5. 增量写入和 active.md 是什么关系？
   <details><summary>答案</summary>
   active.md 是索引（"做到第几节了"），GDD 文件是内容。增量写入让 GDD 文件每节批准即落盘，所以崩溃后 active.md 说"做到第 4 节"时，文件里真的有第 1-4 节的真实内容。两者配合才能恢复。
   </details>

6. **迁移到自己的项目时，为什么不能把"必须读 active.md"写进 CLAUDE.md 就算了事？**
   <details><summary>答案</summary>
   CLAUDE.md 是"大模型读到时自觉遵守"的软约束，大模型会忘、会跳。把"必须读"放进 hook 是因为 hook 是事件自动触发的、大模型绕不过。强约束放 hook，软约束放 rules，这是迁移时的核心分工原则。
   </details>

7. **迁移时 active.md 应该写"做了什么"还是"现在在做什么"？**
   <details><summary>答案</summary>
   只写"现在在做什么"——它是当前快照，不是日志。日志交给 session-stop.sh 归档到 session-log.md。如果把全量历史写进 active.md，会越来越长，hook 预览的 20 行最后都是过期信息，反而失去提醒作用。
   </details>

8. **为什么 hook 只做"检测 + 预览 + 提醒"，不做恢复？**
   <details><summary>答案</summary>
   恢复需要理解"上次到底停在哪、决策是什么、下一步该走哪节"，这是大模型擅长的事，不是脚本擅长的事。Hook 越简单越稳——只做三件事（检测、预览、提醒），把复杂的理解交给大模型。把恢复逻辑塞进 hook 会让脚本越来越臃肿、难维护。
   </details>

9. **在 Cursor 这种没有 hook 的环境里，怎么变通实现状态保存？**
   <details><summary>答案</summary>
   在 .cursorrules 里写"每次完成里程碑后更新 active.md"——这是软约束，大模型可能忘，需要用户偶尔提醒。压缩前后也写"清理上下文前先读 active.md"。比 Claude Code 弱，但比没有强。详见第四部分 4.6 节变体 B。
   </details>

10. **MVP 版本最少要做哪几步？**
    <details><summary>答案</summary>
    5 步：建目录 → 定 active.md 模板 → 写 session-start.sh → 注册 SessionStart hook → 在 skill 里加"更新 active.md"。这 5 步能跑通"启动检测 + skill 写 + 中断恢复"三个核心场景。pre-compact / post-compact / session-stop 可以后补。
    </details>

11. **`production/` 里 `stage.txt` 和 `active.md` 都能告诉大模型"现在在干什么"，有什么区别？**
    <details><summary>答案</summary>
    stage.txt 是"项目级阶段指针"（如 Production），决定哪些 skill 该跑、状态栏显示什么；粒度粗、变化慢、由 /gate-check 在门禁通过时更新。active.md 是"任务级当前快照"（如"在做 combat-damage-calc 故事"），粒度细、变化频繁、由 skill 在每个里程碑后更新。前者是"项目在哪个阶段"，后者是"我现在手头在干啥"。
    </details>

12. **为什么 `sprint-status.yaml` 用 YAML 而不是直接用 `sprints/sprint-03.md` 里的表格？**
    <details><summary>答案</summary>
    YAML 机器可读（skill 直接 yaml.load，不用正则解析 markdown）、状态原子化（改一个 status 字段不影响其它内容）、避免 markdown 表格对齐漂移、git diff 清晰。markdown 表格是人读的叙事文档，skill 优先读 yaml，fallback 到 markdown。这是"人读 + 机读 双层源"模式。
    </details>

13. **`production/session-state/` 和 `production/session-logs/` 为什么是 gitignored？而 `production/sprints/` 是 git tracked？**
    <details><summary>答案</summary>
    session-state/active.md 是个人"当前在干什么"的私有快照，跨开发者协作时每人不同，且历史已归档到 session-logs/。session-logs/ 含个人工作习惯信息且持续增长。两者对他人无价值。sprints/ 是团队共享的决策产物，对所有人都需要可见。判断标准：这个文件对其他开发者或未来的自己有价值吗？有 → 提交；没 → gitignore。
    </details>

14. **`production/review-mode.txt` 这种"项目级偏好"文件的设计经验是什么？**
    <details><summary>答案</summary>
    "一次决策、多次复用"。review 深度（lean/full/solo）是项目级偏好，不是单次决策。如果不抽出来，每次跑带门禁的 skill 都要问一遍用户，体验差。写到单文件后所有 skill 共享同一设置，启动时第一件事就是读它。同类的还有代码风格、测试严格度、目标平台 —— 都可以用同样的单文件配置模式。
    </details>

15. **设计 `production/` 里一个新文件时，必须回答哪三个问题？**
    <details><summary>答案</summary>
    谁写（哪个 skill / hook / 用户）、谁读（哪些 skill / hook / 用户）、什么时候（哪个阶段、哪个事件）。答不上来说明这个文件不该存在，避免"为了未来可能的用途"创建空文件。这是工程经验七的核心。
    </details>
