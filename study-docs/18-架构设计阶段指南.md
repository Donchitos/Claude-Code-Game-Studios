# 18 · 架构设计阶段（Phase 3）指南

## 这篇文档解决什么问题

前几篇讲了 `design/`（设计大脑）和 `docs/`（施工档案）。这篇专攻开发流程的 **Phase 3：Technical Setup（技术搭建阶段）**——设计做完、代码还没开始写之间的这个"翻译阶段"。

你会有两个核心疑问：

1. **为什么 ADR 文档的模板在 `docs/CLAUDE.md` 里指定，而不是像 GDD 那样在技能 `/design-system` 里指定？** `/design-system` 明确要输出一个文档，但 `/architecture-decision` 似乎没有明确"输出需求"？

2. **架构设计阶段要做什么？** `/create-architecture`、`/architecture-decision`、`/architecture-review`、`/create-control-manifest` 这四个技能分别是什么作用？何时用？怎么用？为什么需要它们？这是游戏开发领域的工程经验和标准吗？

读完这篇你会明白：设计文档（GDD）怎么"翻译"成可实现的架构蓝图，以及为什么这套翻译流程这么设计。

---

## 一句话定位

> **Phase 3 架构设计阶段 = 把 GDD 翻译成技术蓝图的"翻译车间"。四个技能各司其职：`/create-architecture` 画总蓝图，`/architecture-decision` 逐个记录技术决策，`/architecture-review` 审查一致性，`/create-control-manifest` 给程序员出"速查规则表"。**

---

## 类比：把 Phase 3 想象成"盖楼前的图纸深化"

- **Phase 2 产出的 GDD** = 建筑设计方案（"这栋楼要有什么功能、几个房间、什么风格"）
- **Phase 3 的四个技能** = 把设计方案深化成施工图纸的四个工种：

| 工种 | 对应技能 | 干什么 |
|------|---------|--------|
| **总图设计师** | `/create-architecture` | 画总平面图：承重墙在哪、管线怎么走、各层怎么分 |
| **结构工程师** | `/architecture-decision` | 每个关键结构决策出一份计算书："为什么用钢结构不用混凝土" |
| **审图员** | `/architecture-review` | 审所有图纸：结构冲突没、管线打架没、符合规范没 |
| **施工手册编写员** | `/create-control-manifest` | 给工人出一张"速查卡"：必须怎么做、绝不能怎么做 |

没有这个深化阶段，施工队（程序员）拿到设计方案就开干，必然返工——管线打架、承重不够、关键决策没记录。

## 术语速查表（先读这节，后面才看得懂）

Phase 3 术语密集，且横跨软件工程和游戏开发两个领域。先从字面到内涵讲清楚。

### 文档与 ID 术语

| 术语 | 全称 / 字面 | 内涵 | 是标准吗 |
|------|------------|------|---------|
| **ADR** | Architecture Decision Record | 架构决策记录。每个重要技术决策一份文档，记录"在什么背景下、做了什么决定、有什么后果"。 | ✅ 软件工程标准（Michael Nygard 2011 推广） |
| **TR-ID** | Technical Requirement ID | 技术需求编号，格式 `TR-[系统名]-[NNN]`（如 `TR-combat-001`）。从 GDD 提取，建立"需求→决策→故事→测试"可追溯链。 | ⚠️ RTM 是标准，TR-ID 命名是本框架特有 |
| **RTM** | Requirements Traceability Matrix | 需求追溯矩阵。追溯"需求→设计→实现→测试"完整链路。航空航天/汽车/医疗等安全关键领域强制要求。 | ✅ 软件工程标准 |
| **control-manifest** | 管控清单 | 给程序员的"速查规则表"——按架构层分类，列出必须做的、禁止做的、性能红线。每条带 ADR 出处。 | ❌ 本框架特有 |
| **architecture.yaml** | 架构注册表 | 跨 ADR 共享约束的"户籍系统"——登记状态归属、接口契约、性能预算、API 选择、禁止模式。防 ADR 间冲突。 | ❌ 本框架特有（机制类似 entities.yaml） |

### 架构分层术语

| 术语 | 内涵 |
|------|------|
| **System Layer Map** | 系统分层图。本框架用 5 层：Platform（OS/引擎 API）→ Foundation（save/load、事件总线）→ Core（物理、战斗、移动）→ Feature（AI、任务、进度）→ Presentation（UI、VFX、音频）。游戏开发常见分层，但非唯一标准。 |
| **Module Ownership** | 模块归属。每个模块定义"拥有什么状态、暴露什么接口、消费什么、用哪些引擎 API"。 |
| **Engine Knowledge Gap** | 引擎知识缺口。LLM 训练数据有截止日期，引擎版本可能晚于截止，导致 AI 对引擎 API 的知识不可靠。分 LOW/MEDIUM/HIGH 风险。 | ❌ 本框架特有（AI 时代特有） |

### 状态与流程术语

| 术语 | 内涵 |
|------|------|
| **Proposed → Accepted → Superseded** | ADR 状态生命周期。新 ADR 默认 Proposed；用户审查后改 Accepted；被新 ADR 取代时旧的标 Superseded。**跳过 Accepted 的 ADR 会被 story 自动阻断**——不能基于未批准的决策写故事。 |
| **Stance** | 立场。一个 ADR 对架构的"主张"——它声称拥有什么状态、定义什么接口、占多少性能预算、选什么 API、禁什么模式。这些 stance 会被提取到 architecture.yaml 注册表。 |
| **TD-ARCHITECTURE / TD-ADR / LP-FEASIBILITY** | 技术总监（TD）和主程序员（LP）的审查门。`/create-architecture` 完成后触发 TD-ARCHITECTURE；每个 ADR 写完触发 TD-ADR；架构蓝图完成后 LP 审"能不能实现"（LP-FEASIBILITY）。 |

## 全景地图：Phase 3 的四个技能

```

│
├─ 3.1  /create-architecture         → docs/architecture/architecture.md（总蓝图）
│       │   画系统分层图、模块归属、数据流、API 边界
│       │   提取 TR-ID、列出"还需要哪些 ADR"
│       │   触发 TD-ARCHITECTURE + LP-FEASIBILITY 门
│       │
├─ 3.2  /architecture-decision (× N) → docs/architecture/adr-[NNNN]-[slug].md（单个决策记录）
│       │   至少 3 个 Foundation 层 ADR
│       │   每个决策走"假设→确认→生成→验证→写入→更新注册表"
│       │   触发 TD-ADR 门
│       │   写入 docs/registry/architecture.yaml（stance 注册表）
│       │
├─ 3.3  /architecture-review         → docs/architecture/architecture-review-[date].md（审查报告）
│       │                              + docs/architecture/tr-registry.yaml（TR-ID 注册表）
│       │   审查所有 ADR 的一致性、引擎兼容性、需求覆盖
│       │   判决 PASS / CONCERNS / FAIL
│       │   必须在 fresh session 运行（独立于创作上下文）
│       │
└─ 3.4  /create-control-manifest     → docs/architecture/control-manifest.md（程序员速查表）
        │   从所有 Accepted ADR 提取规则，按层分类
        │   Required / Forbidden / Guardrails 三分
        │   每条带 ADR 出处
        │   触发 TD-MANIFEST 门（注：此 gate 在 director-gates.md 中未定义，文档不一致）
```

**Phase 3 Gate（`/gate-check technical-setup`）要求**：

- `docs/architecture/architecture.md` 存在
- 至少 3 个 ADR 存在且 Accepted
- 架构审查报告存在
- `docs/architecture/control-manifest.md` 存在
- `design/accessibility-requirements.md` 存在（UX 侧并行产出）

## 核心问题 1：为什么 ADR 模板在 docs/CLAUDE.md，而不在技能里？

### 先看事实

| 文档类型 | 模板/骨架规定在哪 | 谁产出 |
|---------|------------------|--------|
| **GDD** | `/design-system` 技能内联骨架（[SKILL.md 第 220-281 行](file:///workspace/.claude/skills/design-system/SKILL.md)） | `/design-system` 单一技能 |
| **ADR** | [docs/CLAUDE.md 第 7-14 行](file:///workspace/docs/CLAUDE.md) 规定模板路径、必填章节、状态流 | `/architecture-decision` 技能执行，但规则在 CLAUDE.md |

注意：两个技能**都**在自己文件里内联了完整格式。差异不在"内不内联"，而在**权威规则存放位置**——ADR 的规则在跨技能的 CLAUDE.md，GDD 的规则在单技能内。

### 三个原因

#### 原因 1：ADR 是跨技能消费的"契约"，GDD 是单技能产出的"设计稿"

ADR 的 `Status` 字段被**多个技能**强制读取：

| 技能 | 怎么读 ADR |
|------|-----------|
| `/story-readiness` | Proposed ADR 引用的 story 会被**自动阻断**（CLAUDE.md 第 13 行） |
| `/create-stories` | 把 ADR 引用嵌入 story |
| `/architecture-review` | 审查所有 ADR 一致性 |
| `/dev-story` | 实现时检查 ADR 约束 |
| `/create-control-manifest` | 只读 Accepted ADR 提取规则 |

多个技能需要**一致**地读取 ADR 状态，规则必须放在跨技能的权威位置（docs/CLAUDE.md），不能散落在某个技能里。

GDD 主要由 `/design-system` 单一技能产出，被 `/design-review`、`/review-all-gdds`、`/consistency-check` 读取——消费方少，章节结构属于"作者指导"，放在作者技能内即可。

#### 原因 2：目录管辖权——CLAUDE.md 管 docs/，GDD 不在 docs/ 下

[docs/CLAUDE.md 第 1-3 行](file:///workspace/docs/CLAUDE.md)开头就声明：

> "When authoring or editing files in this directory, follow these standards."

ADRs 存在 `docs/architecture/`，归 docs/CLAUDE.md 管辖。GDDs 存在 `design/gdd/`，归 [design/CLAUDE.md](file:///workspace/design/CLAUDE.md) 管辖——而 design/CLAUDE.md 确实规定了 GDD 的 8 章节规则。所以"GDD 规则不在 docs/CLAUDE.md"是因为管辖权，不是因为不重要。

#### 原因 3：ADR 状态流是强制门控，需要全局可见性

"跳过 Accepted 会被 story 自动阻断"——这是影响整个生产流程的硬约束。GDD 的 Status（Draft/In Review/Approved）影响面较小，主要由 `/design-review` 处理。强制门控的规则需要全局可见，所以放 CLAUDE.md。

### 那"/architecture-decision 没有明确输出需求"对吗？

**不完全对**。`/architecture-decision` 确实有明确输出——产出一份 ADR 文件到 `docs/architecture/adr-[NNNN]-[slug].md`（[SKILL.md 第 385 行](file:///workspace/.claude/skills/architecture-decision/SKILL.md)）。只是它的输出方式不像 `/design-system` 那么"显式建骨架 + 逐节填"。

具体差异见下表：

| 维度 | `/design-system`（GDD） | `/architecture-decision`（ADR） |
|------|------------------------|-------------------------------|
| **骨架先行** | ✅ 先建空骨架（`[To be designed]` 占位符），再逐节填 | ❌ 一次性生成完整草稿 |
| **Section Cycle** | ✅ 每节走 Context→Questions→Options→Decision→Draft→Approval→Write | ❌ 用 Assumptions-First（先推导假设→确认→生成→多阶段验证→一次写入） |
| **即时写入** | ✅ 每节批准后立即写盘 | ❌ 全部验证通过后一次性写入 |
| **产出文件数** | 1 个 GDD（8 必填章节） | 1 个 ADR（含 Context/Decision/Consequences 等约 12 节） |

**为什么机制不同？** 因为 GDD 章节相对独立（Overview、Formulas、Edge Cases 可分别设计），适合逐节填；ADR 章节强耦合（Decision 必须回应 Context，Consequences 必须回应 Decision），不适合逐节独立审批——分开审会导致前后矛盾。

## 核心问题 2：四个技能详解

### 技能 1：`/create-architecture` —— 画总蓝图

**作用**：把所有 GDD 翻译成一份整体技术蓝图。它回答："这么多系统，技术上怎么组织？分几层？谁拥有什么？数据怎么流？还缺哪些决策？"

**产出**：[`docs/architecture/architecture.md`](file:///workspace/docs/architecture/architecture.md)（主架构文档）

**谁运行**：technical-director（技术总监）

**何时用**：Phase 3 的**第一步**——所有 MVP GDD 批准后、写任何 ADR 之前。

#### 完整工作流（8 个 Phase）

| Phase | 做什么 | 行号 |
|-------|--------|------|
| **0. 加载所有上下文** | 读引擎文档（VERSION/breaking-changes/deprecated/best-practices/modules）+ 读所有 GDD + 读现有 ADR + **提取 TR-ID** + 生成 Knowledge Gap Inventory | 第 36-127 行 |
| **1. 系统分层映射** | 把每个系统映射到 5 层（Platform/Foundation/Core/Feature/Presentation）；逐系统询问 + 批准 + 即时写入骨架 | 第 130-161 行 |
| **2. 模块归属图** | 每模块定义 Owns/Exposes/Consumes/引擎 API；表格 + ASCII 依赖图；引擎 API 版本检查 | 第 164-185 行 |
| **3. 数据流** | 帧更新路径 / 事件信号路径 / 存读档路径 / 初始化顺序；ASCII 序列图 | 第 188-205 行 |
| **4. API 边界** | 模块间公共契约；伪代码或项目实际语言；引擎类型版本检查 | 第 208-223 行 |
| **5. ADR 审计 + 追溯检查** | ADR 质量检查 + **TR 覆盖检查**（每个 TR 映射到 ADR）+ 列出"还需要哪些 ADR" | 第 226-268 行 |
| **6. 缺失 ADR 清单** | 按 priority 分组：Must have / Should have / Can defer | 第 271-286 行 |
| **7. 写主架构文档** | 写入 architecture.md | 第 289-339 行 |
| **7b. TD 签字 + LP 可行性** | TD-ARCHITECTURE 自审 + LP-FEASIBILITY spawn + 记录签字 | 第 343-379 行 |
| **8. 移交** | 固定模板输出：架构完成 / 接下来跑哪些 ADR / Gate 就绪状态 / 未决问题 | 第 382-436 行 |

#### architecture.md 的章节结构

| 章节 | 内容 |
|------|------|
| Document Status | Version / Last Updated / Engine / GDDs Covered / ADRs Referenced / TD Sign-Off / LP Feasibility |
| **Engine Knowledge Gap Summary** | 凝缩自 Phase 0d，列出 HIGH/MEDIUM 风险的引擎域 |
| **System Layer Map** | 5 层架构图，每个系统归到哪层 |
| **Module Ownership** | 每模块 Owns/Exposes/Consumes/Engine APIs |
| **Data Flow** | 帧更新/事件/存档/初始化的数据流图 |
| **API Boundaries** | 模块间公共契约 |
| **ADR Audit** | 现有 ADR 质量检查 + TR 覆盖情况 |
| **Required ADRs** | 还需要写哪些 ADR，按 priority 分组 |
| Architecture Principles | 3-5 条从概念/GDD/技术偏好推导的原则 |
| Open Questions | 推迟的决策 |

#### TR-ID 是什么、怎么提取

**TR-ID**（Technical Requirement ID）= 技术需求编号，格式 `TR-[系统名]-[NNN]`（如 `TR-combat-001`）。

[SKILL.md 第 69-78 行](file:///workspace/.claude/skills/create-architecture/SKILL.md)说明提取来源——从每个 GDD 提取 6 类技术需求：

- 游戏规则隐含的数据结构
- 明示或暗示的性能约束
- 系统需要的引擎能力
- 跨系统通信模式
- 必须持久化的状态（存读档影响）
- 线程或时序要求

这些需求编号成 TR-ID，构成 **Technical Requirements Baseline**（技术需求基线），喂给后续每个 Phase。Phase 5 检查每个 TR 是否被某个 ADR 覆盖——没覆盖的就是"还需要写的 ADR"。

> 💡 **注意**：`/create-architecture` 只在自己的文档内构建 baseline 表格，**不创建** tr-registry.yaml。tr-registry.yaml 由 `/architecture-review` Phase 8 创建和更新。

#### 它怎么决定"需要哪些 ADR"

两步机制：

1. **Phase 5 追溯检查**：把每个 TR 映射到现有 ADR。状态三种：
   - ✅ Covered（已被某个 ADR 覆盖）
   - ⚠️ Partial（部分覆盖）
   - ❌ Gap（完全没覆盖）

2. **Phase 6 缺失 ADR 清单**：把所有 ❌ Gap 的 TR + Phase 1-4 中做出的但无 ADR 记录的决策，按 priority 三级分组：
   - **Must have**：coding 前必须有（Foundation 和 Core 决策）
   - **Should have**：相关系统开发前应有
   - **Can defer**：可推迟到实现期

#### 触发什么 Director Gate

| Gate | 触发时机 | 模式 | 检查什么 |
|------|---------|------|---------|
| **TD-ARCHITECTURE** | Phase 7 写完文档后 | self-review（不受模式控制） | (1) 每个 TR 是否覆盖 (2) HIGH risk 引擎域是否处理 (3) API 边界是否 clean (4) Foundation 层 ADR 缺口是否在实现前解决 |
| **LP-FEASIBILITY** | TD 自审后 | full spawn；lean/solo skip | (a) 难实现的决策 (b) 缺失的 interface 定义 (c) 避免技术债或违背引擎惯用法的模式 |

### 技能 2：`/architecture-decision` —— 逐个记录技术决策

**作用**：针对 `/create-architecture` 列出的每个"Required ADR"，逐个产出一份 ADR 文档，记录"在什么背景下、考虑了哪些方案、选了什么、有什么后果"。

**产出**：`docs/architecture/adr-[NNNN]-[slug].md`（单个 ADR 文件）+ 更新 `docs/registry/architecture.yaml`（stance 注册表）

**谁运行**：无指定 agent（sonnet 模型）

**何时用**：Phase 3 的**第二步**——`/create-architecture` 之后，逐个写 ADR。至少 3 个 Foundation 层 ADR。

#### ADR 文档结构（必填章节）

来自 [docs/CLAUDE.md 第 9-10 行](file:///workspace/docs/CLAUDE.md) + [ADR 模板](file:///workspace/.claude/docs/templates/architecture-decision-record.md)：

| 章节 | 写什么 |
|------|--------|
| **Title** | `# ADR-[NNNN]: [标题]` |
| **Status** | `Proposed \| Accepted \| Deprecated \| Superseded by ADR-XXXX` |
| **Date** | 创建日期 |
| **Engine Compatibility**（表格） | 引擎版本、依赖的 API、风险等级（LOW/MEDIUM/HIGH）、post-cutoff API 标注 |
| **ADR Dependencies**（表格） | Depends On / Enables / Blocks / Ordering Note |
| **Context** | Problem Statement / Constraints / Requirements——为什么要做这个决策 |
| **Decision** | 选了什么方案；含架构图 / 关键接口 |
| **Alternatives Considered** | 考虑过但拒绝的方案，每个说明为什么拒绝 |
| **Consequences** | Positive / Negative / Risks——这个决策的后果 |
| **GDD Requirements Addressed**（表格） | 这个 ADR 满足了哪些 GDD 需求（链接到 GDD 章节） |
| **Performance Implications** | 性能影响（帧时间、内存等） |
| **Migration Plan** | 迁移计划（如何从旧方案过渡） |
| **Validation Criteria** | 怎么验证这个决策生效 |

#### 协作机制：Assumptions-First（假设优先）

不像 `/design-system` 的逐节循环，`/architecture-decision` 用 **Assumptions-First** 模式：

1. **先推导假设**：从已读的 GDD/引擎文档/现有 ADR 推导 best guesses（[第 171-207 行](file:///workspace/.claude/skills/architecture-decision/SKILL.md)）
2. **用 AskUserQuestion 确认**：呈现 confirm/adjust，**非开放性问题**
3. **生成完整草稿**：一次性生成整个 ADR
4. **多阶段验证**：Engine Specialist（5.5）→ TD-ADR（5.6）→ GDD Sync Check（5.7）
5. **一次性写入批准**：全部验证通过后，问你"可以写入吗"
6. **写入后更新注册表**：提取 stance 到 architecture.yaml（BLOCKING，必须你批准）

**为什么不用逐节循环？** 因为 ADR 章节强耦合——Decision 必须回应 Context，Consequences 必须回应 Decision。分开审会导致前后矛盾。一次性生成 + 多阶段验证更合理。

#### ADR 状态生命周期

```
Proposed  →  Accepted  →  Superseded (by ADR-XXXX)
                ↓
            Deprecated
```

- **Proposed**：新 ADR 默认状态（[SKILL 第 180 行](file:///workspace/.claude/skills/architecture-decision/SKILL.md)："Always Proposed for new ADRs — never ask the user"）
- **Accepted**：用户审查后**手动**改（技能不自动改状态）。**跳过 Accepted 的 ADR 会被 story 自动阻断**
- **Superseded**：旧 ADR 被新 ADR 取代时，旧的 stance 设 `status: superseded_by: ADR-[NNNN]`

#### 更新 architecture.yaml 注册表

**文件**：[`docs/registry/architecture.yaml`](file:///workspace/docs/registry/architecture.yaml)

**提取的 stance 类型**（[第 393-398 行](file:///workspace/.claude/skills/architecture-decision/SKILL.md)）：

- State it claims ownership of（声称拥有的状态）
- Interface contracts it defines（定义的接口契约）
- Performance budget it claims（占的性能预算）
- API choices it makes explicitly（明确的 API 选择）
- Patterns it bans（禁止的模式）

注册表 5 个 section：

| Section | 登记什么 |
|---------|---------|
| `state_ownership` | state / owner_system / adr / interface / write_access / referenced_by |
| `interfaces` | contract / pattern（signal/direct_call/event_bus/shared_resource/rpc）/ producer / consumers / signal_signature |
| `performance_budgets` | target_fps / total_frame_budget_ms / system / budget_ms |
| `api_decisions` | purpose / api / not（被禁的替代）/ reason |
| `forbidden_patterns` | pattern / description / why |

**铁律**：无用户明确批准不写 architecture.yaml（BLOCKING）。

#### tr-registry.yaml 结构

[`docs/architecture/tr-registry.yaml`](file:///workspace/docs/architecture/tr-registry.yaml) 是 TR-ID 的永久注册表。规则（[第 1-25 行](file:///workspace/docs/architecture/tr-registry.yaml)）：

- **ID 永久**：never renumber, never delete（用 `status: deprecated`）
- 新 entry 只 append 到每个 system list 末尾
- reworded（同意图换措辞）：ID 不变，更新 requirement 文本 + 加 revised 日期
- removed：设 `status: deprecated`
- split/replaced：设 `status: superseded-by` 指向新 TR-ID

Entry 结构示例：

```yaml
- id: TR-combat-001
  system: combat
  gdd: design/gdd/combat-system.md
  requirement: "Player takes damage from enemies based on attack power minus defence"
  created: 2026-03-10
  revised: ""
  status: active
```

**读者**：`/create-stories`（嵌入 ID 到 story）、`/story-readiness`（验证 TR-ID 存在且 active）、`/story-done`（review 时查当前 requirement 文本）

#### 判决词

| Verdict | 条件 |
|---------|------|
| **PASS** | 所有需求覆盖、无冲突、引擎一致 |
| **CONCERNS** | 有缺口或部分覆盖，但无 blocking 冲突 |
| **FAIL** | 关键缺口（Foundation/Core 层需求未覆盖）或 blocking 跨 ADR 冲突 |

**注意**（[第 664-665 行](file:///workspace/.claude/skills/architecture-review/SKILL.md)）："the verdict is advisory; the user decides whether to continue despite CONCERNS or even FAIL findings"——判决是建议性的，用户最终决定。

#### 为什么必须 fresh session

和 `/design-review` 不能和 `/design-system` 同会话一个道理（[第 447-454 行](file:///workspace/.claude/skills/architecture-decision/SKILL.md)）：

> "Never run `/architecture-review` in the same session as `/architecture-decision`. The reviewing agent must be independent of the authoring context."

同会话会继承完整创作上下文，使独立批判不可能——审查者"既当运动员又当裁判"。

## 这是游戏开发领域的工程经验和标准吗

### ADR —— ✅ 软件工程标准（非游戏特有）

- **起源**：Michael Nygard 2011 年在 ThoughtWorks 技术雷达推广 ADR 概念。现已是软件架构领域广泛采用实践。
- **本框架的扩展**：标准 ADR 通常含 Context/Decision/Consequences。本框架**扩展**了游戏/引擎特定字段：
  - **Engine Compatibility 表格**（含 Knowledge Risk LOW/MEDIUM/HIGH）——标准软件 ADR 无此字段，这是针对 LLM 训练数据与引擎版本差距的特有设计
  - **ADR Dependencies**（Depends On / Enables / Blocks）——标准 ADR 通常无结构化依赖图
  - **GDD Requirements Addressed**——将 ADR 链接到游戏设计文档，本框架特有
- **状态流**：Proposed → Accepted → Superseded 与标准 ADR 实践一致

### TR-ID 与 RTM —— ✅ 软件工程标准

- **Requirements Traceability Matrix (RTM)**：软件工程标准实践，航空航天（DO-178C）、汽车（ISO 26262）、医疗（IEC 62304）等安全关键领域**强制要求**。追溯"需求→设计→实现→测试"完整链路。
- **本框架的实现**：
  - TR-ID 格式 `TR-[system-slug]-NNN` 是本框架特有命名
  - 完整链路：GDD requirement → ADR → Story → Test
  - `tr-registry.yaml` 提供 stable ID 跨 review run 不变——对 RTM 实践的工程化强化
- **本框架特有**：将 RTM 概念应用于游戏开发（游戏开发通常不强制 RTM），并将 GDD 作为需求源

### control-manifest —— ❌ 本框架特有

- SKILL.md 自定义定义，无外部标准引用
- 概念定位为 ADR 的"flat actionable rules sheet"——ADRs 解释 why，manifest 告诉 what
- Manifest Version 机制（story 嵌入版本日期检测 staleness）是本框架特有
- 传统软件工程有"coding standards"、"style guide"等类似概念，但无统一的"control manifest"标准
- 游戏开发领域也无此标准概念

**最接近的概念**：Coding Guidelines / Architecture Principles Document，但本框架的 control-manifest 更结构化（按层分类 + Required/Forbidden/Guardrails 三分 + 每条带 ADR source）。

### System Layer Map（5 层）—— ⚠️ 游戏开发常见，但非唯一标准

- 本框架 5 层：Platform / Foundation / Core / Feature / Presentation
- 与游戏开发社区常见分层一致（如《Game Engine Architecture》by Jason Gregory 讨论的分层）
- **但非唯一标准**：不同引擎和团队用不同分层（Unity 常用 DDD 风格、Unreal 更粗粒度）
- 本框架的 5 层来自对 155 个游戏 postmortem 的研究（[WORKFLOW-GUIDE 第 260-261 行](file:///workspace/docs/WORKFLOW-GUIDE.md)提到）

### Engine Knowledge Gap Summary —— ❌ 本框架特有（AI 时代特有）

- 概念核心：LLM 训练数据有 cutoff date，引擎版本可能 post-cutoff，导致 LLM 对引擎 API 知识不可靠
- 风险分级：LOW（在训练数据内）/ MEDIUM（接近 cutoff，需验证）/ HIGH（post-cutoff，必须验证）
- **这是针对 AI 辅助开发的特有概念**。传统软件工程无此概念（人类开发者通过文档学习，无"cutoff"问题）。本框架的设计前提是 Claude Code 作为开发伙伴，因此需要显式管理 LLM 知识与引擎版本的差距——这是 AI 时代游戏开发工作流的创新设计。

| **Section Cycle** | ✅ | ❌ Assumptions-First | ✅ 逐 section | N/A | ❌ Rules Summary |
| **即时写入** | ✅ 每节 | ❌ 一次性 | ✅ 每 section | ✅ Phase 8 | ❌ 一次性 |
| **Registry 更新** | entities.yaml | architecture.yaml | ❌ | tr-registry.yaml | ❌ |
| **Director Gate** | CD-GDD-ALIGN | TD-ADR + Engine Specialist | TD-ARCHITECTURE + LP-FEASIBILITY | 无（本身是审查者） | TD-MANIFEST（未定义） |
| **Fresh Session** | /design-review 须 fresh | /architecture-review 须 fresh | 无明确要求 | 本身须 fresh | 无明确要求 |

**核心机制差异的原因**：

- **GDD 用骨架先行 + Section Cycle**：8 个章节相对独立（Overview、Formulas、Edge Cases 可分别设计），适合逐节填；且 GDD 内容多（8 节 × 多轮修改 = 30-50k token），增量写入防上下文爆
- **ADR 用 Assumptions-First + 一次性写入**：章节强耦合（Decision 必须回应 Context，Consequences 必须回应 Decision），分开审会前后矛盾；且单份 ADR 内容量小于 GDD，一次性写入可控

## 常见误区

**误区 1："ADR 可以跳过 Accepted 直接用。"**
❌ 危险。[CLAUDE.md 第 13 行](file:///workspace/docs/CLAUDE.md)明确："Never skip Accepted — stories referencing a Proposed ADR are auto-blocked"。Proposed 状态的 ADR 引用的 story 会被 `/story-readiness` 自动阻断。必须用户手动把 ADR 改成 Accepted。

**误区 2："四个技能可以并行跑。"**
❌ 不行。它们有严格顺序：`/create-architecture` → `/architecture-decision`（× N）→ `/architecture-review` → `/create-control-manifest`。因为后者依赖前者的产出（`/architecture-decision` 需要 `/create-architecture` 的 Required ADRs 列表；`/architecture-review` 需要已写入的 ADRs；`/create-control-manifest` 只读 Accepted ADRs）。

**误区 3："`/architecture-review` 可以接着 `/architecture-decision` 在同一会话跑。"**
❌ 不行。必须 fresh session。同会话会继承完整创作上下文，审查者"既当运动员又当裁判"，丧失独立批判能力。

**误区 4："control-manifest 包含输入控制方案（按键映射等）。"**
❌ 误解。"control" 指管控规则，不是控制器。manifest 是程序员的"什么必须做、什么绝不做"规则表，不含输入映射/控制方案/平台适配/无障碍——那些是 UX 文档的事。

**误区 5："`/create-architecture` 会创建 tr-registry.yaml。"**
❌ 不会。`/create-architecture` 只在自己文档内构建 TR baseline 表格。tr-registry.yaml 由 `/architecture-review` Phase 8 创建和更新。

**误区 6："性能预算可以随便填，反正后面能调。"**
❌ 危险。`/architecture-review` Phase 4 会检查所有 ADR 的性能预算总和是否超 `total_frame_budget_ms`（60FPS=16.6ms）。超了会判冲突。最好写 ADR 时就诚实评估。

**误区 7："两个系统都能改玩家血量，没事吧。"**
❌ 大事。这是 State Ownership 冲突——architecture.yaml 规定每块共享状态只有一个 `owner_system`，只有归属者有 `write_access`。两个 ADR 都写同一状态 = 数据竞争。`/architecture-review` 会检测出来判冲突。

**误区 8："这套架构流程是游戏开发行业标准。"**
⚠️ 部分是。ADR 和 RTM 是软件工程标准（非游戏特有）；5 层架构是游戏开发常见但非唯一标准；control-manifest 和 Engine Knowledge Gap 是本框架特有（后者是 AI 时代特有创新）。

## 小测验

**Q1**：你跑完 `/create-architecture`，它列出了 5 个 Required ADR。你只写了 2 个就急着跑 `/architecture-review`。会怎样？

<details>
<summary>答案</summary>

`/architecture-review` 会判 **FAIL** 或至少 **CONCERNS**——Phase 3 的追溯检查会发现 3 个 Required ADR 对应的 TR 状态是 ❌ Gap（Foundation/Core 层需求未覆盖）。CLAUDE.md 规定 Phase 3 Gate 要求"至少 3 个 ADR 存在且 Accepted"。2 个不够，gate 过不了。必须至少写完 3 个 Foundation 层 ADR。

</details>

**Q2**：为什么 ADR 的模板规则在 docs/CLAUDE.md，而 GDD 的模板规则在 design/CLAUDE.md 和 /design-system 技能里？

<details>
<summary>答案</summary>

三个原因：

1. **跨技能消费**：ADR 的 Status 字段被多个技能强制读取（/story-readiness、/create-stories、/architecture-review、/dev-story、/create-control-manifest），规则必须放跨技能权威位置。GDD 主要被 /design-system 单技能产出，消费方少。
2. **目录管辖权**：docs/CLAUDE.md 管 docs/ 目录（ADR 在 docs/architecture/）；design/CLAUDE.md 管 design/ 目录（GDD 在 design/gdd/）。各管各的。
3. **强制门控需要全局可见**："跳过 Accepted 会被 story 自动阻断"是影响全流程的硬约束，需全局可见。

</details>

**Q3**：你写了一个 ADR，状态是 Proposed。你直接基于它创建了 story 并开始开发。会发生什么？

<details>
<summary>答案</summary>

`/story-readiness` 会**自动阻断**这个 story。CLAUDE.md 第 13 行明确："Never skip Accepted — stories referencing a Proposed ADR are auto-blocked"。必须先把 ADR 状态改成 Accepted（用户手动改，技能不自动改），story 才能通过就绪检查。

</details>

**Q4**：`/architecture-decision` 为什么不用 `/design-system` 那样的"骨架先行 + Section Cycle"机制？

<details>
<summary>答案</summary>

因为 ADR 章节强耦合——Decision 必须回应 Context，Consequences 必须回应 Decision，Alternatives Considered 必须和 Decision 对应。逐节独立审批会导致前后矛盾（比如 Context 写了问题 A，Decision 却解决问题 B）。

`/architecture-decision` 用 **Assumptions-First** 模式：先推导假设→确认→一次性生成完整草稿→多阶段验证（Engine Specialist + TD-ADR + GDD Sync）→一次写入。这样保证整份 ADR 前后一致。

GDD 章节相对独立（Overview、Formulas、Edge Cases 可分别设计），适合逐节填。

</details>

**Q5**：`tr-registry.yaml` 里的 `TR-combat-003` 被从 GDD 删除了。你怎么处理？

<details>
<summary>答案</summary>

**不能删，也不能重编号**。tr-registry.yaml 的核心规则是 Permanent IDs——永不重新编号、永不删除。正确做法：把 `status` 从 `active` 改成 `deprecated`，保留 ID 和历史。这样已引用 `TR-combat-003` 的 story 不会断链。如果是被新需求替换，则标 `superseded-by: TR-combat-NNN` 指向新 ID。

</details>

**Q6**：`/architecture-review` 判了 CONCERNS。你必须修复才能继续吗？

<details>
<summary>答案</summary>

不必须。`/architecture-review` 的判决是 **advisory（建议性的）**——用户最终决定是否继续。CONCERNS 表示"有应解决的问题但非 blocking"。你可以选择带着 CONCERNS 继续，但建议先解决。只有 FAIL 是严重情况（关键缺口或 blocking 冲突），但即便 FAIL 用户仍可决定继续（风险自担）。

</details>

**Q7**：control-manifest 的 "Manifest Version" 是干什么用的？

<details>
<summary>答案</summary>

用于**检测 staleness（过期）**。Story 文件创建时嵌入当前 manifest 的 Version 日期。`/story-readiness` 比较 story 嵌入版本与 manifest 当前版本——如果 manifest 更新了（比如新 ADR 被接受、manifest 重新生成）但 story 还引用旧版本，会提示"stale"，提醒你复查 story 是否仍符合最新规则。

</details>

**Q8**：Engine Knowledge Gap 是什么概念？为什么传统软件工程没有？

<details>
<summary>答案</summary>

Engine Knowledge Gap（引擎知识缺口）是**本框架特有**概念，针对 AI 辅助开发。LLM 训练数据有 cutoff date，引擎版本可能晚于截止，导致 AI 对引擎 API 知识不可靠。分 LOW（在训练数据内）/ MEDIUM（接近 cutoff，需验证）/ HIGH（post-cutoff，必须验证）三档风险。

传统软件工程没有这个概念——人类开发者通过读文档学习，无"cutoff"问题。这是 AI 时代游戏开发工作流的创新设计，前提是 Claude Code 作为开发伙伴。

</details>

## 补充：`src/` 目录放什么——引擎项目源码怎么放

前面讲了 Phase 3 产出架构文档。这些文档指导的是 `src/` 里的代码怎么写。初学者最常问：**`src/` 是放引擎项目源码吗？虚幻引擎有 Content 和 Source 目录，直接把项目放 src 吗？**

### `src/` 不是放引擎项目，是放"游戏逻辑代码"

**关键澄清**：`src/` 放的是**项目自己的游戏源代码**，按"系统层"分子目录组织，**不是**按引擎原生约定组织。

来自 [`.claude/docs/directory-structure.md:7`](file:///workspace/.claude/docs/directory-structure.md)：

```
├── src/                         # Game source code (core, gameplay, ai, networking, ui, tools)
```

来自 [`WORKFLOW-GUIDE.md:100-106`](file:///workspace/docs/WORKFLOW-GUIDE.md) 的详细布局：

```
src/                  # Game source code
  core/               # Engine/framework code（引擎集成层）
  gameplay/           # Gameplay systems（玩法系统）
  ai/                 # AI systems（AI 系统）
  networking/         # Multiplayer code（多人游戏）
  ui/                 # UI code（UI 代码）
  tools/              # Dev tools（开发工具）
```

**核心原则**：`src/` 是"系统层视图"——按代码职责分目录，不按引擎约定分。

### 各引擎怎么和 `src/` 对应

这是模板的**灰区**——不同引擎有不同的原生目录约定。下面是三种主流引擎的实际对应关系。

#### Godot（最清晰，文档示例最多）

- **仓库根 = Godot 项目根**（`project.godot` 在仓库根）
- **`src/` 直接放 GDScript/C# 源码**，按系统层分子目录
- Godot 通过 `res://` 路径引用：`res://src/gameplay/combat/damage_calculator.gd`
- 美术/音频/shader/data 放 `assets/`，Godot 通过 `res://assets/...` 引用

实际示例（来自 [docs/examples/session-implement-combat-damage.md](file:///workspace/docs/examples/session-implement-combat-damage.md)）：

```
仓库根/
├── project.godot              ← Godot 项目文件
├── src/
│   └── gameplay/
│       └── combat/
│           ├── damage_calculator.gd
│           └── health_component.gd
├── assets/                    ← 美术/音频/data
├── design/                    ← 设计文档
└── docs/                      ← 架构文档
```

#### 虚幻引擎（Unreal）—— 存在歧义，需项目自行决断

这是用户问的核心场景。**模板没有显式规定**，但根据多个证据点可以推断：

**事实**：

- 仓库根 = Unreal 项目根（`.uproject` 在仓库根）
- Unreal 原生 `Source/` 目录用于 C++ 类（引擎约定，由 UBT 编译）
- Unreal 原生 `Content/` 目录用于资产（`.uasset`/`.umap`）
- [`unreal-specialist.md:112`](file:///workspace/.claude/agents/unreal-specialist.md) 要求"按 Unreal 推荐文件夹结构组织 `/Content/`"
- [`test-setup/SKILL.md:37,194`](file:///workspace/.claude/skills/test-setup/SKILL.md) 提到 Unreal 测试目录是 `Source/Tests/`（引擎原生）

**三种可行的映射方案**（项目维护者自行决断）：

| 方案 | C++ 类放哪 | Blueprint/资产放哪 | 模板 `src/` 怎么用 |
|------|-----------|-------------------|------------------|
| **A. 引擎原生优先** | Unreal `Source/` | Unreal `Content/` | `src/` 留空或不用 |
| **B. 双轨并存** | Unreal `Source/`（C++ 类） | Unreal `Content/`（资产） | `src/` 放设计文档/代码注释/蓝图设计规格 |
| **C. 模板优先（不推荐）** | `src/core/` + `src/gameplay/` | Unreal `Content/` | 强行把 C++ 放 `src/`，但违背 Unreal 编译约定 |

> ⚠️ **推荐方案 A 或 B**。Unreal 的 `Source/` 目录有强烈的引擎约定——UBT（Unreal Build Tool）按 `Source/` 下的 `.Build.cs` 和模块结构编译。强行把 C++ 类放 `src/core/` 会导致编译失败或需要额外配置。模板的 `src/` 分层模型是为 Godot 这种"项目根=仓库根、代码可任意组织"的引擎设计的，对 Unreal 这种强约定引擎不适用。

**Unreal 项目的推荐结构**：

```
仓库根/
├── MyGame.uproject            ← Unreal 项目文件
├── Source/                    ← Unreal 原生（C++ 类，UBT 编译）
│   ├── MyGame/
│   │   ├── MyGame.Build.cs
│   │   ├── Characters/
│   │   ├── Weapons/
│   │   └── Tests/             ← 引擎原生测试目录
│   └── MyGameEditor/
├── Content/                   ← Unreal 原生（资产）
│   ├── Blueprints/
│   ├── Maps/
│   ├── Materials/
│   └── Data/                  ← 数据驱动配置（对应模板的 assets/data/）
├── Config/
├── design/                    ← 模板的设计文档
├── docs/                      ← 模板的架构文档
└── src/                       ← 留空或放蓝图设计规格文档
```

> 💡 **关键**：`/gate-check` 和 `/dev-story` 等技能会扫描 `src/` 找代码。Unreal 项目如果用方案 A（C++ 在 `Source/`），这些技能可能检测不到代码。需要项目维护者在 CLAUDE.md 里注明"本项目的源码在 `Source/` 而非 `src/`"。

#### Unity —— 同样存在歧义

- Unity 原生 `Assets/` 目录用于所有资产和代码

```
│   ├── Scripts/               ← C# 代码（按系统层分）
│   │   ├── Core/
│   │   ├── Gameplay/
│   │   ├── AI/
│   │   ├── Networking/
│   │   └── UI/
│   ├── Prefabs/
│   ├── Materials/

├── Packages/
├── ProjectSettings/
├── design/
├── docs/
└── src/                       ← 留空或软链接到 Assets/Scripts/
```

### `src/` 的治理机制

`src/` 没有单一规则文件，由多套机制共同治理：

#### 目录级 CLAUDE.md

### 最佳实践总结

1. **仓库根 = 引擎项目根**（`project.godot`/`.uproject`/`ProjectSettings/` 放仓库根）

4. **Unity**：代码放 `Assets/Scripts/`，模板 `src/` 留空或软链接
5. **按需创建 `src/` 子目录，但保持系统层结构**（[`WORKFLOW-GUIDE.md:135-139`](file:///workspace/docs/WORKFLOW-GUIDE.md)）

8. **每个 `src/` 子目录触发对应规则**——写 `src/gameplay/` 自动套 gameplay-code.md 规则
9. **写代码前查 `docs/engine-reference/`**——LLM 训练数据可能早于引擎版本
10. **`src/` 与 `prototypes/` 严格隔离**，原型代码重写不迁移

### 核心矛盾点（写给初学者的诚实说明）

模板的 `src/` 分层模型（按系统层：core/gameplay/ai/networking/ui/tools）是为 **Godot 这种"项目根=仓库根、代码可任意组织"的引擎**设计的。

对于 **Unreal/Unity 这种有强烈原生目录约定的引擎**，模板需要项目维护者自行决断如何映射。模板没有给出明确答案——这是设计上的留白，不是疏漏。原因可能是：

- Unreal 的 `Source/` 由 UBT 按模块编译，强行改路径会破坏编译
- Unity 的 `Assets/` 由 Asset Pipeline 管理，代码必须在 `Assets/` 下
- 强行统一会导致引擎工具链失效

**初学者的实操建议**：

- 用 Godot → 直接按模板，`src/` 放 GDScript
- 用 Unreal → C++ 放 `Source/`，在 CLAUDE.md 注明"本项目源码在 Source/ 而非 src/"，让 AI 知道去哪找代码
- 用 Unity → 代码放 `Assets/Scripts/`，同样在 CLAUDE.md 注明

## 深入：虚幻引擎项目怎么放——用 UEProject/ 取代 src/

初学者最常追问：**根目录已经有 design/、docs/、tests/ 等模板目录，不空。直接把虚幻引擎项目建到仓库根的 `UEProject/` 里（含 `Source/`、`Content/`、`.uproject`），让 `UEProject/` 取代 `src/`，`src/` 就留空。这样行吗？技能涉及的 src 目录是硬编码吗？能调整吗？**

### 简短回答

- **推荐用 `UEProject/` 取代 `src/`**——这是更符合虚幻/Unity 引擎原生结构的方案
- **`src/` 路径是部分硬编码**——规则文件的 `paths` 字段、3 个 Hook 脚本、技能提示文本里有字面 `src/`，需要调整
- **没有官方"代码路径配置"开关**——只能手动改文件适配
- **改完后 `src/` 留空**（保留 `.gitkeep` 占位），所有代码在 `UEProject/Source/` 下

### 为什么用 UEProject/ 取代 src/ 更符合引擎原生结构

虚幻引擎的项目创建流程（Epic Games Launcher / Unreal Editor → New Project）会把 `.uproject`、`Source/`、`Content/`、`Config/`、`Plugins/` 等一堆文件直接生成到指定目录。UE 的工具链（UBT、UAT）预设了 `Source/` 在项目根下、`Content/` 在项目根下这种结构。

**用 `UEProject/` 取代 `src/` 的好处**：

- UE 项目自包含（`.uproject` + `Source/` + `Content/` + `Config/` 等全在 `UEProject/` 下）
- UE 工具链原生结构不被破坏（`UEProject/Source/` 就是 UE 认识的 `Source/`）
- 与仓库其他资产（design/、docs/、tests/）平级，根目录整洁
- `src/` 留空不碍事，模板的其他机制（规则、Hook）改个路径前缀就能适配
- Unity 同理：用 `UnityProject/` 取代 `src/`，代码放 `UnityProject/Assets/Scripts/`

代价：需要调整规则文件、Hook 脚本、技能提示文本里的 `src/` 引用，让它们指向 `UEProject/Source/`。

本方案（`UEProject/` 取代 `src/`）与官方方向一致——都是用引擎原生 `Source/` 作为代码根，改 rule 的 paths。区别是官方假设 `Source/` 在仓库根，本方案把 `Source/` 放在 `UEProject/` 子目录下以保持根目录整洁。paths 前缀从 `Source/core/**` 变成 `UEProject/Source/**/Core/**`，只是多一层前缀。

### 推荐流程

按这个顺序操作：

1. **创建 UE 项目到 `UEProject/`**——用 Unreal Editor 新建项目时选 `UEProject/` 作为目录
2. **在 `UEProject/Source/MyGame/` 下按域分子目录**——`Core/`、`Gameplay/`、`AI/`、`Networking/`、`UI/`
3. **改 6 处文件**（按上面"完整修改清单"）
4. **在根 CLAUDE.md 注明代码路径**（修改 6）
5. **跑 `/setup-engine`**——让它识别 UE 版本，更新引擎引用文档
6. **跑 `/onboard`**——让它扫描 `UEProject/Source/` 推断架构（AI 会根据 CLAUDE.md 去那里找）

### Unity 项目同理

Unity 项目用 `UnityProject/` 取代 `src/`：

```
仓库根/
├── UnityProject/              ← Unity 项目根（取代 src/）
│   ├── Assets/
│   │   ├── Scripts/           ← C# 代码（按系统层分）
│   │   │   ├── Core/
│   │   │   ├── Gameplay/
│   │   │   ├── AI/
│   │   │   ├── Networking/
│   │   │   └── UI/
│   │   ├── Prefabs/
│   │   ├── Materials/
│   │   └── Data/              ← ScriptableObject 配置
│   ├── Packages/
│   └── ProjectSettings/
├── src/                       ← 留空
├── design/
└── docs/
```

规则 paths 改为 `UnityProject/Assets/Scripts/**/Core/**` 等，Hook 和技能同理。
