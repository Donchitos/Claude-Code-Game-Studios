## 0. 核心思想：数据先行，逻辑消费数据

```
数据（上下文文档）              逻辑（skill + agent）
─────────────────              ─────────────────────
game-concept.md      ←生成于──  /brainstorm
systems-index.md     ←生成于──  /map-systems
GDD ×N               ←生成于──  /design-system
ADR ×N               ←生成于──  /architecture-decision
control-manifest.md  ←生成于──  /create-control-manifest
story ×N             ←生成于──  /create-stories
src/ + tests/        ←生成于──  /dev-story
        ↓ 被消费于
下游逻辑必须读上游数据才能跑：
/create-stories 读 GDD + ADR + manifest
/dev-story     读 story + TR registry + ADR + manifest
/story-done    读 story + 引用的 GDD/ADR
```

**一环套一环**：没有 game-concept 就没法 map-systems；没有 GDD 就没法写 ADR（TR-ID 无从提起）；没有 ADR（Accepted）就没法建 story（会 Blocked）；没有 story 就没法 dev-story。**每个 skill 的输入都是上一个 skill 的输出**。

**引用而非复制**：下游文档只嵌上游的 ID（TR-ID、ADR 编号、manifest 版本日期），不复制正文——上游改了，下游引用永远指向最新。这是数据体系不腐烂的关键设计。

## 2.3 agent 之间的依赖与调用规则

三层层级（[agent-coordination-map.md](file:///workspace/.claude/docs/agent-coordination-map.md)）：

```
Tier 1 总监: creative-director / technical-director / producer
Tier 2 主管: game-designer / lead-programmer / art-director / audio-director
             / narrative-director / qa-lead / release-manager / localization-lead
Tier 3 专家: 程序员×6 / 设计师×5 / 艺术音频×3 / QA×3 / 运营×5 / 引擎专家×15
```

- **垂直委派**：总监 → 主管 → 专家，复杂决策不越级
- **横向咨询**：同层可互相咨询，但不得跨域拍板
- **冲突升级**：设计冲突→creative-director；技术冲突→technical-director；范围冲突→producer
- **实际实现**：所有"委派"都发生在 skill 正文里——主会话按 skill 指示用 Agent 工具派生。agent 之间**不直接互调**，都经主会话中转（hub-and-spoke，不是 p2p）

# 第四部分：数据体系的四条设计原则（抄作业必看）

### 原则 1：引用而非复制
story 里不抄 GDD 原文，只写 `TR-COMBAT-003`；不抄 ADR 全文，只写 `adr-0007`。上游更新，下游永远最新。代价：读的时候要多跳一层（所以才有 tr-registry.yaml 这种"跳转表"）。

### 原则 2：状态即文件
进度不靠对话记忆，靠 `stage.txt`（一行）、`review-mode.txt`（一行）、`sprint-status.yaml`、`active.md`。会话崩了/压缩了，hook 和 skill 靠这些文件恢复。**"文件即记忆，不是对话"**（WORKFLOW-GUIDE 原话）。

### 原则 3：逐节写盘
`/design-system` 每节批准后立即写文件，不攒到最后。崩溃/压缩只丢未定的讨论，已定的决策都在盘上。

### 原则 4：人读 MD，机读 YAML/单行
给人看的长文档用 MD 自由结构；给逻辑读的用 YAML（tr-registry、sprint-status、entities）或单行 txt（stage、review-mode）。消除了"脆弱的 markdown 扫描"（WORKFLOW-GUIDE 原话）。

## 小测验

**Q1**：为什么 `/create-stories` 要求 ADR 必须是 Accepted？Proposed 会怎样？
> **A**：Proposed 表示决策未定稿，基于它写代码会返工。所以 story 会标记 `Status: Blocked`。数据体系用状态字段实现"逻辑消费的时序约束"。

**Q2**：story 文件里嵌 manifest 版本日期有什么用？
> **A**：检测陈旧。若 manifest 在 story 创建后更新过（决策变了），`/story-readiness` 会警告——防止按旧规则写新代码。这是"引用而非复制"的配套保鲜机制。

**Q3**：为什么状态用 YAML/单行 txt 而不是 MD？
> **A**：MD 给人看，结构松散；skill/hook/脚本要机器解析，YAML 和单行 txt 稳定。WORKFLOW-GUIDE 明说这消除了"脆弱的 markdown 扫描"。

**Q4**：agent 之间会直接互相调用吗？
> **A**：不会。所有派生都由主会话按 skill 正文发起（hub-and-spoke）。"总监→主管→专家"的层级是 skill 正文里的路由规则，不是 agent 间的直接通信。

**Q5**：如果跳过 `/map-systems` 直接 `/design-system` 会怎样？
> **A**：数据链断了——design-system 要读 systems-index 来确定上下游依赖和设计顺序。WORKFLOW-GUIDE 引 155 个游戏复盘：跳过系统枚举，制作期成本翻 5-10 倍。Phase 1 门禁也过不了。

**Q6**：`/dev-story` 一共要读几份文档？分别管什么？
> **A**：5 份——story（做什么+验收）、tr-registry（追溯设计需求）、ADR（怎么做的决策）、control-manifest（代码层规则）、technical-preferences（引擎约定）。逻辑跑起来前，数据必须先到位。
