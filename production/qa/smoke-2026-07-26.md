## 2. Honest speed derivation (production, not the spike)

The spike's own 144 cells/sec assumed `PAN_SPEED_FACTOR 1.2` / `DISTANCE_MAX 120.0`
— an earlier prototype's constants, not the shipped `CameraInputConfig`. The
shipped production defaults are `distance_max = 60.0`, `pan_speed_factor = 0.7`
(`src/camera_input/camera_input_config.gd`), and `CameraInput.derive_pan_delta`'s
own formula (`input_dir.normalized() * delta * distance * pan_speed_factor`) gives
a steady-state max of **`distance_max * pan_speed_factor` = 42.0 cells/sec** — the
speed this story's traverse measurement actually uses. Restated explicitly in the
tool's own class doc comment so a future config change cannot silently
invalidate this measurement's stated methodology.

## 5. `max_chunk_generation_cost_ms` — chosen value + rationale

**Chosen: 1.0 ms** (NEW field, `data/config/voxel_world_config.tres` +
`VoxelWorldConfig.max_chunk_generation_cost_ms`'s own doc comment).

- ~4.7x headroom over the measured p95 compute-only cost (0.212 ms), ~4.4x over
  the measured worst sample (0.226 ms).
- **Not a runtime throttle** — ADR-0015 Decision §6 forbids any synchronous
  fallback/preemption of an in-flight `WorkerThreadPool` task ("a synchronous
  fallback IS the failure mode"), so this value cannot and does not cap
  `_bg_regenerate_from_seed`'s actual wall time. It is a recorded REGRESSION
  GUARD: a future change that makes terrain generation dramatically more
  expensive (added noise octaves, tree stamping, etc.) should be checked
  against this bound rather than silently eroding ADR-0015's "regen_worst =
  0.00 ms by construction" async guarantee.
- `VoxelWorldConfig.validate()` returns no clamp for `1.0` (inside the new
  `[0.001, 1000.0]` range — `CHUNK_GENERATION_COST_MS_MIN`/`_MAX`).

## 6. `max_concurrent_async_tasks` — chosen value + rationale

**Chosen: 32 (kept, the already-shipped value)** — measured fresh against
production code, not re-cited from the spike.

Full-span corridor traverse, 2000x2000-cell world (shipped `world_width_cells`/
`world_depth_cells` default), `view_radius_chunks=24`/`settlement_radius_chunks=8`
(shipped defaults), `page_budget_ms`/`evict_budget_ms=4.0` (shipped defaults),
42.0 cells/sec (§2), 3 one-way legs, 8,397 `update_residency()` calls sampled per
cap:

| Cap | avg | p95 | worst | Budget | Result |
|---|---|---|---|---|---|
| 32 | 2.369 ms | 3.927 ms | 5.512 ms | ≤ 16.6 ms | **PASS** (3.0x headroom on worst) |
| 64 | 2.359 ms | 2.836 ms | 10.727 ms | ≤ 16.6 ms | **PASS** (1.5x headroom on worst) |

Both caps stay comfortably inside the frame budget — confirms the ADR-0015
spike's own "the exact cap is not load-bearing" finding holds on production
code, not just the spike's synthetic terrain-gen formula. **Kept at 32**: no
measured benefit to 64 (worse worst-frame here, only a marginally better p95),
and a smaller cap leaves more `WorkerThreadPool` headroom for other systems
(mesh building, Villager AI) sharing the same pool. Per ADR-0015 Decision §6,
cap-miss = "stay queued," never "run synchronously" — this value remains
NON-CRITICAL to correctness, recorded here so it is never later mistaken for a
hard correctness threshold.

`VoxelWorldConfig.validate()` returns no clamp for `32` (inside the existing
`[1, 128]` range — `MAX_CONCURRENT_ASYNC_TASKS_MIN`/`_MAX`).

`VoxelWorldGrid` code (not the spike): `max_concurrent_async_tasks` kept at 32
